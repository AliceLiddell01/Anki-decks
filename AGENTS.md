# Инструкции для агентов Anki-decks

## 1. Назначение

Этот репозиторий хранит персональные Anki-колоды в JSON-формате CrowdAnki и контекст для их безопасного анализа и редактирования.

Отвечай пользователю, пиши документацию и сообщения коммитов на русском языке. Точные имена JSON-ключей, путей, UUID, HTML/CSS, японских выражений и внешних инструментов сохраняй без перевода.

## 2. Источники истины

Для задачи над конкретной колодой используй источники в таком порядке:

1. целевой CrowdAnki JSON в текущей ветке;
2. связанные с ним `note_models`, `deck_configurations`, дерево `children` и сами `notes`;
3. относящиеся к задаче документы `.codex/context/`;
4. официальная документация CrowdAnki/Anki, только если требуется уточнить внешний формат или поведение.

Контекстные документы помогают навигации, но не заменяют проверку фактического JSON.

## 3. Маршрутизация контекста

Перед работой с колодой:

1. прочитай `.codex/context/INDEX.md`;
2. определи область изменения;
3. открой только документы, которые владеют этой областью;
4. не загружай большой JSON целиком, если задача решается точечным поиском или скриптом.

Базовая карта репозитория — `.codex/context/01-PROJECT-MAP.md`.
Схема и безопасная навигация по CrowdAnki JSON — `.codex/context/02-CROWDANKI-JSON.md`.
Проверки после изменения — `.codex/context/03-VERIFICATION.md`.

Для структурного анализа экспорта используй toolkit `tools/anki-repo`
(`inspect`, `find`, `stats`, `validate`, `qa`, `review`, `review-check`) вместо
ручного чтения многомегабайтного `deck.json`. Его контракт описан в
`tools/anki-repo/README.md`.

Для проверки содержимого карточек используй `qa` (детерминированные findings по
фиксированному реестру правил) и `review` (компактный batch заметок по найденной
проблеме). Предложения внешнего агента проверяй через `review-check`: он ничего не
пишет и выдаёт готовый запрос для `edit`. Toolkit не вызывает LLM API и не ходит в
сеть, поэтому содержательное суждение о карточке делает внешний агент, а
`anki-repo` остаётся детерминированной границей репозитория.

Для правки значения поля существующей заметки используй `edit` того же toolkit'а
вместо ручного скрипта: он по умолчанию работает как dry-run, требует `--expect`,
пишет только по явному `--apply`, меняет только значения полей и проверяет
байтовый diff до записи. `edit` не является общим редактором JSON: он не
добавляет, не удаляет и не перемещает сущности, не трогает `media/` и
идентификаторы, и отказывается править неканонический или невалидный экспорт.

## 4. Инварианты CrowdAnki

- Не меняй `crowdanki_uuid`, `guid`, `note_model_uuid` и `deck_config_uuid` без явной причины.
- Не меняй порядок полей заметки вслепую: сначала разреши `note_model_uuid` и сопоставь `fields` с `note_models[].flds[].ord`.
- Не считай `media_files` содержимым media: это список ссылок/имён файлов, а не бинарные данные.
- Не смешивай правку лингвистического содержимого с изменением модели карточки, HTML/CSS или настроек планировщика, если задача этого не требует.
- При массовой правке используй детерминированный скрипт или точечное преобразование; избегай ручного переписывания многомегабайтного JSON.
- Сохраняй существующее форматирование JSON, если нет отдельной задачи на нормализацию.
- Не удаляй неизвестные ключи только потому, что они не нужны текущей задаче.

## 5. Работа с японскими словарными колодами

Текущий целевой путь словарной колоды:

`decks/japanese/words/`

Для знакомого экспорта ожидается модель заметки со следующими полями:

1. `Слово`
2. `Часть речи`
3. `Значение`
4. `Ударение`
5. `Пример`
6. `Похожие слова`

Это удобная карта, а не лицензия на предположение: после добавления или замены JSON всегда сверяй фактический `note_model_uuid` и `note_models[].flds`.

Состав колод — это данные, а не контракт репозитория. `tools/anki-repo` работает
с произвольным CrowdAnki-экспортом и не знает имён полей конкретной модели.
Не закрепляй текущий состав, уровни, имена моделей и полей в коде, тестах, CI или
документации: изменение или временное отсутствие колоды не должно требовать их
правки.

Не смешивай два разных инварианта:

- default-набор тестов независим от live payload: тесты строят собственные
  синтетические экспорты и `decks/**` не читают;
- repository CI валидирует live payload как данные репозитория: он рекурсивно
  находит все фактически присутствующие CrowdAnki-экспорты под `decks/**` и
  требует их структурной валидности. Структурно невалидный закоммиченный экспорт
  делает CI красным, отсутствие экспортов — нет.

Подробности — в разделе 7.

## 6. Изменения и Git

- Одна самостоятельная задача — одна рабочая ветка и один PR.
- Не работай напрямую в `main`.
- Не сливай PR без отдельной явной команды пользователя.
- В PR описывай фактический набор изменений и выполненные проверки.
- Не добавляй в постоянный контекст номер текущего PR, SHA, временный план или разовые результаты ревью.
- Не оставляй в постоянном коде, тестах, CI и документации временных
  идентификаторов: номеров stage/этапов, номеров PR, SHA, абсолютных локальных
  путей и имён авторов.

## 7. Проверки и CI

Единственная точка сборки — корневой Cargo workspace. Оттуда же запускаются
проверки:

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

Заявленная MSRV объявлена один раз — в `[workspace.package] rust-version`
корневого `Cargo.toml`; участники наследуют её. Не дублируй версию в workflow,
скриптах или документации: CI читает её через `cargo metadata`.

`.github/workflows/ci.yml` выполняет эти же проверки независимо от локального
окружения: на `pull_request`, на push в default branch и вручную. Дополнительно он
сам находит `deck.json` внутри `decks/` и вызывает для каждого `validate`: каждый
фактически присутствующий экспорт обязан быть структурно валидным, и ошибка
`validate` делает шаг красным. Отсутствие экспортов под `decks/` ошибкой не
является. CI только читает репозиторий (без секретов, публикаций и записи в
колоды) и не называет ни одной колоды, уровня, модели или поля по имени: он не
закрепляет текущий состав `decks/`, но валидирует фактический payload как данные
репозитория. Независимость default-тестов от payload — отдельный инвариант: тесты
синтетические и `decks/**` не читают. Заметки агента, временный план и разовые
результаты ревью в CI не попадают.

## 8. Skills

`.agents/skills/` содержит repository skills — по одному каталогу
`.agents/skills/<name>/SKILL.md` на skill, с собственными reference-файлами.
Применяй их, когда текущий запрос явно подпадает под назначение skill.

- `anki-coderabbit-review` — явный CodeRabbit review cycle текущего checkout.
  Маршрутизируй сюда только явный CodeRabbit intent: «сделай ревью CodeRabbit»,
  «запусти CodeRabbit», «прогони кодрэббит», «сделай 5 итераций CodeRabbit»,
  «повтори CodeRabbit ещё 2 раза», продолжение уже начатого CodeRabbit-цикла.
  Default — 3 completed iterations, если пользователь не назвал своё
  положительное число; каждая completed iteration заканчивается отдельным
  commit + push текущей ветки. Merge не входит в этот cycle.
- Обычное «ревью», generic code review без CodeRabbit intent, обычная разработка,
  подготовка PR, обычный commit/push и задачи по изменению самого skill в этот
  skill не маршрутизируются.

Процедуру CodeRabbit workflow владеет сам skill; не дублируй её здесь и не
переноси в `.codex/context/`.

Новые skills и изменения существующих добавляй только по явной просьбе
пользователя, не придумывая преждевременную автоматизацию.
