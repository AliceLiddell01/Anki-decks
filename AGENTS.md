# Инструкции для агентов Anki-decks

## 1. Назначение

Этот репозиторий хранит персональные Anki-колоды в JSON-формате CrowdAnki и контекст для их безопасного анализа и редактирования.

Отвечай пользователю, пиши документацию и сообщения коммитов на русском языке. Точные имена JSON-ключей, путей, UUID, HTML/CSS, японских выражений и внешних инструментов сохраняй без перевода.

## 2. Источники истины

Для задачи над конкретной колодой используй источники в таком порядке:

1. целевой CrowdAnki JSON в текущей ветке;
2. связанные с ним `note_models`, `deck_configurations`, дерево `children` и сами `notes`;
3. относящиеся к задаче документы `.codex/context/`;
4. официальная документация CrowdAnki/Anki, только если требуется уточнить внешний формат или поведение.

Контекстные документы помогают навигации, но не заменяют проверку фактического JSON.

## 3. Маршрутизация

Перед работой с колодой:

1. прочитай `.codex/context/INDEX.md` — он владеет картой владельцев и тем, какие вопросы кому принадлежат;
2. определи область изменения;
3. открой только тех владельцев, которые владеют этой областью;
4. не загружай большой JSON целиком, если задача решается точечным поиском или скриптом.

Профильные владельцы вне `.codex/context/`:

- `tools/anki-repo/README.md` — контракт набора инструментов `anki-repo`: команды, вывод, коды возврата, реестр QA-правил и границы `edit`;
- `tools/asset-store/README.md` — публичный контракт общего хранилища ресурсов и CLI изображений кандзи, границы владения файловой системой, жизненный цикл, `new`/`full` и машинные результаты;
- `.agents/skills/anki-card-create/` — агентский процесс создания новых карточек и пакета ресурсов кандзи;
- `.agents/skills/anki-git-workflow/` — обычная процедура Git/GitHub;
- `.agents/skills/anki-code-review/` — независимое ревью кода без записи в файлы и без CodeRabbit;
- `.agents/skills/anki-coderabbit-review/` — явно запрошенный цикл ревью CodeRabbit.

Процедурой каждого рабочего процесса владеет сам его владелец. Не дублируй её здесь, не переноси в `.codex/context/` и не создавай второго владельца той же процедуры.

Для структурного анализа экспорта, проверки содержимого карточек и точечной правки значения поля существующей заметки используй набор инструментов `tools/anki-repo`, а не ручное чтение или правку многомегабайтного `deck.json`. Он не вызывает LLM API, не ходит в сеть и меняет `deck.json` только по явному `--apply`; содержательное суждение о карточке делает внешний агент, а не набор инструментов.

Мутирующих команд в наборе инструментов четыре, и каждая работает по тем же правилам
(режим без записи по умолчанию, запись только по явному `--apply`, канонический `deck.json`,
отказ при невалидном результате):

- `edit` — значение существующего поля существующей заметки;
- `create` — новая заметка в **уже существующей** колоде **уже существующей**
  модели. Перед ним смотри фактическую схему полей через `models`: имя поля —
  свойство конкретного экспорта, а не контракт репозитория. По умолчанию значения
  новых полей не содержат ссылок на медиа; правила могут явно разрешить проверенные
  изображения кандзи и высотного ударения только для сочетания UUID модели и точного
  имени поля. Контракт правил и размещения файлов —
  `tools/anki-repo/README.md`;
- `retire` — вывод заметки из обращения одним тегом. Физического удаления заметок
  в наборе инструментов нет: заметку, которую пора убрать из работы, помечают и удаляют
  вручную в Anki, когда это действительно нужно;
- `migrate-media` — перевод ссылок на старое имя файла потребителя на текущее
  каноническое имя домена.

`migrate-media` — **единственное** исключение из правила «существующие заметки не
меняются», и исключение узкое: команда правит только те ссылки, чью семантику
доказала (поле принадлежит владельцу канонического имени, а форма ссылки — та
самая, которую он распознаёт), и отказывает целиком, если доказать не удалось.
Обход этого пути — ручная правка `deck.json`, переименование файлов в `media/`,
замена слова в запросе, лишь бы конфликт не возник, — не годится: такие обходы не
оставляют ни доказательства семантики, ни согласованного состояния `media_files`.

Изменения экспорта показывай до записи детерминированным diff (`edit`/`create`/
`retire`/`migrate-media` в режиме без записи), а после — статическим отчётом `visual-report`
между состоянием до и после. Каталог отчёта — это артефакт прогона: он обязан лежать
вне `decks/**`, не попадать в коммит и не заменять собой проверку фактического JSON.

Маршрут «создать и проверить» целиком описан в `tools/anki-repo/README.md`; там же
владелец контракта каждой из этих команд.

## 4. Инварианты CrowdAnki

- Не меняй `crowdanki_uuid`, `guid`, `note_model_uuid` и `deck_config_uuid` без явной причины.
- Не меняй порядок полей заметки вслепую: сначала разреши `note_model_uuid` и сопоставь `fields` с `note_models[].flds[].ord`.
- Не считай `media_files` содержимым медиа: это список ссылок/имён файлов, а не бинарные данные.
- Не смешивай правку лингвистического содержимого с изменением модели карточки, HTML/CSS или настроек планировщика, если задача этого не требует.
- При массовой правке используй детерминированный скрипт или точечное преобразование; избегай ручного переписывания многомегабайтного JSON.
- Сохраняй существующее форматирование JSON, если нет отдельной задачи на нормализацию.
- Не удаляй неизвестные ключи только потому, что они не нужны текущей задаче.

## 5. Данные и контракт репозитория

Состав колод — это данные, а не контракт репозитория. Не закрепляй текущие
колоды, уровни, имена моделей и имена полей как обязательный контракт в коде,
тестах и CI: изменение, перемещение или временное отсутствие колоды не должно
требовать их правки. Документация может описывать текущее состояние `decks/` как
пример навигации, но обязана помечать его состоянием на сегодня, а не требованием
к репозиторию; источник истины — фактический JSON.

После добавления или замены экспорта сверяй фактический `note_model_uuid` и
`note_models[].flds`, а не предполагай их. Описание текущей модели — удобная карта
навигации, а не лицензия на предположение.

Отсюда два инварианта, которые нельзя смешивать:

- набор тестов по умолчанию независим от фактических данных репозитория: тесты строят собственные
  синтетические экспорты и `decks/**` не читают;
- CI репозитория валидирует фактически присутствующие данные репозитория: он рекурсивно
  находит все фактически присутствующие CrowdAnki-экспорты под `decks/**` и
  требует их структурной валидности. Структурно невалидный закоммиченный экспорт
  делает CI красным, отсутствие экспортов — нет.

## 6. Изменения и Git

- Одна самостоятельная задача — одна рабочая ветка и один PR.
- Не работай напрямую в `main`.
- Жизненный цикл работы с Git/GitHub принадлежит `.agents/skills/anki-git-workflow/`. Локальный commit не завершает обычную публикуемую задачу: публикация доводится до проверенного удалённого состояния.
- Merge выполняется только по отдельной текущей явной команде пользователя.
- В PR описывай фактический набор изменений и выполненные проверки.
- Не добавляй в постоянный контекст номер текущего PR, SHA, временный план или разовые результаты ревью.
- Не оставляй в постоянном коде, тестах, CI и документации временных
  идентификаторов: номеров этапов, номеров PR, SHA, абсолютных локальных
  путей и имён авторов.

## 7. Проверки и CI

Единственная точка сборки — корневое рабочее пространство Cargo. Оттуда же запускаются
проверки:

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

`.github/workflows/ci.yml` выполняет те же проверки независимо от локального
окружения и дополнительно валидирует каждый фактически найденный экспорт под
`decks/`. CI только читает репозиторий и не называет ни одной колоды, уровня,
модели или поля по имени. Заметки агента, временный план и разовые результаты
ревью в CI не попадают.

Заявленная MSRV объявлена один раз — в `[workspace.package] rust-version`
корневого `Cargo.toml`; участники наследуют её. Не дублируй версию в процессе CI,
скриптах или документации.

Детали проверок, кодов возврата и локального воспроизведения набора —
`.codex/context/03-VERIFICATION.md`.

## 8. Skills

`.agents/skills/` содержит skills репозитория — по одному каталогу
`.agents/skills/<name>/SKILL.md` на skill, с собственными справочными файлами.
Применяй их, когда текущий запрос подпадает под назначение skill.

- `anki-card-create` — создание новых карточек в существующей колоде от
  пользовательского запроса до проверенного результата: фактическая схема модели,
  настроенные обработчики, зависимости ресурсов кандзи, частичный прогресс, проверка
  человеком и отдельная публикация только ресурсов. Применяется к просьбам создать
  карточку или пакет карточек и продолжить такой процесс. Не применяется к правке
  существующих заметок.
- `anki-git-workflow` — обычная процедура Git/GitHub текущей рабочей копии.
  Применяется автоматически, когда работа достигает создания ветки, подготовки индекса, commit,
  push, PR, merge или очистки после работы, а также по явным просьбам
  «закоммить», «запушь», «создай PR», «обнови PR», «слей PR». Не применяется к
  объяснению Git без изменений.
- `anki-code-review` — независимое ревью кода PR/текущей рабочей копии без записи в файлы.
  Маршрутизируй сюда обычные просьбы «сделай код-ревью», «проведи код-ревью»,
  «сделай ревью PR», в том числе при явном отказе от запуска CodeRabbit.
  Skill сам восстанавливает требования, включая исходный текст постановки задачи из Windows
  Downloads, проверяет diff в
  контексте окружающего кода и не исправляет/не публикует изменения как
  побочный эффект.
- `anki-coderabbit-review` — явный цикл ревью CodeRabbit текущей рабочей копии.
  Маршрутизируй сюда только явное положительное намерение запустить или
  продолжить CodeRabbit: «сделай ревью CodeRabbit»,
  «запусти CodeRabbit», «прогони кодрэббит», «сделай 5 итераций CodeRabbit»,
  «повтори CodeRabbit ещё 2 раза», продолжение уже начатого CodeRabbit-цикла.
  По умолчанию — 3 завершённые итерации, если пользователь не назвал своё
  положительное число. Merge не входит в этот цикл.
- Маршрут определяется намерением с учётом отрицания и порядка действий.
  Само упоминание CodeRabbit не разрешает его запуск: «сделай код-ревью без
  CodeRabbit» и «проверь самостоятельно, не запускай CodeRabbit» остаются в
  `anki-code-review`. При запросе независимого ревью с последующим сравнением
  сначала заверши и зафиксируй собственный анализ, затем читай внешний результат
  по контракту `anki-code-review`. Сравнение с доступным результатом не разрешает
  новый запуск CodeRabbit; последующая фаза `anki-coderabbit-review` требует
  явного положительного поручения его запустить. Задача по изменению самого
  skill ревью не является просьбой запустить ревью.

Процедурой каждого рабочего процесса владеет сам skill; не дублируй её здесь и не переноси
в `.codex/context/`.

Новые skills и изменения существующих добавляй только по явной просьбе
пользователя, не придумывая преждевременную автоматизацию.
