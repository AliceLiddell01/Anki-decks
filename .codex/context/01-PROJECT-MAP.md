# Карта репозитория

## Назначение

`Anki-decks` — хранилище версионируемых CrowdAnki JSON-экспортов персональных Anki-колод и минимального контекста для агентов, которые эти экспорты анализируют или редактируют.

## Структура

```text
AGENTS.md
README.md
Cargo.toml                   # корневой Cargo workspace: owner edition и MSRV
Cargo.lock
.github/
└── workflows/
    └── ci.yml               # независимый CI: код/тесты и заявленная MSRV
.agents/
└── skills/
.codex/
└── context/
    ├── INDEX.md
    ├── 01-PROJECT-MAP.md
    ├── 02-CROWDANKI-JSON.md
    └── 03-VERIFICATION.md
decks/
└── japanese/
    └── words/
tools/
└── anki-repo/               # toolkit анализа и точечной правки CrowdAnki-экспорта
```

## Владельцы

- `decks/` — сами версионируемые колоды.
- `decks/japanese/words/` — японская словарная колода.
- `.codex/context/` — долговременные карты формата и рабочего процесса.
- `.agents/skills/` — repository skills, по каталогу на skill; процедуру владеет
  сам skill, а не этот файл.
- `tools/anki-repo/` — Rust package `anki-repo` для анализа экспорта и одной
  строго ограниченной правки его значений (`edit`); его контракт описан в
  `tools/anki-repo/README.md`. Это участник корневого workspace, а не отдельный
  workspace: `cargo` запускается из корня репозитория.
- `Cargo.toml` в корне — единственный владелец `[workspace.package]`: заявленной
  MSRV (`rust-version`) и `edition` для всех Rust-участников. `Cargo.lock` тоже
  лежит в корне.
- `.github/workflows/ci.yml` — независимый CI репозитория: читает код, не
  публикует артефакты и не использует секреты. Подробности — в `03-VERIFICATION.md`.
- `AGENTS.md` — короткий обязательный контракт для любого агента.

`decks/` — данные, а не контракт репозитория: toolkit работает с произвольным
CrowdAnki-экспортом и не знает имён полей конкретной модели, а CI и default-набор
тестов не зависят от того, какие колоды сейчас лежат в `decks/`. Текущий состав
и имена моделей ниже — состояние на сегодня, а не требование к репозиторию.

## Как находить место изменения

1. Определить целевой файл колоды в `decks/`.
2. Установить, меняется ли содержимое заметок, структура deck tree, note model, deck config или только документация.
3. Для JSON сначала получить верхнеуровневые ключи и нужные UUID/имена, затем переходить к конкретному поддереву.
4. Не читать все `notes` подряд, если задача относится к одной модели, одному уровню, одному уроку или ограниченному набору слов.
5. После изменения выполнить проверки из `03-VERIFICATION.md`.

## Быстрый анализ без ручного чтения JSON

Для структурного анализа экспорта используй `tools/anki-repo`: `inspect`
показывает состав колоды, `find` ищет заметки по `guid` или по значению поля,
`stats` считает распределения, `validate` проверяет структурные инварианты.

Для проверки содержимого карточек используй `qa` (детерминированные findings по
фиксированному реестру правил) и `review` (компактный batch заметок по найденной
проблеме), а предложения внешнего агента проверяй через `review-check`: он ничего
не пишет и выдаёт готовый запрос для `edit`. Toolkit не вызывает LLM API: разбор
содержимого делает внешний агент.

Для правки значения поля существующей заметки используй `edit` того же toolkit'а,
а не ручной скрипт: он разрешает то же соответствие `note_model_uuid` →
`flds[].ord` → `fields`, по умолчанию работает как dry-run, требует `--expect` и
проверяет байтовый diff до записи. Команды и контракт вывода описаны в
`tools/anki-repo/README.md`.
