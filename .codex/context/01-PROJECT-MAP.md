# Карта репозитория

## Назначение

`Anki-decks` — хранилище версионируемых CrowdAnki JSON-экспортов персональных Anki-колод и минимального контекста для агентов, которые эти экспорты анализируют или редактируют.

## Структура

```text
AGENTS.md
README.md
Cargo.toml                   # корневое рабочее пространство Cargo: владелец edition и MSRV
Cargo.lock
.github/
└── workflows/
    └── ci.yml               # CI: код/тесты, заявленная MSRV, validate найденных экспортов
.agents/
└── skills/
.codex/
└── context/
    ├── INDEX.md
    ├── 01-PROJECT-MAP.md
    ├── 02-CROWDANKI-JSON.md
    └── 03-VERIFICATION.md
decks/
└── japanese/
    └── words/
tools/
├── anki-repo/               # набор инструментов анализа и точечной правки CrowdAnki-экспорта
└── asset-store/             # общая библиотека ресурсов и CLI kanji-assets
```

## Владельцы

- `decks/` — сами версионируемые колоды.
- `decks/japanese/words/` — японская словарная колода.
- `.codex/context/` — долговременные карты формата и рабочего процесса.
- `.agents/skills/` — skills репозитория, по каталогу на skill; процедурой владеет
  сам skill, а не этот файл. Обычной процедурой Git/GitHub владеет
  `.agents/skills/anki-git-workflow/`, независимое ревью кода без изменения файлов —
  `.agents/skills/anki-code-review/`, явно запрошенный цикл ревью CodeRabbit —
  `.agents/skills/anki-coderabbit-review/`.
- `tools/anki-repo/` — пакет Rust `anki-repo` для анализа экспорта и строго
  ограниченной записи в него (`edit`, `create`, `retire`, `migrate-media`), а
  также статического отчёта `visual-report`; контракт описан в
  `tools/anki-repo/README.md`. Это участник корневого рабочего пространства, а не отдельное
  рабочее пространство: `cargo` запускается из корня репозитория.
- `tools/asset-store/` — пакет Rust общей библиотеки жизненного цикла ресурсов,
  которыми управляет программа, и
  бинарника `kanji-assets`; его единственный публичный контракт —
  `tools/asset-store/README.md`. Пакет входит в корневое рабочее пространство и наследует
  его `edition` и MSRV. Он не зависит от Anki/Yarxi и не читает `decks/**/media/`.
- `Cargo.toml` в корне — единственный владелец `[workspace.package]`: заявленной
  MSRV (`rust-version`) и `edition` для всех Rust-участников. `Cargo.lock` тоже
  лежит в корне.
- `.github/workflows/ci.yml` — независимый CI репозитория: форматирование,
  Clippy, тесты, заявленная MSRV и `validate` для каждого найденного в `decks/`
  экспорта. Читает репозиторий, не публикует артефакты и не использует секреты.
  Подробности — в `03-VERIFICATION.md`.
- `AGENTS.md` — короткий обязательный контракт для любого агента.

`decks/` — канонический корень пользовательских колод и одновременно данные, а не
контракт репозитория: набор инструментов работает с произвольным CrowdAnki-экспортом и не
знает имён полей конкретной модели, а ни CI, ни набор тестов по умолчанию не
перечисляют конкретные колоды, уровни, модели и поля. Текущий состав и имена
моделей ниже — состояние на сегодня, а не требование к репозиторию.

Независимость тестов по умолчанию от фактических данных репозитория — не то же самое, что независимость
CI от валидности данных. Фактически закоммиченный экспорт остаётся предметом
проверки репозитория: CI рекурсивно находит `deck.json` под `decks/**` и требует
валидности каждого найденного экспорта, поэтому структурная ошибка в закоммиченной
колоде делает CI красным, а отсутствие экспортов ошибкой не является. Подробности
— в `03-VERIFICATION.md`.

## Как находить место изменения

1. Определить целевой файл колоды в `decks/`.
2. Установить, меняется ли содержимое заметок, дерево колод, модель заметки, настройки колоды или только документация.
3. Для JSON сначала получить верхнеуровневые ключи и нужные UUID/имена, затем переходить к конкретному поддереву.
4. Не читать все `notes` подряд, если задача относится к одной модели, одному уровню, одному уроку или ограниченному набору слов.
5. После изменения выполнить проверки из `03-VERIFICATION.md`.

## Быстрый анализ без ручного чтения JSON

Для структурного анализа экспорта используй `tools/anki-repo`: `inspect`
показывает состав колоды, `find` ищет заметки по `guid` или по значению поля,
`stats` считает распределения, `validate` проверяет структурные инварианты.

Для проверки содержимого карточек используй `qa` (детерминированные замечания по
фиксированному реестру правил) и `review` (компактный пакет заметок по найденной
проблеме), а предложения внешнего агента проверяй через `review-check`: он ничего
не пишет и выдаёт готовый запрос для `edit`. Набор инструментов не вызывает LLM API: разбор
содержимого делает внешний агент.

Для правки значения поля существующей заметки используй `edit` того же набора инструментов,
а не ручной скрипт: он разрешает то же соответствие `note_model_uuid` →
`flds[].ord` → `fields`, по умолчанию работает в режиме без записи, требует `--expect` и
проверяет байтовый diff до записи. Новая заметка добавляется командой `create` (перед
ней смотри фактическую схему полей через `models`), а вывод заметки из обращения —
командой `retire` одним тегом: физического удаления заметок в наборе инструментов нет.
Единственное ограниченное исключение для существующей заметки — `migrate-media`,
которая меняет доказанные медиассылки после проверки пары «идентичность ресурса — имя» и всех
потребителей. Ручная правка `deck.json` и файлов `media/` в обход команды
запрещена. Создание колод и моделей набор инструментов не выполняет. Полный контракт
команд и вывода описан в `tools/anki-repo/README.md`.
