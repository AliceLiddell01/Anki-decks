# Создание карточек CrowdAnki

## Область

Этот skill владеет оркестрацией создания **новых** заметок в существующей
колоде и модели. `tools/anki-repo/README.md` владеет контрактом `models`,
`create`, `validate`, `visual-report`, правилами обработчиков и командой
`migrate-media`; `tools/asset-store/README.md` — контрактом `kanji-assets`,
`pitch-assets`, целостностью ресурсов, итоговым доверием и состоянием пакетов.
Общий жизненный цикл Git/GitHub выполняй через `anki-git-workflow`; здесь заданы
дополнительные ограничения публикации корпуса ресурсов. Не создавай обёртку,
вторую копию парсера манифеста или собственную логику получения и проверки
изображений.

При первом обращении к колоде прочитай `.codex/context/INDEX.md`, затем
профильных владельцев. Не загружай многомегабайтный `deck.json` целиком.

## Создание и частичный прогресс

1. Определи целевой экспорт и узел колоды по запросу и фактическим данным.
   Вызови `anki-repo models` с точным селектором; проверь UUID модели, имена и
   порядок `flds[].ord`, примеры значений и шаблоны. Не выводи содержательное
   значение поля только из его имени. Уточни недостающее, если оно неоднозначно.
2. Прочитай отслеживаемый в Git `.anki-repo/create.yaml`. Сопоставь фактический
   `note_models[].crowdanki_uuid` и точные имена полей с правилами. Выполняй
   `processors` в объявленном порядке. Назначенное обработчику поле —
   **потребитель медиассылок**; правила не объявляют его источником слова.
   Для каждой новой заметки сохрани вне Git явное соответствие её GUID,
   семантического входа (`surface`, известного `reading`) и фактических полей
   модели, потребляющих `kanji_assets`/`pitch_accent`. Семантический вход берётся
   из пользовательского запроса либо явно проверенного сопоставления исходного
   текстового поля этой модели; не угадывай его по имени поля и не считывай
   слово из ещё пустого поля результата. Если источник неоднозначен, уточни
   именно слово/чтение или сопоставление. Из `surface` выдели поддерживаемые
   символы кандзи, исключая kana; для pitch используй точную `surface` и
   отдельно известное `reading`. Дедуплицируй зависимости между заметками;
   противоречащие запросы одной `surface` передай владельцу для отказа, не
   отбрасывай чтение произвольно. Пустое поле результата не блокирует эту
   подготовку. Пример контракта —
   [references/semantic-input.md](references/semantic-input.md).
3. Подготовь зависимости через их владельцев: `kanji_assets` — по
   [references/kanji-batch.md](references/kanji-batch.md), `pitch_accent` — по
   [references/pitch-batch.md](references/pitch-batch.md). Используй только
   ресурсы, которые владелец подтверждает для текущих байтов по правилам
   доверия своего домена. По его каноническому результату заполни назначенное
   поле медиассылкой в создаваемом запросе; отсутствие правила не разрешает
   медиа. Не угадывай расширение или имя файла. Браузерное получение ресурсов
   разных доменов запускай последовательно: они делят каталог браузера.
4. Раздели заметки по состоянию **всех** зависимостей. Готовые запускай через
   `anki-repo --json create ... --request ...` в dry-run; изучи полный
   машиночитаемый план, блокеры и результаты каждой заметки. `--apply` выполняй
   только для разрешённых заметок после успешного dry-run. Остальные оставь
   ожидающими с причиной, без отсутствующих медиассылок. Доказанный
   `no_pitch_accent_on_source` разрешает зависимость без медиа: поле остаётся
   пустым. После каждого раунда продвигай вновь готовые заметки, не ожидая
   решения по независимым. Отказ по занятому имени файла разбирай по разделу
   [Прежнее имя файла-потребителя](#прежнее-имя-файла-потребителя).
5. Сохраняй итоговый запрос создания, GUID и состояние заметок вне `decks/**`
   и Git. При возобновлении сверяй их с фактическим экспортом и результатами
   `create`, затем создавай только новые разблокированные заметки. Память чата
   не заменяет сохранённое состояние. Повтор завершённого процесса должен
   сходиться к `already_applied`/no-op без дубликатов.
6. До первого `--apply` сохрани состояние «до» в отдельном каталоге вне
   `decks/**` (копия экспорта или `git worktree` закоммиченного состояния).
   После каждой записи проверь фактический JSON через `anki-repo validate`
   и сравни состояния через `visual-report` с явными `--before` и `--after`.
   Отчёт держи вне `decks/**` и Git. Осмотри карточки и медиа; статическое
   превью не заменяет Anki.

Показывай раздельные числа/списки созданных заметок, готовых только в dry-run,
заблокированных ресурсами и другими причинами; ресурсы разделяй на автоматически
подтверждённые, подтверждённые человеком, ожидающие проверки и назначенные к
повторному получению. Ошибка одного элемента не отменяет успешных соседей.
Для pitch отдельно называй `no_pitch_accent_on_source`, `ambiguous_vocabulary`,
`vocabulary_not_found` и технические отказы: у них разные действия.

## Прежнее имя файла-потребителя

Единственная разрешённая правка **существующей** заметки в этом процессе —
перевод ссылки на текущее каноническое имя домена командой
`anki-repo migrate-media`. Её контракт, флаги, доказательства и причины отказа
принадлежат `tools/anki-repo/README.md`.

Плоское пространство имён `media/` общий для доменов: изображение символа называется
`<char>.gif|png`, pitch — `<surface>.pitch.png`. Прежнее pitch-имя
`<surface>.png` может совпасть с именем резервного PNG кандзи. `create`
отказывает (`destination_media_conflict` или `media_filename_collision`),
сохраняя оба набора байтов. Это ожидаемый конфликт прежнего имени.

1. Докажи связь прежнего имени с конкретной идентичностью через владельца домена
   и семантику **каждого** живого потребителя. Для полей проверь фактические
   `note_model_uuid` и правила обработчиков; учитывай также ссылки в шаблонах
   и CSS. Неподтверждённый потребитель блокирует освобождение имени.
2. Выполни `migrate-media` в dry-run и покажи доказанные ссылки, каноническое
   имя, размещение и освобождаемый файл.
3. Затем выполни `--apply`. Канонические байты берутся из проверенного
   хранилища домена: совпадение SHA даёт `reuse`, расхождение — `copy`.
   Освободившееся имя может занять канонический резервный PNG кандзи.
4. Повтори миграцию: ожидается `changed: false`. Снова выполни
   `anki-repo validate` и продолжай создание, включая конфликтную заметку.
5. Отдельно перечисли затронутые существующие заметки и файлы: прежнее и новое
   имя, SHA состояния до и после и фактическое освобождение прежнего имени.

Не заканчивай набор на N−1 заметках из-за этого конфликта, не заменяй слово,
не правь `deck.json` и не переименовывай `media/` руками. Не маскируй конфликт
под `kanji_asset_missing` или `pitch_asset_missing`. При отказе
`legacy_media_reference_unproven` покажи свидетельства (`guid`, поле или
поверхность ссылки, причину и число вхождений) и уточни недостающее.

## Решения человека

`kanji_assets` принимает только структурированное действие для **текущего**
`AssetIdentity + SHA-256`: «漢 - подтверждён» одобряет конкретный кандидат,
«字 - артефакт битый» или «не тот иероглиф» отклоняет его и назначает повторное
получение этой идентичности. Семантическое решение человека имеет приоритет над
автоматическим, включая `REJECTED`, но не обходит формат, декодирование,
целостность и границы путей. Это не криптографическая подпись. Неоднозначный
ответ не меняет состояние; при смене хеша требуется новое решение.

`pitch_accent` принимает выбор `select` при `ambiguous_vocabulary`,
`reject`/`reacquire` и новое поколение получения. Человек не может заменить
автоматическое `VERIFIED` осмотром PNG. Точные команды и проверки текущего SHA
находятся в соответствующем справочнике домена.

## Исходная точка публикации корпусов

Перед первым `batch start` сохрани вне Git push remote, default branch и точный
SHA удалённой base. Для **каждого используемого домена отдельно** сохрани ID и
неизменяемый план пакета, исходный снимок владельца и результат его проверки.
Сверь каноническую область хранилища с этим SHA через `git diff` и
`git status --short --untracked-files=all`: до пакета там не должно быть отличий.
Читай снимки только через следующие API, не разбирай манифест самостоятельно:

| Домен | Каноническая область | Снимок владельца | Проверка корпуса |
|---|---|---|---|
| `kanji_assets` | `.asset-store/kanji` | `cargo run --locked --bin kanji-assets -- --output json list` | `kanji-corpus-gate` |
| `pitch_accent` | `.asset-store/pitch-accent` | `cargo run --locked --bin pitch-assets -- --output json corpus list` | `pitch-corpus-gate`; офлайн API также `pitch-assets --output json corpus check` |

Схемы ответов различаются; точные поля снимка, доверия и завершённости описаны
в справочнике каждого домена. Отсутствующее хранилище допускает пустой исходный
снимок только если каталог действительно отсутствует, а сохранённая base не
содержит канонического корпуса. При этом kanji `list` возвращает ненулевой код,
`outcome = blocked`, `error.code = store_missing`; pitch `corpus list` — код
`4`, `outcome = failed`, `error.code = store_missing`. Любая другая ошибка
закрывает публикацию. Проверка корпуса допускает отсутствие корпуса; это не
разрешает считать ошибку чтения пустым снимком.

Если удалённую base или чистое исходное состояние установить нельзя,
карточки и пакеты можно продолжать, но публикация остаётся
`LOCAL_READY_TO_PUBLISH` до восстановления доказуемой исходной точки.
При возобновлении не заменяй сохранённый SHA или снимок текущим состоянием.

## Публикация канонических ресурсов

1. Дождись завершённого разрешения всех запрошенных идентичностей **в этом домене**.
   Через его API повторно прочитай снимок корпуса и `batch status`; сравни с
   сохранённым снимком. Любая изменённая идентичность должна входить в исходный
   план этого пакета, а её итоговый SHA и доверие — совпадать с состоянием
   владельца пакета. Независимые исходные идентичности сохраняются. Доказанное
   отсутствие pitch разрешает элемент без добавления записи или файла.
   Постороннее изменение либо несовпадение закрывает публикацию со статусом
   `LOCAL_READY_TO_PUBLISH`; сохрани состояние, не удаляй изменения и не
   запускай получение заново. При нулевой разнице не создавай branch/commit.
2. Один домен — одна отдельная ветка: `kanji-assets/<batch-id>` или
   `pitch-assets/<batch-id>`. Сохрани точное имя и путь worktree для возобновления;
   при коллизии проверь принадлежность существующей ветки этому пакету, не
   перезаписывай чужую. Создай её поздно в отдельном worktree от сохранённого
   SHA удалённой base. Текущий checkout не переключай. Перенеси только
   канонические байты и записи доверия данного домена, сохраняя исходные
   идентичности. Сверь снимки через API того же владельца и байты исходного
   checkout и worktree.
3. Добавляй в индекс по явному списку разрешённых реально существующих файлов внутри доменного корня:
   кандзи — `.owner.json`, `manifest.json`, `assets/gif/*.gif`,
   `assets/png/*.png`; pitch — `.owner.json`, `manifest.json`,
   `assets/png/*.png`. Это непосредственные файлы, не вложенные каталоги.
   `.runtime`, `.tmp`, `.lock`, браузерные артефакты и отчёты проверки исключены.
   Проверь изменения в индексе и состояние рабочего каталога: только канонический корпус нужного домена,
   без колод, исходного кода, skill, приёмочных данных и чужих файлов.
4. Запусти **проверку корпуса этого домена** кодом текущего checkout с CWD worktree:

   ```bash
   # Выполняется в worktree; <checkout> — корень текущего checkout.
   cargo run --quiet --locked --manifest-path <checkout>/Cargo.toml \
     -p asset-store --bin <kanji-corpus-gate|pitch-corpus-gate>
   ```

   Бинарник worktree исходной base может не поддерживать новую схему манифеста.
   Отказ актуальной проверки корпуса оставляет `LOCAL_READY_TO_PUBLISH`: не понижай
   `schema_version` и не переписывай манифест под старый код. После успешной
   проверки создай локальный коммит ресурсов даже без GitHub auth.
5. Эта ветка дополнительная к текущей задаче. Общий жизненный цикл Git выполняй
   через `anki-git-workflow`. Для удалённой публикации второй ветки требуется
   отдельное явное основание в текущем запросе пользователя; без него сохрани
   локальный коммит и `LOCAL_READY_TO_PUBLISH`.
6. Перед push выполни fetch актуальной base и объедини её с неопубликованной
   веткой по правилам `anki-git-workflow`, сохраняя обе стороны. Не заменяй
   `manifest.json` целиком и не выбирай `ours`/`theirs` вслепую. Неразрешимый
   конфликт оставляет коммит и состояние локально, с запретом push.
   После успешного объединения повторно прочитай снимок **того же владельца**,
   запусти **проверку корпуса того же домена**, проверь сохранность независимых идентичностей
   актуальной base и точные SHA/доверие пакета. Diff относительно полученной base должен
   содержать только его канонический корпус и запрошенные идентичности.
7. Выполни проверку прав администратора ниже перед каждым push, затем явный refspec и проверку
   точного удалённого SHA через `anki-git-workflow`. При возобновлении перечитай
   сохранённые ID/план/снимок/ветку, повтори сверки владельца, корпуса и прав
   администратора; получение ресурсов не повторяй. Merge PR требует отдельной текущей
   команды пользователя. После разрешённого merge и fetch итоговой base
   повтори снимок и проверку корпуса соответствующего домена, сверь опубликованные SHA,
   доверие и сохранность независимых идентичностей. При расхождении сообщи его и
   сохрани состояние для разбора, не запускай новый пакет.

## Проверка прав администратора перед публикацией

Перед **каждым** remote push докажи для хоста, владельца и репозитория фактического
push remote активный сеанс GitHub CLI, его login и рассчитанное через API
`permission = admin`. Проверка связывает проверенную учётную запись с credential,
которым пойдёт сам push: remote должен быть HTTPS, а credential helper — того же
сеанса GitHub CLI (например `credential.https://<host>.helper` =
`!gh auth git-credential`, как после `gh auth setup-git`). SSH, иной или
неподтверждённый helper закрывает допуск. Наличие `GH_TOKEN`, `GITHUB_TOKEN`,
`GH_ENTERPRISE_TOKEN` или `GITHUB_ENTERPRISE_TOKEN` делает активную учётную
запись неоднозначной и тоже закрывает допуск.

Проверь код завершения `gh auth status --active --hostname "$host"`; получи login
и permission без показа данных аутентификации:

```bash
login="$(gh api --hostname "$host" user --jq '.login')"
permission="$(gh api --hostname "$host" \
  "repos/$owner/$repo/collaborators/$login/permission" --jq '.permission')"
```

Только точный `permission == admin` этой учётной записи и репозитория разрешает push.
`read`, `write`, `maintain`, `none`, неизвестный ответ, ошибка API/auth, неверный
remote или отсутствие основания на вторую ветку оставляют
`LOCAL_READY_TO_PUBLISH`. Не используй `gh auth token`, не показывай данные аутентификации
и не выводи право из имени пользователя, владельца репозитория или возможности push. Контракт команд —
[официальный `gh auth status`](https://cli.github.com/manual/gh_auth_status),
[`gh api`](https://cli.github.com/manual/gh_api) и
[Права пользователя через GitHub API](https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user).

Перед исполнением сверь актуальные `--help` и README владельца: изменение
синтаксиса API не разрешает менять смысловые инварианты этого процесса.
