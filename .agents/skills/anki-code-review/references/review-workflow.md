# Порядок независимого ревью кода

## 1. Зафиксировать объект ревью

Сначала определи репозиторий, base и проверяемую ревизию:

- если пользователь дал PR URL/номер — это объект ревью;
- если названа ветка или диапазон коммитов — используй их;
- иначе работай с текущей рабочей копией и её PR, если он есть.

Зафиксируй точные SHA проверяемых HEAD/base. Если невозможно разрешить
ревизию, явно отметь ограничение вместо обозначения плавающей ссылки как
точного снимка.
Не переключай рабочую копию только ради ревью и не смешивай изменения другого PR.

До собственного анализа не читай замечания CodeRabbit, комментарии ботов ревью,
замечания ревью от людей или готовые таблицы рассмотрения замечаний.

## 2. Восстановить исходные требования

### 2.1. Windows Downloads

Пользователь обычно сохраняет исходную постановку в Windows Downloads и не
удаляет её до закрытия PR. Сначала разреши фактическую системную папку Downloads
через Windows Known Folders API. Не хардкодь имя Windows-пользователя, диск или
абсолютный путь и не считай расположение по умолчанию текущей системной папкой.

Алгоритм разрешения пути:

1. В Windows используй Windows PowerShell; из WSL вызови его через взаимодействие
   с Windows (`powershell.exe` или доступный Windows `pwsh.exe`). Получи путь
   текущего пользователя через документированный `SHGetKnownFolderPath` с
   `FOLDERID_Downloads` (`{374DE290-123F-4565-9164-39C4925E467B}`). Для PowerShell
   допустима небольшая .NET/P/Invoke обёртка над этим API. Используй `dwFlags = 0`,
   инициализируй COM перед вызовом и освободи выходной указатель через
   `CoTaskMemFree` даже при неуспешном `HRESULT`; передавай `hToken = NULL`, чтобы
   получить системную папку текущего пользователя. API возвращает фактическое
   расположение с учётом перенаправления, а не предположение по `%USERPROFILE%`.
2. Если механизм получения системной папки недоступен или не удалось получить
   валидный путь, допустим явно обозначенный запасной вариант
   `%USERPROFILE%\Downloads`. Сначала получи `$env:USERPROFILE` из Windows, затем
   проверь этот каталог через Windows `Test-Path -LiteralPath ... -PathType
   Container`. Отметь в отчёте, что использован запасной вариант, а перенаправление
   системной папки подтвердить не удалось. Если надёжно получить `USERPROFILE`
   или проверить каталог невозможно, не угадывай путь и зафиксируй ограничение.
3. Проверь, что разрешённый Windows-путь абсолютный и существует как каталог.
   Если API успешно вернул валидный путь, но каталог по нему отсутствует, укажи
   ограничение; не подменяй его старым расположением по умолчанию. При работе
   непосредственно в Windows используй разрешённый Windows-путь. Только из WSL
   передай его из PowerShell без потери пробелов и Unicode (например, UTF-8 Base64
   с последующим декодированием в WSL), затем вызови `wslpath -u` с путём как одним
   аргументом в кавычках. Проверь успешное завершение `wslpath` и существование
   полученного WSL-каталога. Ошибка преобразования или доступа — ограничение,
   а не повод искать в старом расположении по умолчанию.
4. Ищи возможные исходные постановки только внутри разрешённого каталога.
   Если одновременно существуют перенаправленная папка и старый
   `%USERPROFILE%\Downloads`, используй путь, возвращённый API: существование
   старого каталога не является основанием выбрать его.

Если среда не позволяет надёжно получить путь через Windows API или проверить
запасной вариант, не угадывай расположение Downloads. Если разрешённый каталог
невозможно прочитать,
зафиксируй ограничение поиска исходной постановки и продолжи по доступным
источникам.

Контракт API: [Known Folders](https://learn.microsoft.com/en-us/windows/win32/shell/known-folders),
[`SHGetKnownFolderPath`](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shgetknownfolderpath)
и [`FOLDERID_Downloads`](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid).

### 2.2. Выбор исходной постановки

Не выбирай «самый новый .txt» автоматически. Кандидат определяется сочетанием:

- времени относительно начала ветки/первых коммитов/создания PR — слабый сигнал;
- характерных терминов из заголовка PR, связанного обсуждения и diff;
- имён команд, модулей, функций или разрабатываемой функциональности;
- совпадения формулировок требований.

Основные кандидаты — текстовые файлы, прежде всего .txt и .md. Имена вроде
«Вставленный текст(...)» сами по себе ничего не доказывают.

Если найдено несколько похожих постановок, прочитай кандидатов и выбери тот,
который содержательно объясняет именно рассматриваемую разработку. Более новая
редакция не считается авторитетнее автоматически: ищи признаки явного
уточнения/переписывания задачи.

В отчёте достаточно указывать источник как Windows Downloads/<filename>, без
абсолютного пользовательского пути.

Если постановка не найдена или её происхождение неоднозначно, не угадывай
требования. Продолжи ревью по связанному обсуждению, контрактам репозитория и
доступному запросу и отметь ограничение.

### 2.3. Остальные источники

Прочитай:

- текущий запрос пользователя;
- связанное обсуждение/задачу и относящиеся к требованиям уточнения;
- AGENTS.md;
- только применимых владельцев из .codex/context/ и профильных README и skills;
- описание PR как список заявлений реализации и заявленных проверок.

Если нормативные источники противоречат друг другу и нельзя доказать более
позднее явное уточнение, не скрывай конфликт.

## 3. Построить карту изменений

Собери `code-review collect` для выбранных base/HEAD по публичному контракту
[anki-repo](../../../../tools/anki-repo/README.md#code-review-collectverifydeltatriage).
Сохрани пакет ревью как локальный артефакт вне `decks/**`. Если путь находится
в репозитории, он виден Git; не добавляй его в индекс автоматически. По просьбе
пользователя его можно включить в PR вместе с точным `head_sha`.
Проверь, что разрешённые SHA относятся к выбранному объекту ревью. Полный
пакет содержит идентичность снимка, область изменений, диагностики и кандидатов;
полные версии релевантных файлов после изменений при необходимости восстанавливаются
из зафиксированных Git-объектов этого снимка. Краткое представление помогает
навигации. Требования и архитектурный контекст восстанавливаются отдельно.

Если сборщик недоступен или завершился ошибкой, зафиксируй причину и собери
доступные свидетельства вручную. Не останавливай независимое ревью, которое можно
корректно продолжить. Статусы анализаторов учитывай отдельно от отсутствия
сигналов; не устанавливай и не скачивай инструменты ради обычного сборщика.

Если работа распределена между субагентами, передай им один сохранённый
неизменяемый пакет и одинаковые SHA. Не собирай плавающие снимки для каждого
направления отдельно.

Для этого source pack сразу инициализируй отдельный semantic-triage artifact:

```bash
anki-repo code-review triage init --pack "$PACK" --out "$TRIAGE"
```

`init` привязывает его к точному `review.json` и Git snapshot. Дальше заполняй
только triage JSON; evidence остаётся неизменным. Подробные поля, reason codes,
проверки связей и identity заданы в публичном контракте
[anki-repo](../../../../tools/anki-repo/README.md#code-review-collectverifydeltatriage).

Получи полный diff и список изменённых файлов. Для каждого существенного
изменения определи:

- путь рабочего кода;
- тесты;
- контракты/конфигурацию/документацию, которые оно затрагивает;
- вызывающий и вызываемый окружающий код;
- существующие абстракции, которые могли быть обойдены или продублированы.

Не читай весь репозиторий без причины, но и не ограничивайся фрагментами diff.
Изменённый публичный контракт или контракт CLI/JSON/файловой системы требует
проверки потребителей и соседних путей выполнения. Изменение общей
вспомогательной функции требует проверки основных мест вызова.

Для удалений найди оставшиеся ссылки; для новых абстракций найди старые пути,
которые они должны были заменить.

## 4. Проверить реализацию независимо

Пройди критерии из review-criteria.md. Минимум:

- корректность и граничные случаи;
- архитектура/владение/контракты;
- обработка ошибок и жизненный цикл;
- тесты;
- специальные обязательные проверки пользователя: хардкод, чрезмерная привязка
  к текущей разработке, требования/область задачи, устаревший/неиспользуемый код,
  остаточный английский.

Для проверки остаточного английского предпочитай языковые кандидаты с учётом
формата из пакета или `language scan` по полным релевантным файлам проверяемого
HEAD.
Проверь содержательную классификацию, origin и исключения по review-criteria.md.
При отказе сканера продолжи ручную проверку полного содержимого затронутых
файлов и отметь ограничение. Один кандидат не является замечанием; автоматическое
применение замен не входит в эту независимую фазу.

При semantic анализе отражай судьбу каждого source candidate ровно одним из
трёх способов: индивидуальное решение, group decision с точными
`candidate_ids` и `representative_candidate_ids`, либо явное сохранение в
`unreviewed_candidate_ids`. Групповое решение фиксирует покрытие группы, но не
превращает её элементы в individually reviewed candidates. Записывай в triage
только устойчивые `reason_code`; пояснение решения сохраняй отдельно. Findings
связывай с source candidate только при доказанной связи и согласованно с обеих
сторон; для finding, найденного независимо, используй provenance `independent`
и не подбирай ближайший candidate.

## 5. Проверить тесты как код

Не принимай наличие теста за доказательство.

Для существенной проверки в тесте спроси:

- упал бы тест при реалистичной неправильной реализации;
- проверяет ли он контракт/свойство, а не копию внутренних шагов;
- не задаёт ли имитация зависимости ровно тот ответ, который рабочий код ожидает;
- покрыт ли путь обработки ошибок, ради которого существует изменение;
- не привязан ли тест к фактическим данным репозитория, имени колоды, одному
  файлу или конкретной реализации функциональности без причины из предметной
  области;
- не внесена ли абстракция рабочего кода только ради удобства теста.

Для изменений параллелизма/жизненного цикла отдельно проверь отмену, частичный
прогресс, очистку, повторные попытки/возобновление и ошибки на границах владения,
если применимо.

## 6. Верификация

Используй применимый набор проверок репозитория и состояние CI как доказательства,
но не подменяй ими ревью.

Запускай/проверяй только релевантные команды, если среда это позволяет.
Не утверждай, что проверка пройдена, если видел только описание PR или чужое
сообщение об успехе.

Зелёный CI означает, что известные обязательные проверки прошли; он не доказывает
отсутствие логических дефектов и слабых тестов.

## 7. Обобщение замечаний

Сначала собери потенциальные замечания, затем для каждого:

1. перепроверь файл в точном проверяемом HEAD и его совпадение со снимком пакета;
   при изменении HEAD обнови свидетельства и повторно проверь затронутые выводы;
2. найди минимальный доказуемый сценарий отказа;
3. проверь, не является ли это дубликатом общей первопричины;
4. назначь уровень серьёзности по finding-policy.md;
5. отдели подтверждённый дефект от вопроса/неопределённости.

Если использовались субагенты, главный ревьюер обязан выполнить этот этап сам.
После разрешённых отдельно исправлений `verify`/`delta` помогают сравнить
исходный пакет и новый снимок. Исчезновение сигнала детектора не закрывает замечание
без проверки поведения, контракта и применимых регрессий.

После завершения семантической проверки проверь artifact против того же source
pack, запиши отсортированный canonical JSON, получи по нему статистику и создай
производный Markdown report в этом порядке:

```bash
anki-repo code-review triage validate --pack "$PACK" --triage "$TRIAGE" --canonical-out "$CANONICAL_TRIAGE"
anki-repo code-review triage summary --pack "$PACK" --triage "$CANONICAL_TRIAGE"
anki-repo code-review triage report --pack "$PACK" --triage "$CANONICAL_TRIAGE" --out "$REPORT.md"
```

Единственный источник статуса individual/group/unreviewed review — результат
валидации и данные этого canonical triage. Не считай запись в group decision индивидуальным
разбором каждого покрытого candidate и не считай `unreviewed_candidate_ids`
рассмотренными. Учитывай раздельно количество individual decision units,
group decision units и candidates, покрытых группами; групповой coverage не
является числом индивидуальных решений или оценкой precision детектора.

Если меняется проверяемый HEAD/base или содержимое source pack, не переноси
решения на новый источник автоматически: собери новый evidence pack и повтори
семантический разбор с новым triage. Старый triage относится только к snapshot,
указанному внутри него.

## 8. Финальный отчёт

Структура:

1. итог: REQUEST_CHANGES / COMMENT / CLEAN и точный проверяемый HEAD;
2. замечания — по убыванию серьёзности;
3. соответствие исходным требованиям и важные расхождения области задачи;
4. ограничения ревью/установления исходных требований, только если они есть;
5. коротко — что фактически проверялось.

Сверь findings и статус покрытия с валидированным triage и его report. В ответе
показывай только доказанные findings, соответствие требованиям и фактические
ограничения; не выводи полный candidate dump, длинные перечни отвергнутых
сигналов или групповые решения как individual review.

Не создавай замечания ради ненулевого списка. CLEAN допустим и предпочтительнее
сомнительных замечаний.
