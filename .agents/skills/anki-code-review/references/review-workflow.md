# Workflow независимого code review

## 1. Зафиксировать target

Сначала определи repository, base и candidate:

- если пользователь дал PR URL/номер — это target;
- если названа ветка или диапазон commits — используй их;
- иначе работай с текущим checkout и его PR, если он есть.

Зафиксируй reviewed HEAD/base настолько точно, насколько позволяет среда.
Не переключай checkout только ради review и не смешивай изменения другого PR.

До собственного анализа не читай CodeRabbit findings, review bot comments,
человеческие review findings или готовые disposition tables.

## 2. Восстановить исходные требования

### 2.1. Windows Downloads

Пользователь обычно сохраняет исходный prompt в Windows Downloads и не удаляет
его до закрытия PR. Если review выполняется из WSL, разреши реальный Windows
Downloads через Windows, а затем преобразуй путь в WSL. Не хардкодь имя
Windows-пользователя, диск C: или путь вида /mnt/c/Users/<name>/Downloads.

Предпочтительный принцип:

1. получить Windows user profile/known Downloads folder через доступный Windows
   PowerShell или shell interface;
2. проверить существование полученного Downloads;
3. преобразовать Windows path через wslpath, если чтение идёт из WSL;
4. только после этого искать candidate prompts.

Если стандартный UserProfile\Downloads отсутствует, проверь Windows known-folder
настройку/перенаправление вместо подстановки чужого абсолютного пути.

### 2.2. Выбор prompt

Не выбирай «самый новый .txt» автоматически. Candidate определяется сочетанием:

- времени относительно начала ветки/первых commits/создания PR — слабый сигнал;
- характерных терминов из PR title, issue и diff;
- имён команд, модулей, функций или feature;
- совпадения формулировок требований.

Основные candidates — текстовые файлы, прежде всего .txt и .md. Имена вроде
«Вставленный текст(...)» сами по себе ничего не доказывают.

Если найдено несколько похожих prompts, прочитай кандидатов и выбери тот,
который содержательно объясняет именно рассматриваемую разработку. Более новая
редакция не считается авторитетнее автоматически: ищи признаки явного
уточнения/переписывания задачи.

В отчёте достаточно указывать источник как Windows Downloads/<filename>, без
абсолютного пользовательского пути.

Если prompt не найден или provenance неоднозначен, не угадывай требования.
Продолжи review по issue/repository contracts/доступному запросу и отметь
ограничение.

### 2.3. Остальные источники

Прочитай:

- текущий запрос пользователя;
- связанный issue/task и относящиеся к требованиям уточнения;
- AGENTS.md;
- только применимые владельцы из .codex/context/ и профильных README/skills;
- PR body как список заявлений реализации и заявленных проверок.

Если нормативные источники противоречат друг другу и нельзя доказать более
позднее явное уточнение, не скрывай конфликт.

## 3. Построить карту изменений

Получить полный diff и список changed files. Для каждого существенного изменения
определи:

- production path;
- tests;
- contracts/config/docs, которые оно затрагивает;
- вызывающий и вызываемый surrounding code;
- существующие abstractions, которые могли быть обойдены или продублированы.

Не читай весь repository без причины, но и не ограничивайся patch hunks.
Изменённый public/CLI/JSON/filesystem contract требует проверки потребителей и
соседних paths. Изменение общего helper требует проверки основных call sites.

Для удалений найди оставшиеся references; для новых abstractions найди старые
пути, которые они должны были заменить.

## 4. Проверить реализацию независимо

Пройди criteria из review-criteria.md. Минимум:

- correctness и edge cases;
- architecture/ownership/contracts;
- error handling и lifecycle;
- tests;
- специальные обязательные проверки пользователя: hardcode, overfitting,
  requirements/scope, legacy/dead code, остаточный английский.

Проверка остаточного английского выполняется по полному содержимому каждого
файла, затронутого PR, а не только по добавленным строкам. Отмечай, внесено ли
это текущим PR или существовало до него.

## 5. Проверить tests как код

Не принимай наличие теста за доказательство.

Для существенного assertion спроси:

- упал бы тест при реалистичной неправильной реализации;
- проверяет ли он contract/property, а не копию внутренних шагов;
- не задаёт ли mock ровно тот ответ, который production code сам ожидает;
- покрыт ли failure path, ради которого существует изменение;
- не привязан ли test к текущему live payload, имени колоды, одному файлу или
  конкретному feature instance без domain-причины;
- не внесена ли production abstraction только ради удобства теста.

Для concurrency/lifecycle изменений отдельно проверь cancellation, partial
progress, cleanup, retry/resume и ошибки на границах ownership, если применимо.

## 6. Верификация

Используй применимую verification matrix репозитория и CI state как evidence,
но не подменяй ими review.

Запускай/проверяй только релевантные команды, если среда это позволяет.
Не утверждай, что проверка пройдена, если видел только PR body или чужое
сообщение об успехе.

Зелёный CI означает, что известные gates прошли; он не доказывает отсутствие
логических дефектов и слабых тестов.

## 7. Синтез findings

Сначала собери candidate findings, затем для каждого:

1. перепроверь актуальный файл/HEAD;
2. найди минимальный доказуемый failure mode;
3. проверь, не является ли это дубликатом общей root cause;
4. назначь severity по finding-policy.md;
5. отдели подтверждённый defect от вопроса/неопределённости.

Если использовались субагенты, главный reviewer обязан выполнить этот этап сам.

## 8. Финальный отчёт

Структура:

1. итог: REQUEST_CHANGES / COMMENT / CLEAN;
2. Findings — по убыванию severity;
3. соответствие исходным требованиям и важные расхождения scope;
4. ограничения review/provenance, только если они есть;
5. коротко — что фактически проверялось.

Не создавай findings ради ненулевого списка. CLEAN допустим и предпочтительнее
сомнительных замечаний.
