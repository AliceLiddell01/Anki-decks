# Anki-decks: независимое ревью кода

## Назначение

Skill владеет содержательным независимым ревью кода и тестов в этом
репозитории. Он восстанавливает требования, определяет фактическую область
изменений, читает необходимый окружающий код и формирует только те замечания,
для которых можно показать конкретный дефект, нарушенный контракт, регрессию
или другой наблюдаемый риск.

Ревью охватывает окружающий код: diff определяет область изменений, но
корректность оценивается в контексте существующих абстракций, контрактов, тестов
и инвариантов репозитория.

Skill не владеет:

- исправлением найденных проблем;
- жизненным циклом ветки/commit/push/PR — им владеет anki-git-workflow;
- запуском CodeRabbit, его замечаниями и правилами итераций — ими владеет
  anki-coderabbit-review;
- набором проверок репозитория — используй существующих владельцев из
  AGENTS.md и .codex/context/;
- содержательной проверкой отдельных Anki-карточек вместо профильного набора
  инструментов и рабочего процесса.

Если текущий запрос одновременно просит ревью и последующее исправление,
сначала закончи независимую фазу ревью и зафиксируй замечания; только затем
переходи к реализации подтверждённых исправлений и обычной процедуре Git/GitHub.

## Контракт маршрутизации

Маршрутизируй сюда, в частности:

- «сделай код-ревью»;
- «проведи код-ревью»;
- «сделай ревью PR #...»;
- «проверь этот PR» в контексте проверки реализации;
- «сделай код-ревью PR без CodeRabbit»;
- «проверь самостоятельно, не запускай CodeRabbit»;
- «сделай независимое ревью, потом сравни с результатом CodeRabbit»;
- просьбу продолжить уже начатое обычное ревью кода.

Выбирай маршрут по намерению пользователя, учитывая отрицание и порядок
порученных действий. Только явный положительный запрос запустить или продолжить
ревью CodeRabbit ведёт в anki-coderabbit-review. Упоминание CodeRabbit само по
себе, включая отказ от его запуска, этого разрешения не даёт. Если запрошены
независимое ревью и последующая внешняя фаза, начни с этого skill и соблюдай
порядок из раздела «Независимость от внешних ревьюеров».

Изменение самого этого skill не является просьбой запустить ревью.

## Контракт работы без изменения файлов

Обычный запуск skill только исследует и сообщает результат. Он не:

- меняет отслеживаемые Git файлы;
- исправляет замечания;
- создаёт коммиты, в том числе пустые коммиты для фиксации выполненного ревью;
- выполняет push ветки;
- меняет описание PR, метки, список ревьюеров или состояние ревью;
- публикует комментарии к строкам кода;
- выполняет merge;
- запускает CodeRabbit.

Разрешены чтение состояния Git/GitHub, исходников, истории и подтверждённых
сведений о задаче, а также неразрушающие проверки. Если проверка создаёт обычные
артефакты сборки/тестов, они не считаются изменением продукта. Локальные
пакеты ревью, semantic-triage JSON и производные отчёты сохраняются вне
`decks/**`; внутри репозитория они видны Git, но не добавляются в индекс
автоматически. Включай артефакт в PR только по просьбе пользователя, сверяя
записанный `head_sha`; пакет описывает указанный SHA, а не commit, который позже
добавит сам пакет. Применение языковых замен не входит в независимую фазу ревью.

## Контракт выбора объекта ревью

Приоритет объекта ревью:

1. явно указанный пользователем PR/ветка/диапазон коммитов;
2. иначе текущая рабочая копия и связанный с ней PR, если он существует.

Не переключай ветки молча и не подменяй объект ревью более удобным. Для
удалённого PR предпочитай структурированное чтение GitHub/gh вместо
переключения на чужую ветку.

## Независимость от внешних ревьюеров

До завершения собственного содержательного анализа не используй замечания
CodeRabbit, другого LLM-ревьюера или человека как список подсказок. Разрешено
читать уточнения задачи/требований из обсуждения, но комментарии ревью,
замечания ботов и таблицы их рассмотрения откладываются.

Если пользователь отдельно просит сравнить независимое ревью с CodeRabbit или
другим ревью, сначала зафиксируй собственный набор замечаний, затем выполняй
сравнение с доступным внешним результатом. Просьба сравнить с результатом сама
по себе не разрешает новый запуск CodeRabbit. Если пользователь явно заказал
также его запуск, переходи к anki-coderabbit-review только после завершения и
фиксации независимого анализа. Фиксация здесь означает сохранённый отчёт или
ответ пользователю, а не изменение кода или commit. Не выдавай чужое замечание
за собственную находку; если внешний результат недоступен, укажи ограничение
сравнения.

## Источники требований

Исходная постановка задачи обычно сохраняется пользователем в Windows Downloads
до закрытия PR. При ревью попытка найти этот текст обязательна, если среда
имеет доступ к файловой системе Windows.

Нормативный контекст собирается из:

- текущего запроса пользователя и явных последующих уточнений;
- исходного текста постановки задачи из Windows Downloads;
- связанного обсуждения/задачи и доказанных уточнений требований;
- применимых контрактов и инвариантов репозитория.

Описание PR — это прежде всего заявление реализации: что автор утверждает, что
сделано и проверено. Оно не заменяет исходную постановку и не становится
источником требования только потому, что описывает уже реализованное решение.

Существенные противоречия между нормативными источниками не разрешай догадкой:
покажи их как ограничение ревью. Если исходная постановка не найдена однозначно,
продолжай по доступным источникам и явно отметь этот пробел.

## Детерминированные свидетельства

Используй `code-review` и `language` существующего `anki-repo` как
вспомогательный источник фактов. Публичным CLI/JSON-контрактом, параметрами,
артефактами и ограничениями владеет
[tools/anki-repo/README.md](../../../tools/anki-repo/README.md).
Не воспроизводи его реализацию одноразовыми скриптами.

Свидетельства, кандидаты и диагностики не являются подтверждённым замечанием.
Каждый потенциальный дефект проверь по требованиям, окружающему коду и
контрактам. Ошибка сборщика или недоступность локального анализатора не
прекращают ревью автоматически: продолжи доступный ручной анализ и обозначь
ограничение. Недоступный Clippy не означает зелёную проверку. Обычный сбор
выполняется без исполнения кода проекта; `--run-clippy` разрешён только при явном доверии к проверяемому
коду. Cargo может исполнить `build.rs` и процедурные макросы, а режим без сети
не ограничивает доступ этого кода к файлам и окружению пользователя.

Итоговое ревью относится к точному проверяемому HEAD. Он должен совпадать со SHA
снимка свидетельств; при изменении объекта собери новый пакет и перепроверь
затронутые выводы либо явно ограничь отчёт прежним снимком. `verify`/`delta`
показывают изменения сигналов детекторов; исправление замечания подтверждается
содержательным повторным ревью.

## Машиночитаемый semantic triage

После сбора evidence веди семантическое рассмотрение в отдельном versioned
triage-артефакте по публичному контракту
[anki-repo](../../../tools/anki-repo/README.md#code-review-collectverifydeltatriage).
Соблюдай четыре независимых слоя:

1. `review.json` — неизменяемые свидетельства и candidates конкретного Git
   snapshot;
2. triage JSON — семантические решения и findings reviewer'а;
3. `report.md` — производный человекочитаемый отчёт из валидированного triage;
4. финальный ответ пользователю — краткое ревью по доказанным findings,
   соответствию требованиям и реальным ограничениям.

Рабочий цикл:

```bash
anki-repo code-review triage init --pack "$PACK" --out "$TRIAGE"
# Содержательно рассмотреть candidates и отредактировать только TRIAGE.
anki-repo code-review triage validate --pack "$PACK" --triage "$TRIAGE" --canonical-out "$CANONICAL_TRIAGE"
anki-repo code-review triage summary --pack "$PACK" --triage "$CANONICAL_TRIAGE"
anki-repo code-review triage report --pack "$PACK" --triage "$CANONICAL_TRIAGE" --out "$REPORT.md"
```

`init` связывает артефакт с точными байтами source `review.json` и его
переносимым `GitTarget`; он не копирует полный evidence для каждого решения.
При semantic review записывай individual decisions, либо group decision с
точным `candidate_ids` и `representative_candidate_ids`, либо оставляй candidate
в `unreviewed_candidate_ids`. Не отмечай всю группу как индивидуально
проверенную: group-covered candidates и число решений по группам должны
оставаться отличимыми в triage и summary. Связывай candidate с finding только
по существующему ID и согласованно с обеих сторон; findings с provenance
`independent` не приписывай detector'у.

Используй прошедший `validate` canonical triage как единственный источник статуса
индивидуального, группового и неполного review. Не выводи этот статус из prose,
ручных счётчиков, raw candidate dump или одного `review.json`. Summary и
generated report показывают покрытие, findings и ограничения, не превращая
группы в фиктивные индивидуальные проверки и не имитируя detector precision.
Не включай тысячи кандидатов или список отвергнутых сигналов в финальный ответ:
показывай только доказанные замечания/findings и фактические ограничения
ревью.

Triage отделён от `LanguageDecisions`: классификация language candidate для
code review не утверждает замену, не запускает `language apply` и не меняет его
контракт. `anki-repo` не вызывает LLM/API, не редактирует `review.json` и не
исправляет findings; семантическое суждение и редактирование отдельного triage
выполняет reviewer.

Если меняется HEAD/base или исходный pack, не переноси triage молча. Собери
новый evidence snapshot и проверь решения заново в triage, привязанном к новому
источнику. Старый artifact сохраняет смысл только для своего исходного snapshot.

## Критерий доказанности

Замечание существует только если можно объяснить:

- где находится проблема;
- какое поведение, требование или инвариант нарушается;
- при каких условиях это проявляется;
- какой наблюдаемый эффект или риск сопровождения получается.

Предположение «здесь потенциально можно улучшить» без конкретного сценария
отказа не является замечанием.

## Параллельный анализ

Для достаточно крупного PR используй доступных субагентов без права записи по
независимым направлениям, если это сокращает время или повышает покрытие.
Не хардкодь число субагентов и не создавай параллельную запись.
Передай всем ревьюерам один и тот же неизменяемый снимок свидетельств, точные
base/HEAD и источники требований. Они открывают код именно проверяемой ревизии;
текущий изменившийся файл не подменяет содержимое файлов проверяемого снимка.

Главный ревьюер обязан сам объединить результат: убрать дубли, перепроверить
доказательства по актуальному объекту ревью, нормализовать уровень серьёзности
и найти межфайловые проблемы, которые отдельный субагент мог не увидеть.

## Справочные документы

Перед содержательным ревью прочитай все три справочных документа:

- references/review-workflow.md — порядок сбора требований, поиска исходной
  постановки, анализа PR и окружающего кода, проверок и обобщения результатов;
- references/review-criteria.md — обязательные инженерные и специальные критерии;
- references/finding-policy.md — порог доказательности, уровень серьёзности и
  формат финального отчёта.

SKILL.md задаёт владельцев и инварианты; справочные документы не должны создавать
альтернативную процедуру Git или CodeRabbit.
