# Независимое ревью кода Anki-decks

## Назначение

Проведи собственное инженерное ревью на основе Git/GitHub, исходной задачи,
реального кода, окружающих вызовов, контрактов и тестов. Diff задаёт исходную
область исследования, но не заменяет изучение взаимодействий и последствий.
Не требуй специального CLI для ревью, пакетов свидетельств, базы данных,
накопления истории, очередей кандидатов или автоматических оценок.

## Вспомогательные инструменты и временные файлы

Для самостоятельного анализа **можно создавать и запускать** любые необходимые
одноразовые вспомогательные инструменты: Python-, shell-, PowerShell-скрипты,
парсеры, анализаторы, проверочные программы, fixtures и отчёты. Не требуй
отдельного разрешения для безопасных диагностических действий в рамках ревью
и не отказывайся от полезной проверки лишь потому, что готового инструмента нет.

**Все файлы, которые агент создаёт для такого анализа** (исходники скриптов,
временные данные, копии входов, результаты, логи), размещай исключительно в
отдельном рабочем каталоге внутри **системного temp за пределами репозитория
и его worktrees**. На Linux/WSL это обычно `/tmp` или допустимый
`$TMPDIR`, на Windows — `%TEMP%`; для Python подходит
`tempfile.TemporaryDirectory(prefix="anki-code-review-")`.
Проверяй фактический путь: даже если `TMPDIR`/`TEMP` указывает внутрь
репозитория либо библиотека предлагает использовать текущий каталог,
не создавай там файлы; выбери другой безопасный системный temp.

Вспомогательные скрипты могут **читать** проверяемый код, запускать
диагностические команды и штатные проверки, но не должны менять исходные
файлы проекта или его Git/GitHub-состояние. Существующие средства сборки
и тестирования используют свои штатные каталоги результатов; не выдавай их
за новые скрипты ревью и не меняй их конфигурацию без необходимости.
Не записывай вспомогательные материалы в `.codex/local/`, `tools/`
или другие каталоги репозитория, не включай их в commit или PR.
После ревью удаляй только собственные временные материалы; если безопасный
temp недоступен, продолжай без записи или прямо сообщи ограничение.

## Порядок

1. Установи объект ревью: репозиторий, PR/ветку/diff, точные base/head и набор
   изменений. Для незакоммиченных изменений учитывай рабочее дерево. Не угадывай
   PR по имени ветки; сверяй его через GitHub.
2. Найди исходную постановку задачи и применимые договорённости проекта:
   `AGENTS.md`, `.codex/context/`, контракты и документацию. Текст PR —
   заявление автора, не замена исходным требованиям. Если постановка недоступна,
   назови это ограничением, а не придумывай её.
3. Прочитай diff и необходимый окружающий код, потребителей, тесты и конфигурацию.
   Проверь поведение по всем применимым критериям из
   [review-criteria.md](references/review-criteria.md).
4. Запускай доступные штатные проверки, когда они релевантны изменению. Не
   подменяй тестирование формальными заглушками. Отделяй подтверждённые сбои от
   невозможности проверки и существовавших ранее проблем.
5. Подготовь замечания по [finding-policy.md](references/finding-policy.md).
   Для каждого нужны точное место, сценарий, нарушенное ожидание, последствия,
   серьёзность и направление исправления. Не дублируй одну первопричину.
6. Итог: сначала доказанные findings по серьёзности, затем покрытие требований,
   выполненные проверки и ограничения. Если находок нет — сообщи CLEAN только
   при достаточном покрытии; обозначь INCOMPLETE по порогу
   [finding-policy.md](references/finding-policy.md), когда критичная часть
   постановки, diff, окружающего кода или обязательной проверки недоступна, и не
   выдавай отсутствие находок за завершённое ревью.

Пояснения к этапам: [review-workflow.md](references/review-workflow.md).

## Границы

Независимое ревью **не запускает CodeRabbit** и не инициирует комментарии,
изменения или публикацию PR само по себе. Само упоминание CodeRabbit не является
поручением его запустить. Сначала закончи собственное ревью; сравнивай с внешним
ревью только по отдельному запросу. Если отдельно поручены исправления,
коммиты, push или PR — используй штатный `anki-git-workflow` без новых запретов
публикации. Команды `anki-repo review` и `review-check` относятся к содержимому
Anki-карточек, а не к независимому ревью исходного кода.
