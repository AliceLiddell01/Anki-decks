# Anki-decks: независимое code review

## Назначение

Skill владеет содержательным независимым review кода и тестов в этом
репозитории. Он восстанавливает требования, определяет фактический scope
изменений, читает необходимый окружающий код и формирует только те findings,
для которых можно показать конкретный дефект, нарушенный contract, regression
или другой наблюдаемый риск.

Это не diff-only review: diff определяет область изменений, но корректность
оценивается в контексте существующих abstractions, contracts, tests и repository
invariants.

Skill не владеет:

- исправлением найденных проблем;
- branch/commit/push/PR lifecycle — им владеет anki-git-workflow;
- CodeRabbit invocation, его findings и iteration semantics — ими владеет
  anki-coderabbit-review;
- repository verification matrix — используй существующих владельцев из
  AGENTS.md и .codex/context/;
- содержательным QA отдельных Anki-карточек вместо профильного toolkit/workflow.

Если текущий запрос одновременно просит review и последующее исправление,
сначала закончи независимую review-фазу и зафиксируй findings; только затем
переходи к реализации подтверждённых исправлений и обычному Git/GitHub lifecycle.

## Trigger contract

Маршрутизируй сюда, в частности:

- «сделай код-ревью»;
- «проведи код-ревью»;
- «сделай ревью PR #...»;
- «проверь этот PR» в контексте проверки реализации;
- просьбу продолжить уже начатое обычное code review.

Явное упоминание CodeRabbit переопределяет этот маршрут и ведёт в
anki-coderabbit-review. Само слово «ревью» или «код-ревью» CodeRabbit не
подразумевает.

Изменение самого этого skill не является просьбой запустить review.

## Read-only contract

Обычный запуск skill только исследует и сообщает результат. Он не:

- меняет tracked-файлы;
- исправляет findings;
- создаёт commits или marker commits;
- push'ит ветку;
- меняет PR body, labels, reviewers или review state;
- публикует inline comments;
- выполняет merge;
- запускает CodeRabbit.

Разрешены чтение Git/GitHub state, исходников, истории и task evidence, а также
неразрушающие проверки. Если проверка создаёт обычные build/test artifacts,
они не считаются изменением продукта и не должны попадать в Git.

## Target contract

Приоритет target:

1. явно указанный пользователем PR/ветка/commit range;
2. иначе текущий checkout и связанный с ним PR, если он существует.

Не переключай ветки молча и не подменяй target более удобным. Для удалённого PR
предпочитай структурированное чтение GitHub/gh вместо checkout чужой ветки.

## Независимость от внешних reviewers

До завершения собственного substantive анализа не используй findings
CodeRabbit, другого LLM-reviewer или человека как список подсказок. Разрешено
читать task/requirement clarifications из обсуждения, но review comments,
bot findings и disposition tables откладываются.

Если пользователь отдельно просит сравнить независимое review с CodeRabbit или
другим review, сначала зафиксируй собственный набор findings, затем выполняй
сравнение. Не выдавай чужой finding за собственную находку.

## Источники требований

Исходная постановка задачи обычно сохраняется пользователем в Windows Downloads
до закрытия PR. При review попытка найти этот prompt обязательна, если среда
имеет доступ к Windows filesystem.

Нормативный контекст собирается из:

- текущего запроса пользователя и явных последующих уточнений;
- исходного task prompt из Windows Downloads;
- связанного issue/task и доказанных уточнений требований;
- применимых repository contracts и invariants.

PR body — это прежде всего заявление реализации: что автор утверждает, что
сделано и проверено. Он не заменяет исходную постановку и не становится
источником требования только потому, что описывает уже реализованное решение.

Материальные противоречия между нормативными источниками не разрешай догадкой:
покажи их как ограничение review. Если исходный prompt не найден однозначно,
продолжай по доступным источникам и явно отметь этот пробел.

## Критерий доказанности

Finding существует только если можно объяснить:

- где находится проблема;
- какое поведение, требование или invariant нарушается;
- при каких условиях это проявляется;
- какой наблюдаемый эффект или maintenance-риск получается.

Предположение «здесь потенциально можно улучшить» без конкретного failure mode
не является finding.

## Параллельный анализ

Для достаточно крупного PR используй доступных read-only субагентов по
независимым направлениям, если это сокращает время или повышает покрытие.
Не хардкодь число субагентов и не создавай параллельную запись.

Главный reviewer обязан сам объединить результат: убрать дубли, перепроверить
evidence по актуальному target, нормализовать severity и найти межфайловые
проблемы, которые отдельный субагент мог не увидеть.

Перед substantive review прочитай все три reference:

- references/review-workflow.md — порядок сбора требований, prompt discovery,

- references/review-criteria.md — обязательные инженерные и специальные критерии;

альтернативный Git workflow или CodeRabbit workflow.
