# Процедура live/smoke-приёмки в Anki-decks

## 1. Спецификация проверки до запуска

Запиши в `.codex/local/reports/<task>/` краткий план:

- текущий commit/ветка, компоненты и команда **штатного** запуска;
- точные входы и их происхождение, правила копирования/изоляции;
- что считается PASS, FAIL и неполным свидетельством;
- критерии завершения и безопасной остановки; ограничения времени и ресурсов;
- ожидаемые наблюдаемые данные: exit code, JSON/JSONL, disk state,
  manifest, checkpoint, браузерные процессы, изображения.

Объём smoke подбирай по риску: он должен проходить значимый **реальный**
путь быстро, но не обязан повторять весь длинный soak. Увеличивай нагрузку
только ради проверяемой гипотезы; не переносить в постоянные скрипты
случайные размеры корпуса и номера задач.

## 2. Вспомогательные скрипты: что разрешено

Разрешено: выбрать набор входов из фактического экспорта, запустить настоящую
команду, передать штатные параметры, ограничить время/ресурсы, наблюдать за
процессами, записать stdout/stderr и код выхода, измерять память и время,
проверить реальные артефакты, сравнить до/после, собрать скриншоты.

Недопустимо: переписать в helper логику `anki-repo`/`asset-store`,
молча сгенерировать «успешный» manifest или `deck.json`, самостоятельно
считать проверенный медиафайл вместо механизма проекта, обходить ошибку
браузера через фиктивный ответ, заменять запись checkpoint своим API
или подтверждать очистку только по собственному списку запущенных процессов.

Языки не ограничены: возможно сочетание Rust/C++ для низкоуровневого
мониторинга, C#/PowerShell для Windows, Bash/Go для Linux, JS/TS для
автоматизации браузерного окружения, Python/R/Lua для анализа измерений
и любого иного подходящего языка. Использование сторонних библиотек само
по себе не причина менять Cargo workspace или коммитить вспомогательный код.
Если helper ошибся, это ошибка наблюдателя — не автоматически ошибка продукта.

## 3. Матрица сценариев по изменённой области

| Область | Smoke через реальный код | Углублённая приёмка |
| --- | --- | --- |
| `anki-repo` и CrowdAnki | CLI на копии действительного экспорта, схема/validate | dry-run и `--apply`, реальное «до/после», idempotency, инварианты UUID/GUID |
| `kanji-assets` / Yarxi | Реальное получение ограниченного набора символов | идентичность статьи, PNG/GIF, сбои/CDP, возобновление, очистка |
| `pitch-assets` / JPDB | Реальное получение небольшого набора | пакет, повтор, ошибки провайдера, проверка PNG/манифеста |
| Пакетный исполнитель | Настоящие `batch start/run/status` и сохранённый результат | прерывание после checkpoint, resume, отсутствие повторной записи/потери |
| Chromium и temp GC | Запуск и штатное закрытие браузерной сессии | отказ bootstrap/CDP, завершение дочерних процессов, проверка чужих ресурсов |
| Изменения скорости/параллелизма | Живой сценарий на штатной сборке | повторяемые сравнительные прогоны с неизменным корпусом, оценка ошибок и ресурсов |

Выбирай только строки, относящиеся к изменению. Точный синтаксис CLI и
допустимые параметры бери из `tools/asset-store/README.md`, а не из примеров
этого skill. Для unit-тестов разрешены fixtures; для живой проверки внешнего
провайдера — нет.

## 4. Доказательства и негативные сценарии

При каждом реальном прогоне зафиксируй:

- фактические команды, версию/сборку бинарника, исходный commit, ОС и
  версии внешних runtime; параметры и входные хеши, когда важна воспроизводимость;
- exit code и stdout/stderr **того процесса**, который выполнял реализацию;
- наблюдения вне самого stdout: сохранённые состояния, количество попыток,
  целостность manifest/export, реальные изображения/отчёты, если применимо;
- для Chromium: завершение/осиротевшие PID, профили, блокировки, остатки в
  системном temp; отделяй доказанную чистоту от неполной видимости `/proc`;
- для прерываний: последний подтверждённый checkpoint, факт остановки,
  результат повторного запуска и отсутствие дублей или потерь;
- для измерений: разные worker settings проверять сопоставимыми входами,
  уточнять разогрев, кэш, ограничения провайдера и погрешность.

Не используй «все процессы завершились» как доказательство корректности
данных. Не используй «файл появился» как доказательство реального
прохождения верификации. Не используй «скрипт завершился 0» как
единственное условие PASS.

Если источник недоступен, подготовка/браузер не запущены, часть доказательств
недоступна или проверка не завершена — отчёт **PARTIAL/NOT_RUN**, а не PASS.
Не скрывай провал, подавляя stderr или меняя ожидаемые значения постфактум.

## 5. Постусловия

1. Убедись, что вспомогательные скрипты и отчёты всё ещё игнорируются Git;
   не перемещай их в `tools/`, `.github/` или `.agents/skills/`.
2. Проверь чистоту пользовательских данных и разницу `git status` относительно
   исходной ревизии. Преднамеренные файлы разработки отдели от мусора прогона.
3. Временные ресурсы очищай через штатный механизм их владельца. При сбое
   диагностики не удаляй чужие процессы или каталоги.
4. Если воспроизведена постоянная регрессия, добавь отдельный **постоянный**
   Rust/контрактный тест на правильном уровне; не коммить весь разовый harness.
5. Сообщи пользователю, какие тесты выполнены, их результаты и точный путь
   к локальным свидетельствам; не обещай возможность повторения, если
   зависимые данные/доступы отсутствуют.
