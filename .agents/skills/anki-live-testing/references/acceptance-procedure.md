# Процедура живой и смок-приёмки в Anki-decks

## 1. Спецификация проверки до запуска

**До запуска** запиши план в `.codex/local/reports/<task>/`:

- текущий коммит, рабочие изменения, команда сборки и происхождение
  исполняемого файла; ОС, компоненты и штатная команда запуска;
- сначала карту всех существенно затронутых путей, требований и рисков
  по изменениям, затем — соответствующий обязательный сценарий для каждого;
  у сценария укажи путь исполнения, способ доказательства и независимый
  ожидаемый результат;
- происхождение входов, их исходное состояние, изоляцию и наличие кэша;
- условия PASS/FAIL, признаки неполного свидетельства, критерии остановки
  и ограничения времени/ресурсов, выбранные **до** получения результата;
- наблюдаемые данные: код завершения, JSON/JSONL, состояние файловой
  системы, манифест, контрольные точки, процессы и изображения.

Не делай ожидаемым результатом выход той же команды, которую проверяешь:
сравнивай с контрактом владельца, входным состоянием и независимыми
постусловиями. Отметь, какие изменённые пути не покрыты и почему; их нельзя считать
проверенными или скрывать за PASS соседнего сценария. Неприменимость
доказывай по области изменения, а не удобством запуска. Нельзя молча
исключать сценарий после неудачного выполнения.

Объём смок-проверки подбирай по риску: он должен проходить значимый **реальный**
путь быстро, но не обязан повторять длительное нагрузочное испытание.
Увеличивай нагрузку только ради проверяемой гипотезы; не переноси в постоянные скрипты
случайные размеры корпуса и номера задач. Если изменение касается
внешнего получения ресурса, выбирай входы так, чтобы запрос действительно
прошёл через провайдера; подтверждённый ресурс из кэша проверяет только
повторное использование. Не очищай каноническое хранилище для получения
нужного исхода.

## 2. Вспомогательные скрипты: что разрешено

Предпочитай существующие штатные проверки. Если их недостаточно, создавай
минимальный разовый автоматизированный сценарий: выбирай входы из настоящего
экспорта, запускай штатную команду, ограничивай время/ресурсы, отслеживай
процессы, сохраняй stdout/stderr и код завершения, измеряй ресурсы,
проверяй реальные артефакты, сравнивай до/после и собирай снимки экрана.
Машинно проверяемые критерии PASS/FAIL и постусловия должны оцениваться
автоматически, а не ручным сопровождением каждого прогона. Проверяй
содержимое машинного вывода, а не только код возврата. Ручной осмотр
визуальных свойств допускается, но отдельно отмечается в отчёте.

Недопустимо: переписать во вспомогательном скрипте логику
`anki-repo`/`asset-store`,
молча сгенерировать «успешный» манифест или `deck.json`, самостоятельно
считать проверенный медиафайл вместо механизма проекта, обходить ошибку
браузера через фиктивный ответ, заменять запись контрольной точки собственным API
или подтверждать очистку только по собственному списку запущенных процессов.

Языки не ограничены: возможно сочетание Rust/C++ для низкоуровневого
мониторинга, C#/PowerShell для Windows, Bash/Go для Linux, JS/TS для
автоматизации браузерного окружения, Python/R/Lua для анализа измерений
и любого иного подходящего языка. Использование сторонних библиотек само
по себе не причина менять рабочую область Cargo или включать
вспомогательный код в коммит. Для параллельных исполнителей используй
раздельные каталоги запусков и независимые файлы результатов либо назначь
одного владельца записи; не перезаписывай доказательства соседних прогонов.
Если вспомогательный скрипт ошибся, это ошибка наблюдателя — не обязательно
ошибка продукта. Диагностируй и укажи его ошибку отдельно, не превращая
неполное наблюдение в PASS.

Штатные `yarxi_dark_acceptance` и `jpdb_pitch_acceptance` создают проверяемые
ZIP только вне рабочей копии по контракту `tools/asset-store/README.md`.
Не направляй их `--output` в `.codex/local/reports/<task>/`: там должны
находиться собственные отчёты, путь внешнего ZIP, SHA-256, размер, результат
проверки архива и ограничения его доступности для повторной проверки.

## 3. Матрица сценариев по изменённой области

| Область | Смок-проверка через реальный код | Углублённая приёмка |
| --- | --- | --- |
| `anki-repo` и CrowdAnki | CLI на копии действительного экспорта, схема/validate | проверка без записи и `--apply`, реальное «до/после», идемпотентность, инварианты UUID/GUID |
| `kanji-assets` / Yarxi | Реальное получение ограниченного набора символов | идентичность статьи, PNG/GIF, сбои/CDP, возобновление, очистка |
| `pitch-assets` / JPDB | Реальное получение небольшого набора | пакет, повтор, ошибки провайдера, проверка PNG/манифеста |
| Пакетный исполнитель | Настоящие `batch start/run/status` и сохранённый результат | прерывание после контрольной точки, возобновление, отсутствие повторной записи/потери |
| Chromium и очистка временных ресурсов | Запуск и штатное закрытие браузерной сессии | отказ инициализации/CDP, завершение дочерних процессов, проверка чужих ресурсов |
| Изменения скорости/параллелизма | Живой сценарий на штатной сборке | повторяемые сравнительные прогоны с неизменным корпусом, оценка ошибок и ресурсов |

Выбирай только строки, относящиеся к изменению. Точный синтаксис CLI и
допустимые параметры бери из `tools/asset-store/README.md`, а не из примеров
этого навыка. Для модульных тестов допустимы синтетические тестовые данные;
для живой проверки внешнего провайдера подмена его ответов недопустима.

## 4. Доказательства и негативные сценарии

Перед приёмкой проверь соответствие исполняемого файла исходному состоянию.
Запуск из другого рабочего дерева или ранее собранного файла без
подтверждённого происхождения не доказывает текущий HEAD; при сомнении
пересобери штатной командой и зафиксируй фактически использованный файл.
Если есть незакоммиченные изменения, включи их в описание проверенной версии.

При каждом реальном прогоне зафиксируй:

- фактические команды, версию/сборку бинарника, исходный коммит, ОС и
  версии внешних сред выполнения; параметры и входные хеши,
  когда важна воспроизводимость;
- код завершения и stdout/stderr **того процесса**, который выполнял реализацию;
- доказательство фактического выполнения требуемого пути: события CLI/CDP,
  исход провайдера, контрольные точки или изменения данных; отметь, был ли
  реальный запрос, повторное использование или пропуск;
- наблюдения вне самого stdout: сохранённые состояния, количество попыток,
  целостность манифеста/экспорта, реальные изображения/отчёты, если применимо;
- для Chromium: завершение/осиротевшие PID, профили, блокировки, остатки в
  системном временном каталоге; отделяй доказанную чистоту от неполной видимости `/proc`;
- для прерываний: последнюю подтверждённую контрольную точку, факт остановки,
  результат повторного запуска и отсутствие дублей или потерь;
- для измерений: разные настройки исполнителей проверяй сопоставимыми входами,
  уточнять разогрев, кэш, ограничения провайдера и погрешность.

Не используй «все процессы завершились» как доказательство корректности
данных. Не используй «файл появился» как доказательство реального
прохождения верификации. Не используй «скрипт завершился 0» как
единственное условие PASS. Не считай успешную проверку кэша доказательством
сетевого получения. Для `anki-repo qa` код `0` допустим даже при замечаниях
уровня `error`: проверяй `findings_total`, `by_code`, `truncated` и подходящие
предметные правила, не только код завершения.

Различай три ситуации: **FAIL** — исполненный проверяемый путь нарушил
ожидаемый контракт; **PARTIAL** — запуск был, но существенные доказательства
отсутствуют или причина сбоя не установлена; **NOT_RUN** — обязательный
сценарий не запускался. Называй ошибку внешней предпосылкой только при
подтверждённой независимой диагностике. Не объясняй сбой построения URL,
работы CDP или обработки ответа «недоступностью провайдера» без доказательств.
Недоступный браузер до запуска — причина NOT_RUN; неполное наблюдение после
запуска — PARTIAL, а доказанный дефект реализации — FAIL.

Для **намеренно негативного сценария** PASS допустим, когда заранее
определённый отказ действительно вызван, обработан штатным кодом и
постусловия проверены. Такой PASS не подтверждает обычный запрос к
провайдеру. Не скрывай сбои подавлением stderr или изменением ожиданий
после результата. **Итоговый PASS** допустим лишь при PASS каждого
обязательного сценария; любой FAIL запрещает общий PASS, а недопроверенный
обязательный сценарий делает итог PARTIAL/NOT_RUN с явной причиной.

## 5. Постусловия

1. Убедись, что вспомогательные скрипты и отчёты всё ещё игнорируются Git;
   не перемещай их в `tools/`, `.github/` или `.agents/skills/`.
2. Проверь чистоту пользовательских данных и разницу `git status` относительно
   исходной ревизии. Преднамеренные файлы разработки отдели от мусора прогона.
3. Временные ресурсы очищай через штатный механизм их владельца. При сбое
   диагностики не удаляй чужие процессы или каталоги.
4. Если воспроизведена регрессия, зафиксируй воспроизведение и желаемый
   постоянный регрессионный тест. **Создавай или меняй** отслеживаемый тест
   только когда это входит в разрешённый объём разработки; при поручении
   лишь проверить или прочитать код не вноси изменений в репозиторий.
   Постоянный тест размещай на соответствующем уровне и не включай
   в него весь разовый набор вспомогательных инструментов.
5. Для каждого обязательного сценария сообщи точный статус, выполненные
   команды, проверенные инварианты и путь к доказательствам. Пропуски,
   частичные результаты и неизвестную причину ошибки указывай явно;
   не обещай повторяемости без необходимых данных и доступов.
