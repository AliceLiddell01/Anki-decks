# Процедура живой и смок-приёмки в Anki-decks

## 1. Спецификация проверки до запуска

Запиши в `.codex/local/reports/<task>/` краткий план:

- текущий коммит/ветка, компоненты и команда **штатного** запуска;
- точные входы и их происхождение, правила копирования/изоляции;
- что считается PASS, FAIL и неполным свидетельством;
- критерии завершения и безопасной остановки; ограничения времени и ресурсов;
- ожидаемые наблюдаемые данные: код завершения, JSON/JSONL, состояние файловой системы,
  манифест, контрольную точку, браузерные процессы, изображения.

Объём смок-проверки подбирай по риску: он должен проходить значимый **реальный**
путь быстро, но не обязан повторять всё длительное нагрузочное испытание. Увеличивай нагрузку
только ради проверяемой гипотезы; не переносить в постоянные скрипты
случайные размеры корпуса и номера задач.

## 2. Вспомогательные скрипты: что разрешено

Предпочитай существующие штатные проверки. Если их недостаточно, создавай
минимальный разовый автоматизированный сценарий: выбирай входы из настоящего
экспорта, запускай штатную команду, ограничивай время/ресурсы, отслеживай
процессы, сохраняй stdout/stderr и код завершения, измеряй ресурсы,
проверяй реальные артефакты, сравнивай до/после и собирай снимки экрана.
Машинно проверяемые критерии PASS/FAIL и постусловия должны оцениваться
автоматически, а не ручным сопровождением каждого прогона. Ручной осмотр
визуальных свойств допускается, но отдельно отмечается в отчёте.

Недопустимо: переписать во вспомогательном скрипте логику `anki-repo`/`asset-store`,
молча сгенерировать «успешный» манифест или `deck.json`, самостоятельно
считать проверенный медиафайл вместо механизма проекта, обходить ошибку
браузера через фиктивный ответ, заменять запись контрольной точки собственным API
или подтверждать очистку только по собственному списку запущенных процессов.

Языки не ограничены: возможно сочетание Rust/C++ для низкоуровневого
мониторинга, C#/PowerShell для Windows, Bash/Go для Linux, JS/TS для
автоматизации браузерного окружения, Python/R/Lua для анализа измерений
и любого иного подходящего языка. Использование сторонних библиотек само
по себе не причина менять Cargo workspace или коммитить вспомогательный код.
Если вспомогательный скрипт ошибся, это ошибка наблюдателя — не обязательно
ошибка продукта.

Штатные `yarxi_dark_acceptance` и `jpdb_pitch_acceptance` создают проверяемые
ZIP только вне рабочей копии по контракту `tools/asset-store/README.md`.
Не направляй их `--output` в `.codex/local/reports/<task>/`: там должны
находиться собственные отчёты, путь внешнего ZIP, SHA-256, размер, результат
проверки архива и ограничения его доступности для повторной проверки.

## 3. Матрица сценариев по изменённой области

| Область | Смок-проверка через реальный код | Углублённая приёмка |
| --- | --- | --- |
| `anki-repo` и CrowdAnki | CLI на копии действительного экспорта, схема/validate | dry-run и `--apply`, реальное «до/после», идемпотентность, инварианты UUID/GUID |
| `kanji-assets` / Yarxi | Реальное получение ограниченного набора символов | идентичность статьи, PNG/GIF, сбои/CDP, возобновление, очистка |
| `pitch-assets` / JPDB | Реальное получение небольшого набора | пакет, повтор, ошибки провайдера, проверка PNG/манифеста |
| Пакетный исполнитель | Настоящие `batch start/run/status` и сохранённый результат | прерывание после checkpoint, resume, отсутствие повторной записи/потери |
| Chromium и очистка временных ресурсов | Запуск и штатное закрытие браузерной сессии | отказ инициализации/CDP, завершение дочерних процессов, проверка чужих ресурсов |
| Изменения скорости/параллелизма | Живой сценарий на штатной сборке | повторяемые сравнительные прогоны с неизменным корпусом, оценка ошибок и ресурсов |

Выбирай только строки, относящиеся к изменению. Точный синтаксис CLI и
допустимые параметры бери из `tools/asset-store/README.md`, а не из примеров
этого skill. Для unit-тестов разрешены fixtures; для живой проверки внешнего
провайдера — нет.

## 4. Доказательства и негативные сценарии

При каждом реальном прогоне зафиксируй:

- фактические команды, версию/сборку бинарника, исходный коммит, ОС и
  версии внешних сред выполнения; параметры и входные хеши, когда важна воспроизводимость;
- код завершения и stdout/stderr **того процесса**, который выполнял реализацию;
- наблюдения вне самого stdout: сохранённые состояния, количество попыток,
  целостность манифеста/экспорта, реальные изображения/отчёты, если применимо;
- для Chromium: завершение/осиротевшие PID, профили, блокировки, остатки в
  системном temp; отделяй доказанную чистоту от неполной видимости `/proc`;
- для прерываний: последнюю подтверждённую контрольную точку, факт остановки,
  результат повторного запуска и отсутствие дублей или потерь;
- для измерений: разные настройки исполнителей проверяй сопоставимыми входами,
  уточнять разогрев, кэш, ограничения провайдера и погрешность.

Не используй «все процессы завершились» как доказательство корректности
данных. Не используй «файл появился» как доказательство реального
прохождения верификации. Не используй «скрипт завершился 0» как
единственное условие PASS.

Если источник **неожиданно** недоступен, подготовка/браузер не запущены,
часть доказательств недоступна или проверка не завершена — отчёт
**PARTIAL/NOT_RUN**, а не PASS. Для **намеренно негативного сценария**,
когда заранее определённый отказ действительно вызван, а его обработка
и постусловия подтверждены штатным кодом, допустим PASS именно этого
негативного сценария. Он не подтверждает успешное получение данных
от настоящего провайдера. Не скрывай провал, подавляя stderr или
меняя ожидаемые значения постфактум.

## 5. Постусловия

1. Убедись, что вспомогательные скрипты и отчёты всё ещё игнорируются Git;
   не перемещай их в `tools/`, `.github/` или `.agents/skills/`.
2. Проверь чистоту пользовательских данных и разницу `git status` относительно
   исходной ревизии. Преднамеренные файлы разработки отдели от мусора прогона.
3. Временные ресурсы очищай через штатный механизм их владельца. При сбое
   диагностики не удаляй чужие процессы или каталоги.
4. Если воспроизведена постоянная регрессия, добавь отдельный **постоянный**
   Rust/контрактный тест на правильном уровне; не коммить весь разовый набор вспомогательных инструментов.
5. Сообщи пользователю, какие тесты выполнены, их результаты и точный путь
   к локальным свидетельствам; не обещай возможность повторения, если
   зависимые данные/доступы отсутствуют.
