# Живые и смок-проверки Anki-decks

## Назначение и активация

Проверяй **фактическое поведение кода Anki-decks** через штатные бинарники,
данные, браузерные сессии и файловые контракты. Применяй skill при разработке,
когда запрошена или необходима smoke/live/интеграционная приёмка, воспроизведение
ошибки в runtime, проверка отказов/возобновления либо сравнительный прогон.

Это не общий skill тестирования и не замена владельцам: требования к колодам —
`.codex/context/03-VERIFICATION.md`; команды и данные —
`tools/anki-repo/README.md`, `tools/asset-store/README.md`; обычные проверки —
`AGENTS.md`; Git/PR — `anki-git-workflow`. Независимый read-only код-ревью
по-прежнему использует отдельный `anki-code-review` со **своим** системным
временным каталогом, а не этот маршрут.

## Главный инвариант: объект проверки — настоящая реализация

Временный помощник **может управлять, наблюдать, собирать данные и сравнивать**,
но **не вправе подменять** исследуемую реализацию, её контракты или результаты:

- Запускай настоящий `anki-repo`, `kanji-assets`, `pitch-assets` и
  фактические обработчики через предусмотренные проектом точки входа.
- Не заменяй реализацию собственным мини-парсером CrowdAnki, алгоритмом
  получения кандзи, мнимым CDP/Yarxi/JPDB или фиктивным writer/checkpoint.
- Не записывай ожидаемый результат напрямую в манифест, пакет, экспорт или
  медиа-каталог с последующим заявлением, что его создала тестируемая команда.
- Не отключай проверки, ошибки, таймауты, защиту хранилища, верификацию медиа,
  TLS-политику или штатную очистку ради успешного результата.
- Не интерпретируй успешную работу тестовой обёртки как успех программы: сверяй
  вывод, код возврата, записанное состояние и побочные эффекты **самого** CLI.
- Синтетические fixtures и подмены внешних зависимостей допустимы в **постоянных
  модульных/контрактных тестах**, когда они не заменяют исследуемый слой. Они не
  доказывают прохождение live-теста реального провайдера или Chromium.
- Предусмотренный проектом тестовый режим/внедрение отказа допустим лишь с
  явной маркировкой, какая часть проверена; не выдавай его за обычный runtime.
  Наряду с этим проверяй штатный путь исполнения, если цель — production-сценарий.

## Временные помощники и границы Git

Во время **разработки и её живой приёмки** размещай вспомогательные исходники в
`.codex/local/scripts/<task>/`, свидетельства в
`.codex/local/reports/<task>/`. `<task>` — понятное имя текущей задачи,
путь строится относительно **корня текущего checkout**, а не абсолютного пути
чужой машины. Эти каталоги подпадают под `/.codex/local/` в `.gitignore`.
Проверь `git check-ignore -v` и `git ls-files` для своих файлов до записи,
после прогона проверь `git status --short`. Ничего из них не добавляй в индекс,
commit или PR. Не удаляй существующие чужие локальные артефакты.

Можно создавать любые **одноразовые** скрипты, обёртки, визуализаторы, сборщики
метрик, драйверы команд и анализаторы — на **любом подходящем языке**, включая
Rust, C/C++, C#, Go, Java/Kotlin, JavaScript/TypeScript (Node.js, Deno, Bun),
Python, PowerShell, Bash, Lua, Zig и другие. Список не ограничивающий: выбери
язык по задаче, доступному runtime/ОС и надёжности, а не по привычке к Python
или shell. Не добавляй обязательную зависимость проекту ради разового помощника.
Скрипт на другом языке не получает разрешения копировать логику приложения.

Рабочие **runtime**-каталоги Chromium, профили, короткие пути сокетов,
файловые блокировки и временные объекты создаёт их **штатный владелец** из
`asset-store`: каталог локальных скриптов не является заменой
`TempWorkspace` или общего системного temp. Изолируй входные данные и
свидетельства, не перенаправляя внутренние пути в обход проверок владельца.

В Git допускаются только самостоятельно обоснованные **постоянные** реализации,
общие проверки контрактов и регрессионные тесты. Одноразовая live-приёмка
конкретного изменения не становится постоянным инструментом лишь потому,
что использовалась в разработке. Не удаляй существующие постоянные CLI приёмки
без отдельного анализа их повторно используемого контракта.

## Порядок работы

1. Установи точные HEAD, область изменения, текущие владельцы контрактов,
   окружение и применимые команды. Прочитай [поверхности проекта](references/project-surfaces.md).
2. Сформулируй проверяемую гипотезу, **штатный** путь выполнения, ожидаемые
   артефакты/инварианты и отрицательный сценарий. Прочитай
   [процедуру и критерии свидетельств](references/acceptance-procedure.md).
3. Проверь базовое состояние и границы записи. Для колод используй копии
   экспортов; для пакетных медиа — отдельную разрешённую область/пакет.
   Канонические `decks/**`, `media/` и подтверждённые `.asset-store/`
   не являются одноразовой песочницей.
4. Подготовь только необходимые помощники в `.codex/local/scripts/<task>/`.
   Они вызывают реальные команды или наблюдают их; не изменяют исходный код
   и тестируемую реализацию ради прохождения проверки.
5. Выполни штатный smoke; затем нужные интеграционные, визуальные,
   отказоустойчивые или нагрузочные сценарии. Зафиксируй реальные exit code,
   события, сохраняемое состояние и выполненную очистку.
6. Выполни применимые постоянные проверки Cargo/репозитория и
   регрессионные тесты. Успех unit-тестов не заменяет живую приёмку, и наоборот.
7. Сверь до/после, защиту пользовательских данных, отсутствие утечек
   Chromium/временных ресурсов и неизменность tracked-файлов, кроме
   намеренных изменений задачи.
8. Отчитайся: **PASS / FAIL / PARTIAL / NOT_RUN**, фактические команды,
   ревизия, среда, покрытые инварианты, ограничения, пути к локальным
   свидетельствам. Не заявляй PASS без реальной проверки.

## Границы публикации

Собранные для приёмки изображения/ответы провайдеров, локальные профили,
журналы, дампы, скриншоты и промежуточные отчёты не публикуются как
постоянные файлы проекта. Канонические проверенные ресурсы могут попадать в Git
только по **отдельному существующему контракту публикации** домена
`asset-store`, а не вследствие самого live-теста.

Этот skill **не** управляет ветками, commit, push, PR и merge: для них действуют
`anki-git-workflow` и прямой запрос пользователя. Также он не превращает
собственную процедуру приёмки в новое CI-задание автоматически.
