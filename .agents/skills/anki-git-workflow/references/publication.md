# Публикация: branch, staging, commit, push, remote postcondition

Этот файл владеет порядком действий обычной публикуемой задачи до
подтверждённого удалённого состояния. Контракт и границы задаёт `SKILL.md`.

## 1. Установить фактическое состояние checkout

Перед mutation зафиксируй repository identity и текущее состояние:

```bash
git rev-parse --show-toplevel
git remote -v
git rev-parse --abbrev-ref HEAD
git status --porcelain
git rev-parse HEAD
```

Прежде чем публиковать, обнови удалённые ссылки, а не доверяй кэшу
remote-tracking:

```bash
git fetch <remote> --prune
```

Если checkout не относится к ожидаемому repository или однозначно установить
текущую ветку и её upstream нельзя — это precondition problem: не угадывай и не
переключай ветки молча.

## 2. Ветка

### Новая самостоятельная задача

1. Установи фактический remote, а не предполагай `origin` по умолчанию: возьми
   remote из upstream текущей ветки, а если upstream ещё нет — из фактического
   состояния `git remote -v`.
2. Установи default/base branch из **удалённого** состояния, а не по памяти:

   ```bash
   git ls-remote --symref <remote> HEAD
   ```

   Локальная ссылка `refs/remotes/<remote>/HEAD` кэшируется и может быть
   устаревшей, поэтому источником истины не является.
3. Обнови базу безопасно (fetch; при необходимости fast-forward локальной базы).
4. Создай смысловую task branch от этой базы. Имя отражает область и содержание
   задачи; временные roadmap/stage-идентификаторы в имя ветки не попадают.
5. Не подмешивай неизвестные пользовательские изменения.

### Продолжение существующей задачи

Используй существующую ветку, а не новую. Перед продолжением проверь её identity,
upstream и связанный PR. Новая ветка не создаётся только потому, что началась
следующая фаза того же work item.

### Прямая работа в default branch

Работа в default branch напрямую не ведётся: это инвариант repository contract
(`AGENTS.md`, «Не работай напрямую в `main`»).

Явная просьба работать прямо в default branch конфликтует с этим контрактом. Это
не исключение и не переопределение инварианта на будущее, а состояние, требующее
решения: сообщи конфликт и предложи task branch, а не начинай молча писать в
default branch.

## 3. Verification и staging

1. Выполни применимую verification от её фактических владельцев
   (`AGENTS.md`, `.codex/context/`, owner-документ затронутой области). Skill не
   подменяет verification matrix и не решает, какие проверки нужны.
2. Просмотри итоговый diff целиком, а не только список файлов.
3. Стейдж только пути текущего work item:

   ```bash
   git add -- <путь> [<путь> ...]
   ```

4. Перечитай staged diff и убедись, что в индекс попало ровно ожидаемое:

   ```bash
   git diff --cached --stat
   git diff --cached
   git status --porcelain
   ```

Случайные staged/untracked файлы пользователя не захватываются: их не добавляют,
не коммитят и не удаляют. В индекс не попадают `.codex/local/` и чужой staging.
Если принадлежность изменений установить нельзя — это состояние, требующее
решения, а не повод угадывать.

## 4. Commit

- Сообщение на русском языке и описывает фактическое изменение, а не исходный
  замысел.
- Если в репозитории есть устойчивый conventional style, сохраняй его.
- В сообщение не попадают номер текущего PR, SHA, имя stage и разовый план.
- Коммит делается в текущей ветке текущего work item; несвязанные локальные
  изменения в него не попадают.

Пустой commit допустим только там, где это требует отдельный явно определённый
workflow (например маркер завершённой CodeRabbit iteration — этим владеет
`anki-coderabbit-review`), а не как способ закрыть задачу без изменений.

## 5. Push

Публикуй текущую task branch **явно** в ожидаемый remote/ref.

Перед push прочитай удалённую ссылку и сравни её с локальным состоянием: так
обнаруживаются невидимые локально удалённые коммиты, и публикация не превращается
в неожиданный отказ. Голый `git push` не является контрактом skill: он подчиняется
`push.default` и другим настройкам Git и в конфигурациях вида `matching` может
опубликовать несколько refs.

Если удалённая ссылка расходится с локальным состоянием, порядок такой:

1. получи удалённые коммиты и изучи их до любых действий: `git fetch <remote>`,
   затем граф (`git log --graph --oneline <remote>/<branch>`) и фактическое
   изменение относительно общего предка (`git merge-base`, `git diff`).
2. определи, что это за состояние. Чужие коммиты не перезаписываются. Расхождение,
   которое нельзя свести обычным путём текущего work item, — это blocker:
   остановись, назови конкретное препятствие и последний подтверждённый
   опубликованный HEAD. Не расширяй задачу молча до разрешения чужой истории.
3. force-push и переписывание истории для «разрешения» расхождения запрещены
   (см. § 8) и основанием для них расхождение не является.

Отказ обычного non-force push на non-fast-forward — это более поздний барьер, а не
замена чтению удалённого состояния. Проверяй ссылку непосредственно перед push и
не продолжай push, если ref изменился между проверкой и push.

```bash
git ls-remote --refs <remote> refs/heads/<branch>

# первая публикация ветки: новый upstream
git push --set-upstream <remote> refs/heads/<branch>:refs/heads/<branch>

# последующая публикация: явный remote и refspec
git push <remote> refs/heads/<branch>:refs/heads/<branch>
```

`<remote>` — фактический remote этой ветки (берётся из её upstream, а не
назначается произвольно). Push выполняется без force: force-push требует
отдельного явного основания (см. § 8).

## 6. Remote postcondition

Публикация подтверждена только тогда, когда выполнено:

```text
expected local HEAD == actual SHA соответствующей remote branch
```

Remote-tracking ref (`refs/remotes/...`) для этого не годится: он может быть
устаревшим. Читай саму удалённую ссылку:

```bash
git rev-parse HEAD
git ls-remote --refs <remote> refs/heads/<branch>
```

Сравни полученные SHA по точному значению. Совпадение — единственное
доказательство доставки. Расхождение означает, что ожидаемое изменение не
опубликовано, и работа не завершена.

`git ls-remote --refs` здесь предпочтителен, потому что отдаёт только refs, без
`^{}`-строк peeled-аннотаций, и даёт однозначное сравнение. Если фактическая среда
требует другого нативного механизма, используй эквивалент, который читает именно
удалённую ссылку, и назови его явно.

## 7. Протокол неизвестного результата сетевой операции

Если push (или любая другая сетевая mutation) завершился неизвестным результатом —
таймаут, обрыв соединения, неясный ответ, — порядок строго такой:

1. Сначала установи фактическое удалённое состояние **чтением**:
   `git ls-remote --refs <remote> refs/heads/<branch>`.
2. Не повторяй push вслепую.
3. Повторяй mutation только тогда, когда доказано, что ожидаемое изменение не
   было доставлено.
4. Не перезаписывай чужие новые удалённые коммиты.

То же правило действует для `gh pr create` и `gh pr edit`: неизвестный результат
сначала разрешается чтением удалённого состояния PR, и только потом mutation
повторяется — если доказано, что она не применилась. Появление второго PR для
того же repository/base/head — дефект, а не допустимый исход гонки.

Persistent publication journal или state machine для этого не нужны: достаточно
чтения фактического удалённого состояния.

## 8. Запрещено без отдельного обоснованного разрешения в текущем запросе

- force-push;
- переписывание опубликованной истории (rebase/amend уже опубликованных
  коммитов);
- удаление неизвестных удалённых ветвей;
- публикация другой ветки вместо текущего work item;
- публикация несвязанных локальных изменений;
- смена base PR, переключение на другой PR и закрытие PR.

## 9. Завершённое состояние публикации

Шаг публикации завершён, когда:

```text
staged diff соответствует задаче
commit создан в task branch текущего work item
push выполнен явно в ожидаемый remote/ref
фактический SHA удалённой ветки равен ожидаемому локальному HEAD
```

Только после этого переходи к lifecycle PR
([`pr-lifecycle.md`](pr-lifecycle.md)) и к передаче результата пользователю.
