# PR lifecycle: body, Draft/Ready, merge, конфликты, cleanup

Этот файл владеет порядком действий после подтверждённой публикации commit'а.
Контракт и границы задаёт `SKILL.md`; postcondition push описан в
[`publication.md`](publication.md).

## 1. Identity PR

Обычная самостоятельная repository task имеет **один** PR.

1. Сначала установи, существует ли PR для текущей task branch:
   структурированное чтение удалённого GitHub state через GitHub MCP/connector,
   когда он доступен и удобнее, либо `gh pr view --json ...` как короткая
   проверка.
2. Если PR существует — обновляй его. Дублирующий PR для того же
   repository/base/head не создаётся.
3. Если PR отсутствует — создай новый.

Не создавай новый PR только потому, что началась следующая фаза того же work
item, и не переключайся на другой PR.

## 2. Источник body PR

Источник body — repository-local Markdown-файл, который **не** является tracked:

```text
.codex/local/pr/<task>/body.md
```

`<task>` — короткий смысловой идентификатор текущего work item, а не номер PR,
SHA или номер stage. Не оставляй в имени или содержимом snapshot текущего work
item.

Правила:

- такой тип артефактов закрыт ignore-правилом в `.gitignore`; правило должно быть
  минимально достаточным и не скрывать потенциально важные tracked-файлы;
- путь действительно игнорируется Git и не является tracked — это проверяется
  фактом (`git check-ignore -v <путь>`, `git ls-files <путь>`), а не
  предположением;
- Python/Rust renderer, schema или шаблонизатор для body не вводится: Markdown
  файла достаточно;
- файл полностью формируется и **перечитывается** до публикации;
- файл сохраняется минимум до подтверждённого повторного чтения опубликованного PR
  и не удаляется, пока результат операции неизвестен.

### Recovery source для уже существующего PR

Локальный ignored-файл — рабочий source, но опубликованный PR нельзя
реконструировать по памяти, prompt'у или краткому отчёту.

Если PR уже существует, а локальный source body отсутствует либо текущий checkout
ещё не доказал его синхронность с опубликованным body:

1. прочитай **полный** текущий body удалённого PR;
2. создай отсутствующий локальный `.codex/local/pr/<task>/body.md` из этого body
   без потери существующих разделов, таблиц и текста;
3. перечитай локальный файл и только после этого вноси новую mutation.

Если локальный файл существует, но отличается от удалённого PR, и неизвестно,
какая сторона новее, не перезаписывай ни одну сторону автоматически: сравни их и
явно примири различия. Для уже опубликованного состояния remote body является
recovery baseline, а не поводом затереть доказанные локальные изменения.

Перед публикацией проверь по локальному файлу: title, body, base/head, реально
выполненные проверки и фактические ограничения. Содержательную структуру body
сверь с [`pr-body.md`](pr-body.md).

## 3. Структура body

Содержательной структурой PR body владеет отдельный reference
[`pr-body.md`](pr-body.md). Перед каждым `create/edit` body должен
соответствовать ему по фактическому состоянию текущего work item.

Для обычного содержательного PR это означает реальные Markdown-заголовки
`## Цель`, `## Область изменений`, `## Реализация`, `## Проверки`,
`## CI`, `## Готовность` и `## Ограничения`, а не пару сплошных
абзацев с подписью `Проверки:`. Условные разделы добавляются только когда
применимы; CodeRabbit cycle использует накопительный раздел и таблицу,
определённые в `pr-body.md`.

Body описывает **фактическое** состояние work item, а не исходный замысел,
который уже разошёлся с реализацией. Факты не выдумываются, честные пропуски
проверок называются прямо. В body не попадают номер stage, разовый план, полный
журнал команд и сырой transcript review.

## 4. Create и edit

Новый PR по умолчанию создаётся **Draft** и остаётся Draft до финального
пользовательского review, если пользователь не дал другую явную команду.

```bash
gh pr create --draft --base <base> --head <branch> --title <title> --body-file <путь>
gh pr edit <number> --title <title> --body-file <путь>
```

Interface `gh` версионно-зависим: flags и способы передать body проверяй по
фактическому `gh pr create --help` / `gh pr edit --help` установленной версии, а
не по памяти. Не полагайся на prompts: body передаётся файлом.

Body публикуется только файлом. Инлайновый `--body`, `--body-file -` со stdin,
heredoc непосредственно в вызове провайдера и запись body через GitHub MCP в
обычном локальном порядке работы запрещены: они разрывают связь между
проверенным локальным файлом и опубликованным описанием.

## 5. Повторное чтение опубликованного PR

После `gh pr create` и после каждого `gh pr edit` — перечитай опубликованный PR и
проверь:

```text
repository
base
head
Draft/Ready state
title
body
```

Сравни опубликованный body с локальным файлом с учётом допустимой нормализации
переводов строк (например CRLF/LF, завершающий перевод строки). Прочие расхождения
означают, что PR не соответствует локальному источнику, и должны быть устранены,
а не проигнорированы.

Отдельно проверь, что опубликованный head — это именно ожидаемый HEAD текущего
work item, а не устаревшее состояние.

## 6. Ready

Draft переводится в Ready только по явной команде пользователя либо когда это
следует из явно определённого контракта текущего work item. Успешный push,
зелёный CI или сам факт созданного Draft PR не переводят PR в Ready и тем более
не разрешают merge.

```bash
gh pr ready <number>
```

## 7. Merge

```text
успешный push ≠ разрешение на merge
зелёный CI ≠ разрешение на merge
созданный Draft PR ≠ разрешение на merge
```

Merge выполняется **только** после отдельной текущей явной команды пользователя
на конкретный PR. Разрешение, выданное ранее и относящееся к другому состоянию
work item, не переиспользуется.

Перед merge заново проверь:

- repository, base/head и точный текущий HEAD PR
  (установленную версию `gh` см. в `gh pr view --help`);
- актуальность обязательных checks и reviews относительно **текущего** HEAD:
  после любого изменения HEAD прежние evidence считаются устаревшими;
- что merge не обходит проверки: `--admin` и любые force-механизмы запрещены;
  auto-merge требует того же отдельного разрешения, а ожидающее auto-merge
  **не** считается выполненным merge.

Merge method выбирай безопасный и согласующийся с фактической политикой
репозитория. Не хардкодь squash: сверься с фактическим состоянием репозитория и
interface установленного `gh` (`gh pr merge --help`). Историческая конвенция этого
репозитория — один squash-commit вида `<заголовок> (#<номер>)`, но это наблюдение
о фактических данных, а не вечный контракт: перед merge политика перепроверяется.

Если установленная версия `gh` умеет привязывать merge к ожидаемому HEAD
(например `--match-head-commit <sha>`), используй эту возможность, чтобы не слить
PR, head которого сдвинулся между проверкой и merge; доступность флага
подтверждается по `gh pr merge --help`.

После merge прочитай фактический конечный статус PR (`merged`) и merge SHA: сам
exit code команды не подтверждает удалённый результат. Дальше переходи к cleanup
(§ 9).

## 8. Base advancement и конфликты

Если base продвинулась или возник конфликт:

1. Установи общий предок и фактическое изменение обеих сторон (`git merge-base`,
   diff каждой стороны) до любых правок.
2. Разрешай конфликт по смыслу: whole-file стратегии `ours`/`theirs` и общий выбор
   «своей» стороны как механический приём не применяются. Чужие изменения не
   удаляются.
3. Generated/derived файл, у которого есть владелец-источник, пересоздаётся из
   source, а не правится вручную.
4. Опубликованная ветка обновляется merge актуальной base, без force и без
   переписывания истории; rebase допустим только для ещё не опубликованной истории.
5. После разрешения проверь отсутствие unmerged paths и активной merge/rebase, а
   также происхождение новой базы и итоговый diff.
6. После изменения HEAD считай прежние CI и review evidence устаревшими
   относительно нового commit и проверь состояние заново: сначала обнови локальный
   файл body, затем опубликуй и перечитай его.
7. Не делай force-push опубликованной ветки только ради удобства.

## 9. Post-merge cleanup

После **подтверждённого** merge допустим обычный cleanup собственного work item:
удаление собственной task branch и локальных временных артефактов (включая
repository-local файл body).

Ограничения:

- удаляй ветку только после доказанного сохранения результата: локальная ветка —
  через `git branch -d`, удалённая — после подтверждения её принадлежности этому
  work item и факта merge;
- не удаляй чужую работу и чужие артефакты;
- если squash-merge мешает `git branch -d`, оставь ветку и сообщи ограничение:
  автоматический переход к `-D` и принудительному удалению запрещён;
- cleanup не является частью автоматического lifecycle: он выполняется после
  подтверждённого merge, а не вместо проверок.

## 10. Завершённое состояние work item

```text
commit опубликован и удалённый SHA подтверждён
PR существует в единственном экземпляре для текущей task branch
PR перечитан после последней mutation и соответствует локальному body-файлу
Draft/Ready state соответствует ожидаемому
merge не выполнен, пока нет отдельной текущей явной команды
```

До отдельного разрешения на merge конечный результат обычной задачи — проверенный
Draft PR. Результат передаётся пользователю на review; merge остаётся за
пользователем.
