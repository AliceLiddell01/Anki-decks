# Anki-decks: жизненный цикл Git/GitHub обычной задачи

## Назначение

Skill — **единственный владелец** общей процедуры Git/GitHub для текущей
рабочей копии: рабочая ветка, индекс, commit, push, проверка удалённого состояния,
создание и обновление PR, структурированное описание PR, Draft/Ready, отдельно
разрешённый merge и очистка после merge.

Skill не владеет:

- содержанием работы: что именно нужно изменить, определяет сама задача и
  профильные владельцы (`AGENTS.md`, `.codex/context/`, `tools/anki-repo`);
- набором проверок репозитория — его владельцы перечислены в `AGENTS.md` и
  `.codex/context/`, в первую очередь `.codex/context/03-VERIFICATION.md`;
- логикой, специфичной для CodeRabbit: вызов провайдера, замечания, их оценка,
  правила итераций, ограничение частоты запросов и правила прогона без
  необходимых исправлений принадлежат `anki-coderabbit-review`;
- обычным ревью кода — им владеет `anki-code-review`; содержательным
  суждением о карточках и правкой колод;
- чужими PR и чужими ветками: skill обслуживает текущую задачу.

Соподчинённость владельцев:

```text
anki-git-workflow
    └─ общая процедура Git/GitHub: ветка / индекс / commit / push /
       точная проверка удалённого состояния / создание и обновление PR /
       структурированное описание PR / Draft+Ready / разрешённый merge /
       конфликты / очистка

anki-code-review
    └─ независимое ревью без изменения файлов: требования / окружающий код /
       замечания; не выполняет изменения Git/GitHub

anki-coderabbit-review
    └─ только процедура CodeRabbit: вызов провайдера / завершение /
       замечания / их оценка / правила итераций / ограничение частоты запросов /
       правила прогона без необходимых исправлений
       и делегирует общую публикацию anki-git-workflow
```

Не создавай второго владельца этой процедуры в `AGENTS.md`, `.codex/context/`
или в skill CodeRabbit и не переноси её в них. Skill не создаёт собственную
обёртку над `git`/`gh`, своего CLI, автомата состояний, сохраняемого журнала
публикации или отдельного хранилища состояния: для этого репозитория достаточно
дисциплины и нативных инструментов.

## Контракт маршрутизации

Skill **не требует** буквального имени skill или специальной фразы. Он
применяется, когда работа достигает жизненного цикла Git/GitHub:

- создание или продолжение рабочей ветки;
- подготовка индекса;
- commit;
- push;
- создание или обновление PR;
- Draft/Ready;
- проверка удалённого состояния, CI и ревью перед передачей пользователю;
- разрешение конфликтов с base;
- отдельно разрешённый merge;
- очистка после merge;
- продолжение уже начатой публикации.

Явные запросы пользователя — «закоммить», «запушь», «создай PR», «обнови PR»,
«слей PR», «сделай Draft PR» — маршрутизируются сюда же.

Skill **не активируется** для:

- простого объяснения Git/GitHub без изменений;
- обычного ревью кода — это `anki-code-review`;
- логики ревью, специфичной для CodeRabbit — это `anki-coderabbit-review`;
- чтения истории, веток или PR только ради исследования, если жизненный цикл Git
  не выполняется;
- задачи по изменению самого этого skill как повода выполнить дополнительные
  действия GitHub сверх текущей задачи.

## Контракт конечного состояния: commit не равен публикации

Это главный контракт skill.

Если обычная задача репозитория предполагает публикацию результата и пользователь
явно не ограничил область задачи локальной работой, состояние

```text
есть новый локальный commit
удалённая ветка его не содержит
```

**не является** завершением задачи. После commit рабочий процесс обязан без
дополнительного сообщения пользователя «теперь push» продолжить публикацию и
довести её до подтверждённого удалённого состояния.

Ожидаемая цепочка обычной публикуемой задачи:

```text
изменение
→ применимые проверки
→ проверенный индекс
→ commit
→ push текущей рабочей ветки
→ проверка точного удалённого HEAD
→ создание или актуализация Draft PR с описанием по `references/pr-body.md`
→ повторное чтение и проверка опубликованного PR
→ передача пользователю на ревью
```

Merge в этот автоматический жизненный цикл **не входит**: он выполняется только
по отдельной текущей явной команде пользователя (см.
[`references/pr-lifecycle.md`](references/pr-lifecycle.md), § «Merge»).

Допустимое переопределение — только явное указание пользователя в текущем запросе:
«только локально», «только commit», «не push». Такое указание ограничивает
цепочку ровно настолько, насколько сказано, и относится к текущей задаче.

Локальный код возврата push сам по себе не является доказательством конечного
состояния, и устаревшая ссылка слежения за удалённой веткой — тоже. Публикация
подтверждена только точным сравнением ожидаемого локального HEAD с фактическим SHA
соответствующей удалённой ветки, прочитанным из удалённого репозитория (см.
[`references/publication.md`](references/publication.md)).

## Штатные инструменты

Граница инструментов:

- штатный `git` — локальная история, `status`/`diff`, ветка, подготовка индекса,
  commit, fetch, merge/rebase по разрешённой политике, push и чтение удалённой
  ссылки;
- `gh` — изменения GitHub текущей задачи: создание/обновление PR, Draft/Ready и
  разрешённый merge;
- GitHub MCP/коннектор — предпочтительное структурированное чтение удалённого
  состояния GitHub, когда он доступен и реально удобнее;
- `gh ... --json` — допустимый запасной вариант и короткая проверка состояния.

Версионно-зависимые операции не описываются как вечный контракт: конкретную
версию `gh`, имена полей и флаги проверяй по фактическому интерфейсу установленного
инструмента там, где это действительно нужно, а не по памяти и не по тексту этого
skill.

## Инварианты

- Одна самостоятельная задача — одна рабочая ветка и один PR.
- Не работай напрямую в ветке по умолчанию. Ветки не переключаются молча.
- Не считай локальный commit доказательством публикации.
- Не считай код возврата push доказательством удалённого конечного состояния без
  чтения фактической удалённой ссылки.
- Разрешение на commit и push не разрешает merge.
- Не создавай дублирующий PR для того же репозитория/base/head.
- Не хардкодь номер PR, имя ветки, SHA, номер этапа, абсолютные локальные пути
  и имя пользователя: ни в этом skill, ни в его справочных документах.
- Не подмешивай и не уничтожай неизвестные пользовательские изменения.
- Merge, force-push, переписывание опубликованной истории и удаление неизвестных
  удалённых ветвей требуют отдельного явного основания в текущем запросе.
- Не ослабляй применимые проверки репозитория и не выдумывай фиктивные проверки
  ради зелёного результата.
- Не расширяй область ответственности skill инфраструктурой «на будущее».

## Подробный порядок действий

- [`references/publication.md`](references/publication.md) — ветка, подготовка
  индекса, commit, push, точная проверка удалённого состояния, протокол
  неизвестного результата сетевой операции и запрещённые операции публикации.
- [`references/pr-body.md`](references/pr-body.md) — содержательная структура
  описания PR, обязательные и условные разделы, формат таблицы результатов
  CodeRabbit и правила накопительного обновления описания.
- [`references/pr-lifecycle.md`](references/pr-lifecycle.md) — идентификация PR,
  источник файла описания внутри репозитория, создание/обновление и повторная
  проверка опубликованного PR, Ready, merge, конфликты с base и очистка.

Читай нужный справочный документ перед выполнением соответствующего шага:
`SKILL.md` задаёт контракт и границы, справочные документы владеют порядком действий.
