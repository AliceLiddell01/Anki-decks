# Anki-decks

Персональный репозиторий для хранения и ревью колод Anki, экспортированных через CrowdAnki в JSON.

## Структура

```text
.
├── AGENTS.md
├── Cargo.toml               # корневой Cargo workspace: владелец MSRV и edition
├── Cargo.lock
├── .github/
│   └── workflows/           # CI: форматирование, Clippy, тесты, MSRV, validate найденных экспортов
├── .agents/
│   └── skills/              # repository skills
├── .codex/
│   └── context/             # долговременный контекст для работы с колодами
├── decks/
│   └── japanese/
│       └── words/           # японская словарная колода CrowdAnki
└── tools/
    └── anki-repo/           # toolkit анализа, QA-review и точечной правки CrowdAnki-экспорта
```

Сами JSON-экспорты добавляются в соответствующие каталоги колод отдельными изменениями. В базовом каркасе репозитория содержимое колод намеренно отсутствует.

`decks/` — канонический корень пользовательских колод. Здесь важно не смешивать два разных инварианта:

- **Default-набор тестов независим от live payload.** Тесты строят собственные синтетические экспорты во временных каталогах и `decks/**` не читают: ни одна конкретная колода, уровень, note model, имя поля или media не является их fixture.
- **Repository CI валидирует live payload как данные репозитория.** Он рекурсивно находит все фактически присутствующие CrowdAnki-экспорты под `decks/**` и требует их структурной валидности, не зная конкретного layout и состава заранее. Структурно невалидный закоммиченный экспорт делает CI красным; отсутствие экспортов под `decks/**` ошибкой не является.

Ни workflow, ни тесты не перечисляют конкретные колоды, уровни, note models, имена полей и media: изменение, перемещение или временное отсутствие содержимого `decks/` не требует их правки. Независимость тестов от payload не отменяет второй инвариант — это разные вещи.

## Принцип работы

- CrowdAnki JSON хранится как версионируемый исходник колоды.
- Изменения содержимого колоды должны быть локальными и проверяемыми: не переписывать большой JSON целиком без необходимости.
- Перед правкой колоды агент читает `AGENTS.md` и `.codex/context/INDEX.md`, затем загружает только относящийся к задаче контекст.
- Идентификаторы CrowdAnki/Anki (`crowdanki_uuid`, `guid`, `note_model_uuid`, `deck_config_uuid`) сохраняются, если задача явно не требует миграции идентичности.
- После изменения JSON обязательно проверяется синтаксис и структурные инварианты колоды.

## Агентский контекст

`.codex/context/` содержит карту репозитория и краткую схему CrowdAnki JSON, чтобы агент не начинал каждую задачу с полного чтения многомегабайтного экспорта.

`.agents/skills/` содержит repository skills: по каталогу
`.agents/skills/<name>/SKILL.md` на skill. Процедуру каждого workflow владеет сам
skill, а не README.

## Инструменты

`tools/anki-repo` — самостоятельный Rust CLI для анализа одного CrowdAnki-экспорта, QA-review его содержимого и одной строго ограниченной правки. Он разрешает связи `note_model_uuid` → `note_models[].flds[].ord` → `Note.fields` и выполняет восемь операций: `inspect`, `find`, `stats`, `validate`, `qa`, `review`, `review-check` и `edit`. У каждой операции есть человекочитаемый вывод и отдельный стабильный JSON-вывод.

Toolkit работает с произвольным CrowdAnki-экспортом и не знает имён полей конкретной модели: имя поля всегда задаёт вызывающая сторона (`--field`), а `--value` и `--match` уточняют отбор.

```bash
cargo run --quiet --bin anki-repo -- validate <каталог-экспорта>
```

Семь команд только читают: они не пишут `deck.json`, не копируют media и не трогают настройки планировщика. Единственная мутирующая команда — `edit`: она меняет значения существующих полей существующих заметок, по умолчанию работает как dry-run и пишет только по явному `--apply`. Конвейер `qa` → `review` → `review-check` готовит проверенный запрос для `edit`, но сам ничего не пишет и не вызывает LLM API. Команды, контракт вывода и exit codes — `tools/anki-repo/README.md`.

## Проверки

Собирать и тестировать нужно из корня репозитория: там лежит Cargo workspace, который владеет заявленной MSRV (`rust-version`) и `Cargo.lock`.

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

То же самое выполняет CI в `.github/workflows/ci.yml`: job «Код и тесты» на стабильном тулчейне, он же проверяет `validate` для каждого найденного экспорта внутри `decks/`, и отдельный job «Заявленная MSRV», который берёт версию из корневого `Cargo.toml` через `cargo metadata` и проверяет сборку на ней. CI только читает репозиторий: без секретов, публикаций и записи в колоды. Ни одна колода, уровень, модель или поле не названы в workflow по имени — экспорты находятся поиском, а их отсутствие не является ошибкой. Напротив, структурно невалидный найденный экспорт валит этот шаг: валидность фактически закоммиченного payload под `decks/**` — обязательный repository gate.

Default-набор тестов самодостаточен: он строит собственные синтетические экспорты во временных каталогах и не требует ни одной конкретной колоды из `decks/`.

### Изменение публичного контракта

Флаг `find --word` / `review --word` и QA-правило `duplicate_primary_field` удалены осознанно. Оба опирались на понятие «главное поле» конкретной модели заметок, а у формата CrowdAnki такого понятия нет; корректной универсальной семантики для них не существует, а угадывать её по позиции поля или имени модели нельзя. Возможность не потеряна: отбор по значению поля выражается явно — `--field <имя поля> --value <значение> [--match exact|contains]`, а групповой QA-контракт принадлежит правилу `duplicate_note_content`.

## Медиа

CrowdAnki JSON может ссылаться на `.mp3`, `.png`, `.gif` и другие media-файлы через `media_files` и HTML-поля заметок. Политика хранения самих media-файлов в этом репозитории пока не определена и не должна предполагаться автоматически.
