# anki-repo

`anki-repo` — небольшой toolkit для детерминированного анализа одного
CrowdAnki-экспорта репозитория `Anki-decks` и одной строго ограниченной правки
его содержимого. Он даёт агенту быстрый и предсказуемый доступ к структуре
`deck.json`, не требуя читать многомегабайтный JSON вручную.

Семь команд — `inspect`, `find`, `stats`, `validate`, `qa`, `review`,
`review-check` — только читают. Восьмая, `edit`, меняет **значения** уже
существующих полей уже существующих заметок. Она не добавляет, не удаляет и не
перемещает заметки, поля, модели и колоды, не трогает `media/`, `guid`,
`note_model_uuid`, `crowdanki_uuid` и `deck_config_uuid`, и по умолчанию вообще
ничего не записывает: запись возможна только по явному `--apply`.

`qa`, `review` и `review-check` образуют конвейер внешней проверки содержимого
карточек: tool детерминированно находит проблемы, отдаёт по ним компактный batch,
принимает структурированные предложения внешнего агента и превращает их в готовый
запрос для `edit`. Сам tool при этом **не вызывает никаких LLM API** и не содержит
ни одного сетевого вызова: разбор содержимого делает внешний агент, а `anki-repo`
остаётся детерминированной границей репозитория.

## Зачем

- Один вызов вместо ручного `jq`/скрипта: `inspect`, `find`, `stats`, `validate`,
  `qa`, `review`, `review-check`, `edit`.
- Разрешение имён полей через `note_model_uuid` → `note_models[].flds[].ord`
  сосредоточено в одной реализации, поэтому агент не повторяет эту логику ни при
  чтении, ни при правке.
- Точечная правка, которая физически не может задеть остальной файл: проверки
  предусловий, dry-run по умолчанию и проверка байтового diff перед записью.
- Конвейер внешнего review, который не читает многомегабайтный `deck.json` целиком:
  детерминированный отбор, компактные страницы по 25 заметок и проверка
  предложений агента против фактического состояния экспорта.
- Стабильный machine-readable вывод: одинаковый JSON на одинаковых данных.
- Человекочитаемый вывод по умолчанию и отдельный JSON-режим для автоматизации.

## Требования

- Rust toolchain с edition 2024. Минимальная поддерживаемая версия (MSRV)
  объявлена один раз — в `[workspace.package] rust-version` корневого
  `Cargo.toml`; участники workspace наследуют её (`edition.workspace = true`,
  `rust-version.workspace = true`), поэтому отдельной копии версии в
  `tools/anki-repo/Cargo.toml` нет. Проверено на стабильном `rustc`/`cargo` и на
  заявленной MSRV.
- Единственная точка сборки — корневой Cargo workspace (`/Cargo.toml`, участник —
  `tools/anki-repo`); `Cargo.lock` тоже лежит в корне репозитория. Собирать и
  тестировать нужно из корня, а не из каталога crate'а.
- Никаких системных сервисов и сети: tool работает только с локальными файлами.
  Ни одна команда не обращается к LLM API или к любому другому внешнему сервису.

## Сборка и запуск

Из корня репозитория:

```bash
cargo build --release --workspace
./target/release/anki-repo --help

# или без установки
cargo run --quiet --bin anki-repo -- inspect decks/japanese/words/Words__N3
```

Пути к экспортам можно задавать и относительно текущего каталога, и абсолютно.

## Команды

Во всех примерах ниже `EXPORT` — каталог экспорта, например
`decks/japanese/words/Words__N3`. Указывать нужно именно каталог: путь к самому
`deck.json` отвергается с понятной ошибкой.

Пути и имена полей в примерах иллюстративны. Toolkit работает с произвольным
CrowdAnki-экспортом и не знает имён полей конкретной модели: `Слово`,
`Часть речи`, `Значение` и прочие имена, а также уровни и пути колод взяты из
текущих пользовательских колод только для наглядности и контрактом не являются.
Имя поля всегда называет вызывающая сторона, а сверяется оно с фактическими
`note_models[].flds[].name` того экспорта, с которым работает команда.

### `inspect`

Компактное описание структуры экспорта: корневая колода, число узлов колоды,
общее число заметок, модели заметок с их полями в порядке `ord`, конфигурации
колод, сводка по media и распределение заметок по путям колод.

```bash
anki-repo inspect decks/japanese/words/Words__N1
anki-repo inspect decks/japanese/words/Words__N1 --verbose
```

`--verbose` добавляет UUID, дерево колод в preorder, шаблоны карточек, статистику
по `guid` и bounded sample диагностики (в том числе примеры отсутствующих и
необъявленных media-имён). В JSON-режиме verbose-часть лежит в
`result.verbose` и появляется только при `--verbose`.

### `find`

Поиск заметок по стабильным критериям. Нужен ровно один критерий: `--guid` либо
`--field` вместе с `--value`.

```bash
# поиск по guid: identity lookup
anki-repo find decks/japanese/words/Words__N1 --guid 'D!TAYVuHi,'

# поиск по сырому значению поля: содержит подстроку
anki-repo find decks/japanese/words/Words__N1 --field Слово --value 偶然

# общий поиск по любому имени поля: подстрока и точное совпадение
anki-repo find decks/japanese/words/Words__N2 --field 'Часть речи' --value Существительное
anki-repo find decks/japanese/words/Words__N1 --field 'Часть речи' --value Существительное --match exact
```

Поведение:

- `--field` задаёт имя поля, `--match` принимает `contains` (по умолчанию) или
  `exact` и применяется только вместе с `--field`. Имя поля проверяется против
  фактических `note_models[].flds[].name` экспорта: неизвестное поле — доменная
  ошибка `unknown_field` (exit code 3), а не пустой ответ.
- Отбора по «слову» как отдельной сущности у команды нет: имя поля всегда
  называет вызывающая сторона, поэтому `--field X --value Y --match contains`
  выражает ровно то же, что раньше выражал удалённый флаг `--word` (см.
  «Изменения публичного контракта»).
- `--deck` ограничивает поиск колодой и всеми её вложенными колодами.
- `--limit` (по умолчанию 20, максимум 500) ограничивает размер вывода, но не
  сам поиск: `matched_total` считает все совпадения, а `returned`/`truncated`
  показывают, что именно попало в ответ.
- Сопоставление чувствительно к регистру и выполняется по сырым значениям поля,
  без нормализации HTML.

### `stats`

Структурная агрегированная статистика: число заметок по колодам, по моделям,
использование конфигураций, разбивка полей на пустые и непустые, сводка по
media.

```bash
anki-repo stats decks/japanese/words/Words__N3
anki-repo stats decks/japanese/words/Words__N3 --group-by 'Часть речи' --top 10
```

- `--group-by` считает распределение по сырым значениям указанного поля; `--top`
  (по умолчанию 20, максимум 500) ограничивает размер вывода, а
  `distinct_values` и `truncated` показывают полную картину.
- Столбцы распределения сортируются по убыванию количества, затем по значению.

### `validate`

Детерминированная проверка структурной целостности одного экспорта.

```bash
anki-repo validate decks/japanese/words/Words__N1
anki-repo --json validate decks/japanese/words/Words__N1
```

`valid` равно `true`, если не найдено ни одного issue уровня `ERROR`.
Предупреждения (`WARNING`) и информационные отметки (`INFO`) не делают экспорт
невалидным. Path-проблемы (нет каталога, нет `deck.json`) — это доменная ошибка
с exit code 3, а проблемы содержимого (включая невалидный JSON) — это issues с
exit code 6.

Уровни и коды issue:

| Уровень | Коды |
|---|---|
| `ERROR` | `invalid_json`, `root_not_deck`, `schema_invalid`, `node_not_deck`, `duplicate_note_model_uuid`, `duplicate_deck_config_uuid`, `note_model_identity_missing`, `deck_config_identity_missing`, `note_model_uuid_missing`, `note_model_unresolved`, `deck_config_unresolved`, `note_fields_count_mismatch`, `note_field_value_not_string`, `note_guid_missing`, `duplicate_note_guid`, `field_name_duplicate`, `field_ord_invalid`, `field_ord_negative`, `field_ord_duplicate`, `field_ord_out_of_range`, `field_ord_gap`, `template_field_unresolved` |
| `WARNING` | `media_reference_undeclared`, `media_files_duplicate`, `media_physical_missing`, `media_dir_missing`, `media_name_not_basename`, `template_construct_unchecked`, `deck_config_uuid_missing`, `deck_name_missing`, `conflicting_note_model_definition`, `conflicting_deck_config_definition`, `template_ord_invalid`, `template_ord_duplicate` |
| `INFO` | `export_summary`, `media_physical_unused`, `note_model_unused`, `deck_config_unused`, `empty_field_values`, `issues_truncated` |

Соглашения, важные для интерпретации результата:

- Отсутствующий физически media-файл — это `WARNING`, а не `ERROR`: политика
  хранения media в репозитории отдельно не определена.
- Имена media сравниваются только по basename; пути из `media_files` никогда не
  используются для доступа к файловой системе.
- Повторное объявление одной и той же модели/конфигурации с тем же определением
  (обычная ситуация во вложенных узлах CrowdAnki) не считается ошибкой; конфликт
  разных определений под одним UUID — это `WARNING`. Сравниваются только
  смысловые части объявления: для модели — `name` и список `flds` (`name` + `ord`),
  для конфигурации — `name`. Различия в `tmpls`, `css` и параметрах
  планировщика эта проверка не сравнивает.
- Ограниченный парсер шаблонов проверяет только простые ссылки вида
  `{{Поле}}` и `{{tts ja_JP:Поле}}`: если хотя бы один сегмент конструкции
  совпадает с именем поля модели, ссылка считается известной. Незакрытый `{{`, а
  также конструкции с фильтрами, в которых не найдено ни одного известного
  имени, помечаются как `template_construct_unchecked` (`WARNING`), чтобы не
  выдавать ложных ошибок. Парность секций `{{#X}}`/`{{/X}}` и прочая логика
  шаблонов не проверяются.
- Число issues одного кода ограничено; при усечении добавляется
  `issues_truncated` с числом опущенных записей.
- Пустой `guid` — это `note_guid_missing` (`ERROR`); как дубликат он не
  репортится и в индекс `guid` не попадает, поэтому `find --guid ''` ничего не
  находит.

### `qa`

Детерминированные findings по содержимому карточек. Правила не обращаются ни к
чему, кроме самого экспорта, и не зависят от текущего состояния репозитория.

```bash
anki-repo qa decks/japanese/words/Words__N1
anki-repo qa decks/japanese/words/Words__N3 --code empty_field_value --max-per-code 5
anki-repo --json qa decks/japanese/words/Words__N5 > findings.json
```

Реестр правил (порядок вывода findings — это порядок реестра, он же порядок
`rules` в JSON):

| Код | Уровень | Что находит |
|---|---|---|
| `empty_field_value` | `warning` | строковое значение поля равно `""` |
| `leading_whitespace` | `warning` | значение начинается с пробельного символа |
| `trailing_whitespace` | `warning` | значение заканчивается пробельным символом |
| `forbidden_white_span` | `error` | `<span>` с белым цветом текста в `style` |
| `duplicate_note_content` | `warning` | несколько заметок одной модели с полностью совпадающим содержимым |

Поведение:

- `--code` можно повторять: вывод ограничивается указанными кодами. Неизвестный
  код — доменная ошибка `unknown_qa_code` (exit code 3), а не пустой ответ:
  опечатка не должна выглядеть как «проблем нет».
- `--max-per-code` (по умолчанию 20, максимум 200) ограничивает число findings
  одного кода в выводе, но не сами подсчёты: `findings_total` и `by_code`
  описывают все findings выбранных кодов, а `truncated` показывает, осталось ли
  что-то за пределами вывода. `rules[].findings` при этом не фильтруется
  аргументами и всегда считает весь экспорт по всем правилам.
- Уровень `error` — это тяжесть проблемы для читателя, а не отказ: `qa` завершается
  с кодом `0` и при найденных `error`-findings.
- Значение поля из одних пробельных символов даёт сразу два finding:
  `leading_whitespace` и `trailing_whitespace`.
- Пустое значение — это не «отсутствующее»: finding получают и `""`, и строка из
  пробелов; `null` и нестроковое значение не считаются пустым полем (это предмет
  `validate`).
- `duplicate_note_content` сравнивает полный набор сырых полей заметки по позициям
  для одной и той же модели, без нормализации HTML и пробелов. Правило не выделяет
  «главное» поле: понятие главного поля принадлежит конкретной модели заметок, а не
  формату CrowdAnki, поэтому у toolkit'а нет корректной универсальной семантики для
  него. Разделить заметки по значению выбранного поля агент может явным
  `--field`/`--value` в `find` и `review`, где имя поля называет вызывающая сторона.
- Реестр состоит ровно из этих пяти кодов. Правило `duplicate_primary_field`
  удалено осознанно, вместе с ним ушло и понятие «поля `Слово`» из реестра QA (см.
  «Изменения публичного контракта»); попытка запросить удалённый код — доменная
  ошибка `unknown_qa_code`, а не пустой ответ.
- Ни одно правило не зависит от имён полей и моделей: одинаковый набор значений
  под другими именами полей и другой моделью даёт тот же набор findings.
- Findings никогда не делают экспорт структурно невалидным и не блокируют `edit`.
  Шкала `error | warning | info` — это тяжесть дефекта для читателя, независимая от
  шкалы `validate`: QA `error` не является ошибкой структуры экспорта.
- Finding может попасть в заметку, которую нельзя исполнить: у неё не разрешается
  модель, нет `guid` или `guid` не уникален. Такие findings **помечаются**
  `addressable: false` и считаются в `unaddressable_findings`, а не исчезают:
  структурную причину называет `validate`, а `qa` не выдаёт неисполнимый адрес за
  обычную цель `edit`.
- Правила-дубликаты описывают группу целиком: `group_size` — число участников,
  `related_note_indices` и `related_guids` — участники группы в каноническом
  порядке findings, причём владелец finding входит в список (`review` в своём
  `related` владельца наоборот исключает). Список ограничен 20 участниками
  (`MAX_RELATED_NOTES`), и тогда `related_truncated: true`: группа никогда не
  обрезается молча.

Каждый finding адресуется позицией заметки в экспорте (`note_index`), `guid`,
путём колоды, моделью и парой «имя поля + `ord`», а `evidence` несёт ограниченные
выборки: длину значения, усечённый образец и детали конкретного правила
(например, `boundary` для пробельных правил и `first_tag` для `forbidden_white_span`).
Данные группы в `evidence` не дублируются: они лежат в полях `group_size`,
`related_note_indices` и `related_guids`.

### `review`

Компактный bounded batch заметок для внешнего review. В отличие от `qa`, который
описывает проблемы, `review` отдаёт то, что нужно прочитать и обдумать: поля
заметки в порядке `ord` и уже найденные по ней QA-findings.

```bash
# отобрать заметки по найденной проблеме
anki-repo review decks/japanese/words/Words__N1 --qa-code empty_field_value --limit 25

# следующая страница
anki-repo review decks/japanese/words/Words__N1 --qa-code empty_field_value --offset 25

# выбор по содержимому и точный lookup
anki-repo review decks/japanese/words/Words__N2 --field 'Часть речи' --value Существительное
anki-repo review decks/japanese/words/Words__N1 --guid 'D!TAYVuHi,'
```

Ровно один критерий отбора обязателен:

| Критерий | Значение |
|---|---|
| `--all` | все заметки области |
| `--guid` | одна заметка по `guid` |
| `--field` + `--value` | сопоставление по имени поля; `--match contains` (по умолчанию) или `exact` |
| `--qa-code` | заметки с finding указанного кода QA |

`--deck` ограничивает область колодой и её вложенными колодами, `--offset`
пропускает выбранные заметки, `--limit` (по умолчанию 25, максимум 200) задаёт
размер страницы. В ответе есть `total_selected`, `returned`, `truncated` и
`next_offset`; `next_offset` равен `null` на последней странице. Отбор и
разрешение имён полей — та же реализация, что у `find`, поэтому неизвестное поле,
неизвестная колода или неизвестный `guid` дают те же ошибки и те же exit codes.

`review` — команда чтения и пагинации, а не поиска «хоть чего-нибудь»: пустая
страница (фильтр без совпадений или `--offset` за концом выборки) — это успешный
ответ с `returned: 0` и exit code `0`, иначе пагинация не могла бы завершаться.
Исключение — `--guid`: он адресует конкретную заметку, поэтому её отсутствие
остаётся ошибкой `not_found` (exit code 4), а неоднозначный `guid` — `ambiguous`
(exit code 5).

Что попадает в batch:

- Заметки без исполнимо адресуемого `guid` в batch не выводятся: без `guid`, с
  пустым `guid` или с `guid`, встречающимся больше одного раза (адрес неоднозначен,
  поэтому исключаются **все** такие вхождения). Их число видно в
  `excluded_unaddressable`; `notes_total` при этом описывает экспорт целиком, а не
  страницу. Пустая страница из-за этого исключения не молчит: счётчик объясняет
  причину.
- `--qa-code` для правил-дубликатов приводит участников группы, а не только
  владельца finding: иначе группа потеряла бы остальных заметок на пути
  `qa → review`. Владелец несёт сам finding (с `group_size` и `related` —
  участниками, кроме себя), а каждый участник — `group_membership` со ссылкой на
  владельца (`code`, `owner_note_index`, `owner_guid`, `group_size`).
  Список участников приходит из domain-результата и ограничен
  `MAX_RELATED_NOTES` (20): в группе из 30 заметок batch получит владельца и 20
  участников, а `related_truncated: true` в finding'е владельца покажет, что
  список неполон. Обещать «всех участников» для группы больше предела нельзя:
  чтобы увидеть остальных, нужен отдельный обход (`review --all` или `--field`).
- `--all`, `--guid`, `--field` и `--qa-code` группы не расширяют: они отбирают ровно
  то, что означает их критерий.

### `review-check`

Проверка предложений внешнего агента против **текущего** состояния экспорта.
Команда только читает: она не пишет ни `deck.json`, ни вспомогательных файлов.

```bash
# проверить предложения и получить готовый запрос для `edit`
anki-repo --json review-check decks/japanese/words/Words__N1 \
  --proposals proposals.json | jq .result.edit_request > request.json

# то же со stdin
anki-repo review-check decks/japanese/words/Words__N1 --proposals - < proposals.json

# готовый запрос уходит в существующую границу записи
anki-repo edit decks/japanese/words/Words__N1 --request request.json
anki-repo edit decks/japanese/words/Words__N1 --request request.json --apply
anki-repo validate decks/japanese/words/Words__N1
```

У команды собственный versioned документ предложений, а не запрос `edit`:

```json
{
  "schema_version": 1,
  "proposals": [
    {
      "proposal_id": "p0",
      "guid": "guid-1",
      "field": "Пример",
      "expected": "",
      "replacement": "пример-1",
      "reason": "в колоде пустой пример"
    }
  ]
}
```

`proposal_id` и `reason` — часть контракта предложения: первый становится
`edit_id` в выпущенном запросе, второй остаётся review-метаданными (в отчёте он
усечён до безопасной длины, а в `edit_request` не переносится вовсе). Неизвестные
ключи запрещены: документ предложений — отдельный публичный вход, поэтому он не
принимает поля чужой формы, а ошибки называют именно его словарь. `review-check`
переиспользует внутренний разбор и разрешение целей `edit`, поэтому выпущенный
`edit_request` принимается `edit` без переупаковки.

Исход предложения:

| Статус | Условие | Попадает в `edit_request` |
|---|---|---|
| `valid` | цель разрешается, текущее значение равно `expected` и отличается от `replacement` | да |
| `already_correct` | текущее значение равно и `expected`, и `replacement` | нет |
| `already_applied` | текущее значение уже равно `replacement` | нет |
| `conflict` | текущее значение не совпало ни с `expected`, ни с `replacement` | нет |
| `invalid` | цель не разрешается: нет заметки, нет поля, поле не редактируется как строка, `guid` неоднозначен | нет |

`problem` для `invalid`-предложений называется по существу проверки:
`note_not_found`, `unknown_field`, `ambiguous_guid`, `field_not_resolvable`.
Последние два случая `edit` для той же цели описывает общим кодом
`internal_error` и прекращает работу целиком; `review-check` этого не повторяет —
неразрешимая цель здесь неисполнимое предложение в отчёте, а не внутренняя ошибка
инструмента, и остальные предложения всё равно проверяются.

Итог и exit code:

| `outcome` | Условие | Exit |
|---|---|---|
| `ok` | нет ни одного `invalid` и ни одного `conflict` | `0` |
| `stale` | есть хотя бы один `conflict`: представление агента устарело | `7` |
| `invalid` | есть хотя бы один `invalid`; при неоднозначном `guid` — `5`, иначе при отсутствующей заметке — `4`, иначе `3` | `5` / `4` / `3` |

`edit_request` присутствует только при `outcome: ok`, хотя бы одном `valid`
предложении и правимом исходнике (`source_editable: true`): пустой `edits`
нарушил бы контракт `edit`, а запрос, собранный из частично неверного документа,
был бы молчаливой правкой «чего получилось». `expected` в выпущенном запросе
переносится из предложения агента, и это безопасно: статус `valid` получают
только предложения, чей `expected` уже совпал с фактическим текущим значением.

Поэтому `review-check` проверяет ещё и сам исходник — ровно теми же условиями,
на которых останавливается `edit` (общая функция, а не вторая реализация):

| Блокер | Код в `source_blockers` | Exit |
|---|---|---|
| `deck.json` не в канонической форме | `source_not_canonical` | `3` |
| в экспорте есть `ERROR` | `export_invalid` | `6` |
| неоднозначный порядок полей модели (`WARNING conflicting_note_model_definition`) | `export_not_mutable` | `6` |

Отчёт по предложениям в этом случае всё равно печатается: статусы, счётчики и
`proposals` остаются полезными агенту, а `source_editable: false` и
`source_blockers` объясняют, почему запрос не выпущен. Код возврата при этом
называет причину блокировки — неправимый исходник делает неисполнимым любой
запрос, и принимать такой `ok` за готовность к записи нельзя.

`stale` и `invalid` — это результат проверки, а не отказ команды, поэтому и в
обычном, и в JSON-режиме отчёт формируется полностью (в JSON он лежит в
`result`, а не в `error`), и только exit code сигнализирует о ненулевом исходе.
Так же ведёт себя `validate` с exit code 6.

Отчёт ограничен (`proposals` — до 50 записей, `proposals_truncated`), но счётчики
`counts` и сам `edit_request` не усекаются: усечение затрагивает только печать, и
человеческий вывод говорит об этом прямо, не обещая «полного списка в `--json`».

Проблемы уровня всего документа остаются доменными ошибками с exit code 3 (пока
документ не разобран, проверять нечего). Собственный словарь предложений даёт
`invalid_request` с `details.reason`: `malformed_proposals` (структурно
некорректный или чужая форма), `unsupported_schema_version`, `empty_proposals`,
`too_many_proposals` (больше 20 000), `proposals_too_large` (больше 8 МиБ) и
`duplicate_proposal_id`. Проверки, общие с запросом `edit`
(`edit::validate_request`), добавляют к ним `empty_guid` и `empty_field`, а повтор
пары «`guid`, поле» — это отдельный код `duplicate_edit_target`, а не `reason`
внутри `invalid_request`.

### Типовой конвейер

```bash
EXPORT=decks/japanese/words/Words__N1

# 1. что вообще есть в экспорте
anki-repo qa "$EXPORT"

# 2. компактный batch по найденной проблеме
anki-repo --json review "$EXPORT" --qa-code empty_field_value --limit 25 > batch.json

# 3. внешний агент читает batch.json и возвращает документ предложений
#    (schema_version, proposals: proposal_id, guid, field, expected, replacement)

# 4. проверка предложений против текущего состояния экспорта
anki-repo --json review-check "$EXPORT" --proposals proposals.json \
  | jq .result.edit_request > request.json

# 5. dry-run, запись и проверка результата — существующими командами
anki-repo edit "$EXPORT" --request request.json
anki-repo edit "$EXPORT" --request request.json --apply
anki-repo validate "$EXPORT"
```

Разделение ответственности в этом конвейере осознанное: `qa` и `review`
детерминированно выбирают материал, внешний агент предлагает содержательную
правку, `review-check` проверяет предложение против факта, а `edit` остаётся
единственным владельцем записи в `deck.json`.

#### Отчёты в JSON-режиме

| Команда | Ключи `result` |
|---|---|
| `qa` | `export_dir`, `notes_total`, `findings_total`, `findings_returned`, `unaddressable_findings`, `truncated`, `max_per_code`, `codes`, `by_code`, `rules`, `findings` |
| `review` | `export_dir`, `selection`, `notes_total`, `total_selected`, `excluded_unaddressable`, `offset`, `limit`, `returned`, `truncated`, `next_offset`, `items` |
| `review-check` | `export_dir`, `deck_json`, `outcome`, `proposals_total`, `counts`, `effective_proposals`, `proposals_truncated`, `source_editable`, `source_blockers`, `proposals`, `edit_request` |

В `items` команды `review` поля заметки лежат в `fields` — объекте в порядке `ord`
модели, как и в `find`. В `findings` команды `qa` поле `field_ord` равно `null`
для правил, которые не привязаны к конкретной позиции поля. Поля адресуемости
(`addressable` в `qa`, `excluded_unaddressable` в `review`) и контекста группы
(`group_size`, `related_note_indices`/`related_guids` в `qa`; `group_membership`,
`related`, `group_size`, `related_truncated` в `review`) присутствуют всегда, в том
числе когда группа не найдена и счётчики равны нулю.

### `edit`

Единственная мутирующая команда. Её предмет — значение одного поля одной уже
существующей заметки. Правка адресуется парой «`guid` заметки, имя поля»: `guid`
ищется в экспорте, имя поля разрешается через `note_model_uuid` заметки и
`note_models[].flds[].ord`, а записывается результат в `fields[ord]`.

Без флага `--apply` команда работает как **dry-run**: она полностью вычисляет
будущий файл и все проверки, но не пишет его. С `--apply` файл заменяется
атомарно и только тогда, когда все проверки прошли.

```bash
# одиночная правка: dry-run
anki-repo edit decks/japanese/words/Words__N1 \
  --guid 'D!TAYVuHi,' --field 'Значение' --expect 'было' --set 'стало'

# та же правка с записью
anki-repo edit decks/japanese/words/Words__N1 \
  --guid 'D!TAYVuHi,' --field 'Значение' --expect 'было' --set 'стало' --apply

# пакетная правка из файла запроса
anki-repo edit decks/japanese/words/Words__N1 --request edits.json --apply

# пакетная правка со stdin
anki-repo edit decks/japanese/words/Words__N1 --request - --apply < edits.json
```

Одиночная правка задаётся флагами `--guid`, `--field`, `--expect` и `--set`; все
четыре обязательны и указываются вместе. Пакетная правка задаётся ровно одним
`--request`: либо путь к JSON-файлу, либо `-` для чтения запроса со stdin.
Одновременно указать и `--request`, и `--guid` нельзя.

`guid`, имя поля и значения в примерах выше иллюстративны: `--expect` — не
подсказка, а предусловие, поэтому в реальном запуске он должен совпадать с
фактическим текущим значением поля. Если фактическое значение поля не совпало с
ожидаемым, правка **не выполняется** целиком (в пакете не применяется ни одна из
конфликтующих правок). Это защищает от правки по устаревшему представлению о
содержимом.

#### Формат запроса

```json
{
  "schema_version": 1,
  "edits": [
    {
      "edit_id": "необязательный идентификатор для отчёта",
      "guid": "D!TAYVuHi,",
      "field": "Значение",
      "expected": "было",
      "replacement": "стало"
    }
  ]
}
```

- `schema_version` обязателен и должен быть равен `1`; неизвестная версия
  отвергается.
- `edits` содержит от 1 до 20000 правок; сам файл запроса — не больше 8 МиБ.
- `edit_id` необязателен, но если указан, то не может повторяться.
- Пара «`guid`, `field`» не может повторяться в одном запросе: порядок
  применения к одному и тому же значению был бы неоднозначным.
- Неизвестные ключи в запросе отвергаются: опечатка в имени поля запроса должна
  быть видна сразу, а не молча проигнорирована.

#### Четыре исхода каждой правки

| Статус | Условие | Запись |
|---|---|---|
| `noop_identical` | текущее значение равно и `expected`, и `replacement` | не нужна |
| `applied` | текущее равно `expected`, отличается от `replacement` | выполнена |
| `dry_run` | то же, но без `--apply` | не выполнена |
| `already_applied` | текущее уже равно `replacement` | не нужна |

`already_applied` и `noop_identical` — успешные исходы, а не ошибки: повторный
запуск той же команды с `--apply` завершается с кодом `0` и не перезаписывает
файл (его `mtime` не меняется). Если все правки оказались безрезультатными,
`applied` в отчёте равно `false`.

Четвёртый случай — текущее значение не совпало ни с `expected`, ни с
`replacement` — это конфликт предусловия: код `expected_mismatch` и exit code 7.
Ни одна правка из пакета в этом случае не применяется; в отчёте перечислены все
конфликты с выборками ожидаемого и фактического значения.

#### Что гарантируется

Правка возможна только для `deck.json`, который уже находится в канонической
форме этого репозитория (LF, отступ 4 пробела, ключи в алфавитном порядке,
non-ASCII без `\u`-экранирования, без завершающего перевода строки). Проверка
строгая: исходник сравнивается побайтово с собственным рендером tool
(`serde_json` с `PrettyFormatter` и отступом 4 пробела), поэтому важны и следствия
этого рендера — формат чисел (`1e3` записывается как `1000.0`), короткие
экранирования управляющих символов `\b`, `\f`, `\n`, `\r`, `\t`, `\uXXXX` для
остальных символов U+0000–U+001F. Это не
косметическое требование: каноническая перезапись документа побайтово совпадает с
источником везде, кроме изменённого значения, поэтому правка не может переписать
остальной файл. Исходник в другой форме (компактный JSON, отступ 2 пробела, CRLF,
завершающий перевод строки) отвергается с кодом `source_not_canonical` и exit
code 3, а не «нормализуется» молча.

Перед записью проверяется:

- исходник действительно каноничен (иначе — `source_not_canonical`);
- в экспорте нет ни одного `ERROR` (`export_invalid`), а также нет
  `conflicting_note_model_definition` (`export_not_mutable`), потому что при
  конфликте определений модели имя поля перестаёт быть однозначным;
- заметки в JSON-дереве и в типизированном дереве совпадают по позициям, `guid` и
  `note_model_uuid` — иначе правка адресовала бы не тот `fields[ord]`;
- все цели разрешаются: `guid` найден ровно один раз, поле есть в модели именно
  этой заметки;
- повторный разбор кандидата даёт ровно запланированное значение;
- байтовый diff содержит ровно запрошенный набор изменений: число различных
  строк файла равно числу эффективных правок, каждая различимая строка содержит
  ровно один строковый токен, а мультимножество пар «было → стало» совпадает с
  запросом;
- прирост размера файла объясняется длиной заменённых токенов, включая
  экранирование;
- валидация кандидата не добавляет ни одного нового `ERROR` (новые `WARNING` и
  `INFO` допускаются и показываются в отчёте);
- замена файла атомарна: кандидат записывается во временный файл в том же
  каталоге, сбрасывается на диск и переименовывается поверх `deck.json` с
  сохранением прав доступа. При любой ошибке временный файл удаляется, а
  исходный `deck.json` остаётся нетронутым.

Все эти проверки — внутренние инварианты: их нарушение означает ошибку в самом
tool, поэтому завершается кодом `internal_error` (70) без записи.

#### Конкурентные запуски `--apply`

Сравнение исходника с публикацией кандидата выполняются как одна критическая
секция: перед проверкой байтов `deck.json` берётся эксклюзивная advisory-
блокировка самого целевого файла, и она удерживается до конца `rename`. Отдельные
`read → compare → rename` такой гарантии не дают: между сравнением и `rename`
другой writer успевает опубликовать более новый результат, который затем молча
затирается.

Что это значит практически:

- два одновременных `anki-repo edit --apply` одного экспорта сериализуются:
  writer'ы выстраиваются в очередь, а проигравший проверяет байты уже под
  блокировкой и получает `source_changed` (exit code `7`) вместо молчаливой
  перезаписи. Чтобы потерять результат молча, отставшему writer'у нужно увидеть
  в файле ровно свой снимок, поэтому обычная конкурентная правка этого не даёт;
- у блокировки есть узкая оговорка, действующая и между процессами `anki-repo`:
  она берётся на дескриптор, открытый по пути, поэтому `rename` поверх
  `deck.json` между `open` и `flock` оставляет блокировку на прежнем inode. Окно
  измеряется одним syscall'ом, повторные проверки его только сужают, а снимает
  полностью лишь блокировка отдельного, не переименовываемого файла;
- блокировка снимается ядром при завершении процесса, поэтому падение
  `anki-repo` не оставляет «залипший» лок;
- ожидание освобождения блокировки блокирующее: процесс не отказывается сразу, а
  дожидается своей очереди. Это осознанно — вместо произвольного отказа захвата
  writer получает доменный ответ `source_changed`;
- гарантия действует между процессами `anki-repo`. Произвольный внешний writer,
  который эту блокировку не соблюдает, обнаруживается только сравнением байтов
  под блокировкой: изменение, попавшее в файл до сравнения, отклоняется
  (`source_changed`), но изменение, случившееся между сравнением и `rename`,
  portable-средствами `std` не перехватывается. Обещать для такого writer'а
  большее нельзя;
- на платформах, где межпроцессной blocking-блокировки нет, публикация
  отклоняется с `write_failed` (exit code `8`), а не выдаётся за защищённую.

#### Ограничения правки

- Меняются только значения полей; `fields` не может стать короче или длиннее.
- Нельзя править `guid`, `note_model_uuid`, `tags`, `media_files`, модели,
  конфигурации и дерево колод: для них нет ни одного аргумента команды.
- `media/` не читается и не изменяется, поэтому переименование media-файла и
  синхронная правка ссылок на него — не одна команда, а две отдельные задачи.
- Один вызов работает с одним экспортом.

#### Отчёт

Человекочитаемый отчёт содержит режим, размеры до и после, число изменённых
строк, статус каждой правки с выборками старого и нового значения, результаты
проверок и сравнение валидации до и после. В JSON-режиме `result` содержит:

| Ключ | Значение |
|---|---|
| `export_dir`, `deck_json` | путь к экспорту и к `deck.json` |
| `dry_run`, `applied` | режим и факт замены файла |
| `source_bytes`, `candidate_bytes`, `byte_delta` | размеры и их разница |
| `changed_lines`, `first_changed_line` | сколько строк файла изменилось и первая из них |
| `edits_total`, `effective_edits` | сколько правок запрошено и сколько меняет значение |
| `summaries` | счётчики по статусам |
| `outcomes` | отчёт по правкам (до 50 записей) и `outcomes_truncated` |
| `validation` | счётчики и новые коды до/после |
| `checks` | результаты пяти обязательных проверок |

## Изменения публичного контракта

Две сущности удалены из toolkit'а осознанно: их семантику задавала одна конкретная
модель заметок, поэтому они превращали состав текущих пользовательских колод в
вечный контракт toolkit'а. Toolkit работает с произвольным CrowdAnki-экспортом и не
знает имён полей конкретной модели.

- Флаг `--word` у `find` и `review` удалён. Он был сокращением для «содержит по
  сырому значению поля `Слово`», то есть единственным содержанием флага было имя
  поля одной модели. Возможность не потеряна и выражается явно:
  `--field <имя поля> --value <значение> --match contains` — ровно та же
  семантика, но имя поля называет вызывающая сторона.
- QA-правило `duplicate_primary_field` удалено. Понятие «главного/головного» поля
  принадлежит конкретной модели заметок, а не формату CrowdAnki, поэтому у toolkit'а
  нет корректной универсальной семантики такого поля. Реестр правил состоит ровно из
  пяти кодов (`empty_field_value`, `leading_whitespace`, `trailing_whitespace`,
  `forbidden_white_span`, `duplicate_note_content`), а групповой контракт —
  `related`, `group_size`, `related_truncated` — принадлежит
  `duplicate_note_content`.
- Публичная константа `PRIMARY_FIELD` из модуля `selection` удалена вместе с ними:
  модуль больше не знает имён полей конкретных моделей, имя поля всегда задаёт
  вызывающая сторона, а сверку с фактическими `note_models[].flds[].name` выполняет
  `ensure_known_field` (доменная ошибка `unknown_field`, exit code 3).

Снятые контракты не возвращаются незаметно: `qa --code duplicate_primary_field` и
`find`/`review --word` отвергаются как неизвестный код или неизвестный аргумент, и
это зафиксировано негативными тестами в `tests/cli_contract.rs` и
`tests/qa_contract.rs`.

## Режимы вывода

- Обычный режим: человекочитаемый текст на русском языке в `stdout`. Длинные
  значения полей приводятся к одной строке и ограничиваются по длине.
- `--json` (можно указывать до или после подкоманды): ровно один JSON-документ
  в `stdout`, ничего в `stderr`.
- Исключение: ошибки разбора аргументов, которые отлавливает сам clap
  (неизвестный флаг, несовместимая комбинация, значение вне диапазона), он
  печатает текстом в `stderr` и завершает процесс с кодом 2 — JSON-конверт в
  этом случае не формируется, потому что команда ещё не определена.

Успешный ответ:

```json
{
  "schema_version": 1,
  "command": "inspect",
  "result": { }
}
```

Ошибка:

```json
{
  "schema_version": 1,
  "command": "find",
  "error": {
    "code": "not_found",
    "message": "по заданному критерию не найдено ни одной заметки",
    "details": { }
  }
}
```

`schema_version` описывает контракт вывода; `code` — стабильный snake_case
идентификатор, не зависящий от имён внутренних типов Rust.

В JSON-режиме поля заметки представлены объектом, ключи которого идут в порядке
`ord` модели. Если модель повреждена и содержит повторяющиеся имена полей, к
повторному ключу добавляется суффикс `#N`, чтобы объект оставался однозначным.

## Exit codes

| Код | Значение |
|---|---|
| `0` | Успех |
| `1` | Зарезервировано |
| `2` | Ошибка использования CLI (неизвестный аргумент, несовместимая комбинация, значение вне диапазона) |
| `3` | Неверный ввод, из-за которого команда не может начать работу: нет каталога, передан не каталог, нет `deck.json`, `deck.json` не читается; для всех команд, которым нужен типизированный экспорт (`inspect`, `find`, `stats`, `qa`, `review`, `review-check`, `edit`), — также невалидный JSON (`invalid_json`), корень не `Deck` (`root_not_deck`) или несоответствие типизированному ядру (`schema_invalid`); для `find`, `review` и `qa` — ещё и неизвестное поле, колода или код QA в критерии, а для `review-check` — неразбираемый документ предложений или неканонический `deck.json` (`source_not_canonical`). `validate` сюда не входит: он читает и невалидный JSON, сообщая о нём issue'ами с exit code `6` |
| `4` | Совпадений не найдено: `find` не нашёл ни одной заметки по заданному критерию, `review --guid` не нашёл заметку с запрошенным `guid`, либо `edit` не нашёл такую заметку (`note_not_found`); для `review-check` — так же, если хотя бы одно предложение ссылается на несуществующую заметку и ни одно на неоднозначный `guid` |
| `5` | `find --guid` или `review --guid` нашёл несколько заметок с одним `guid`; для `review-check` — если среди `invalid`-предложений есть хотя бы одно с неоднозначным `guid` |
| `6` | `validate` нашёл хотя бы один `ERROR` issue, в том числе `invalid_json`, `root_not_deck` или `schema_invalid`; `edit` отказался править экспорт с `ERROR` или с неоднозначным определением модели. Повтор `guid` (`duplicate_note_guid`) — это `ERROR`, поэтому `edit` на таком экспорте завершается кодом `6`, а не `5`: проверка валидности исходника идёт раньше разрешения правки. `review-check` называет тот же блокер (`export_invalid` / `export_not_mutable`) и возвращает `6` вместо итогового кода отчёта — запрос он не выпускает |
| `7` | `edit` обнаружил конфликт предусловия: текущее значение поля не совпало с `expected` (`expected_mismatch`) либо `deck.json` изменился между проверкой и заменой файла (`source_changed`); `review-check` обнаружил хотя бы одно предложение со статусом `conflict` (`stale`) |
| `8` | `edit` не смог заменить `deck.json`: отказ файловой системы при записи кандидата |
| `70` | Неожиданная внутренняя ошибка, включая нарушение внутреннего инварианта правки и отказ записи вывода (нет места на диске, негодный дескриптор) |

Закрытый читателем pipe (например `anki-repo … | head`) внутренней ошибкой не
считается: результат команды уже вычислен, поэтому сохраняется её собственный
exit code.

Коды доменных ошибок (`error.code`) и их exit codes; проблемы содержимого в
`validate` (`invalid_json`, `root_not_deck`, `schema_invalid`) доменными ошибками
не являются и описаны в разделе `validate`:

| Код | Exit | Когда |
|---|---|---|
| `usage` | 2 | Несовместимые аргументы, обнаруженные вне clap |
| `input_unreadable` | 3 | Каталог экспорта недоступен, передан путь к файлу или не читается файл запроса (`edit`) либо документ предложений (`review-check`) |
| `deck_json_missing` | 3 | В каталоге нет `deck.json` |
| `invalid_json` | 3 | `deck.json` не является валидным JSON |
| `root_not_deck` | 3 | Корень не является CrowdAnki `Deck` |
| `schema_invalid` | 3 | JSON валиден, но не соответствует типизированному ядру |
| `unknown_field` | 3 | Указанного поля нет ни в одной модели экспорта; для `edit` — также если поля нет в модели целевой заметки |
| `unknown_deck` | 3 | Указанная колода не найдена |
| `unknown_qa_code` | 3 | Указанного кода QA нет в реестре правил (`qa --code`, `review --qa-code`) |
| `invalid_request` | 3 | `edit`: пустой, слишком большой или структурно некорректный документ запроса, повторяющийся `edit_id`, чужая `schema_version`, пустой `guid` (`empty_guid`) или пустое имя поля (`empty_field`); `review-check`: те же проблемы документа предложений — `details.reason` равен `malformed_proposals`, `unsupported_schema_version`, `empty_proposals`, `too_many_proposals`, `proposals_too_large`, `duplicate_proposal_id`, `empty_guid` или `empty_field` |
| `duplicate_edit_target` | 3 | `edit` и `review-check`: пара «`guid`, поле» запрошена дважды (отдельный код, а не `details.reason` внутри `invalid_request`) |
| `proposal_not_executable` (`details.reason`) | — | Не отдельный код: `review-check` сообщает о неисполнимом предложении статусом `invalid` внутри отчёта, а не ошибкой команды |
| `source_not_canonical` | 3 | `edit`: `deck.json` не в канонической форме; `review-check`: тот же блокер в `source_blockers`, запрос не выпущен |
| `export_invalid` | 6 | `edit`: в исходном экспорте есть `ERROR` (в том числе `duplicate_note_guid` — повтор `guid` делает адресацию правки неоднозначной); либо кандидат правки получил новый `ERROR` (проверка до записи). `review-check` называет этот блокер в `source_blockers` и возвращает `6` вместо итогового кода отчёта |
| `export_not_mutable` | 6 | `edit`: в экспорте есть `conflicting_note_model_definition`; `review-check` — тот же блокер в `source_blockers` |
| `expected_mismatch` | 7 | `edit`: текущее значение не совпало с `expected` |
| `source_changed` | 7 | `edit`: `deck.json` изменился (или исчез) между чтением исходника и заменой файла; правка отменена, файл не тронут |
| `write_failed` | 8 | `edit`: не удалось записать кандидат или заменить `deck.json` |
| `not_found` | 4 | `find` и `review --guid`: нет совпадений по заданному критерию |
| `note_not_found` | 4 | `edit`: в экспорте нет заметки с указанным `guid`; в отчёте `review-check` — код проблемы предложения (доменной ошибкой не является) |
| `ambiguous` | 5 | `find --guid` и `review --guid`: `guid` не разрешается однозначно. Для `edit` и `review-check` эта ветка недостижима как *код возврата*: повтор `guid` отсекается раньше как `export_invalid` (6), а в отчёте `review-check` он остаётся статусом предложения `invalid`/`ambiguous_guid` |
| `internal_error` | 70 | Внутренняя ошибка, включая нарушение байтового инварианта правки |

## Детерминированность

Одинаковые входные данные дают побайтово одинаковый вывод:

- узлы колод обходятся в preorder;
- заметки сохраняют порядок экспорта;
- поля модели выводятся в порядке `ord`;
- распределения сортируются по количеству (по убыванию), затем по значению;
- issues в `validate` сортируются по уровню, коду, пути колоды, месту и тексту;
- правки в `edit` разрешаются в порядке запроса, а канонический кандидат
  сериализуется тем же кодом, что и при проверке каноничности, поэтому одинаковый
  вход даёт побайтово одинаковый кандидат;
- findings в `qa` и `review` сортируются по позиции правила в реестре, затем по
  позиции заметки в экспорте, затем по `ord` поля и его имени; порядок не зависит
  от порядка обнаружения;
- предложения в `review-check` сохраняют порядок документа, а счётчики `counts` не
  зависят от того, попала ли конкретная запись в усечённый отчёт;
- при отказе правки `deck.json` не изменяется ни на байт.

## Ограничения

- Tool намеренно умеет работать только с одним экспортом за вызов.
- `edit` меняет только значения полей существующих заметок: структура экспорта,
  идентификаторы (`guid`, `crowdanki_uuid`, `note_model_uuid`,
  `deck_config_uuid`), `tags`, `media_files` и `media/` недоступны для правки.
- `edit` требует канонический `deck.json`; экспорт в другой форме нужно сначала
  привести к канонической форме отдельной задачей.
- `edit` не сливает и не переносит колоды, не создаёт и не удаляет заметки и не
  меняет модели карточек.
- Media не копируются и не сравниваются по содержимому: сравниваются только имена.
- Поиск не поддерживает регулярные выражения и не нормализует HTML.
- Toolkit не знает имён полей конкретной модели: поле всегда называет вызывающая
  сторона через `--field`, а имя проверяется против фактических
  `note_models[].flds[].name` экспорта. Снятый флаг `--word` и удалённое правило
  `duplicate_primary_field` не возвращаются (см. «Изменения публичного контракта»).
- Семантика `--deck` требует точного пути колоды, как он собран из `name` узлов.
- Tool не проверяет семантику японского содержимого и не сравнивает колоды между
  собой: `qa` находит только перечисленные структурные и форматные признаки, а
  содержательное суждение о карточке делает внешний агент.
- Tool не вызывает LLM и не ходит в сеть. Конвейер `qa`/`review`/`review-check`
  сознательно останавливается на границе репозитория: предложения приносит
  внешний агент, а `anki-repo` проверяет их и отдаёт готовый запрос для `edit`.
- Предложения принимаются только в форме, которую понимает `edit`: правка значения
  существующего поля существующей заметки. `qa` и `review` не предлагают
  добавление, удаление и переименование сущностей, а `review-check` их не примет.
- Усечение отчёта (лимит findings на код, страница `review`, предел правок и
  предложений) никогда не скрывает факт усечения: счётчики считают всё, а текст
  сообщает, что остаток не выводится ни в human-, ни в JSON-режиме.
- `review-check` проверяет предложение против текущего состояния экспорта, но не
  резервирует его: между проверкой и `edit --apply` содержимое может измениться, и
  тогда конфликт предусловия поймает уже `edit`.
- Неразрешимая цель предложения (`field_not_resolvable`, `ambiguous_guid`) на
  реальном пути почти недостижима: нестроковое значение поля, отсутствие поля и
  повтор `guid` — это уже `ERROR` уровня `validate`, поэтому такой экспорт
  блокирует запрос раньше классификации (`export_invalid`). Проверка остаётся в
  коде как честная классификация для исходника, который прошёл предпроверку, и
  покрыта контрактными тестами.
- Уровни и коды правил QA не настраиваются: реестр правил фиксирован и расширяется
  только кодом, вместе с тестами.

## Проверки

Все проверки запускаются из корня репозитория — оттуда, где лежит корневой Cargo
workspace (`/Cargo.toml`):

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

`--locked` уместен потому, что `Cargo.lock` лежит в корне и версия workspace — общая
для всех участников.

То же самое независимо от локального окружения выполняет CI
(`.github/workflows/ci.yml`) на `pull_request`, на push в default branch и вручную:
`cargo fmt --all --check`, `cargo clippy --workspace --all-targets --locked -- -D
warnings` и `cargo test --workspace --locked`. Затем CI сам находит `deck.json`
внутри `decks/` и вызывает для каждого `validate`, не называя ни одной колоды,
уровня, модели или поля по имени: если экспортов нет, шаг проходит успешно. CI
только читает репозиторий, поэтому изменение состава `decks/` не требует правки
workflow.

Заявленная MSRV проверяется отдельным job'ом на версии из корневого `Cargo.toml`:
workflow читает `[workspace.package] rust-version` через `cargo metadata`, заодно
убеждается, что участники workspace не расходятся в этой версии, и собирает
workspace на ней (`cargo +<msrv> check --workspace --all-targets --locked`).
Версия объявлена ровно один раз — в корневом манифесте; ни workflow, ни эта
документация не хранят её копию. Локально ту же проверку можно воспроизвести так:

```bash
MSRV=$(cargo metadata --no-deps --format-version 1 | jq -r '[.packages[].rust_version] | unique | .[]')
rustup toolchain install "$MSRV" --profile minimal
cargo "+$MSRV" check --workspace --all-targets --locked
```

`cargo nextest run` (если nextest установлен) можно использовать локально вместо
`cargo test`: CI выполняет именно `cargo test --workspace --locked`.

Набор тестов состоит из:

- unit-тестов доменной логики (разрешение полей через `ord`, обход дерева,
  проверки `find`/`stats`, сканер шаблонов, контракт exit codes);
- unit-тесты правил QA: каждое правило проверяется на своих границах (пустое
  значение, пробелы по краям и внутри, белый `<span>`, группировка дубликатов), а
  также порядок findings и усечение отчёта; отдельный тест фиксирует, что набор
  правил и уровень каждого кода — публичный контракт, а findings не зависят от имён
  полей и моделей;
- `tests/synthetic.rs` — синтетические fixtures на каждую ветку validation и
  каждую доменную ошибку;
- `tests/export_contract.rs` — свойства, обязанные выполняться для любого
  корректного CrowdAnki-экспорта: counts, порядок полей и media пересчитываются из
  сырого JSON и из содержимого каталога, а форма фикстур намеренно не совпадает с
  формой реальных колод. Ни один тест не требует, чтобы `decks/` существовал или
  содержал конкретные колоды;
- `tests/cli_contract.rs` — аргументы CLI, exit codes и разделение
  `stdout`/`stderr` через реальный binary, включая негативные проверки снятых
  контрактов: флаг `--word` отвергается как неизвестный аргумент;
- `tests/qa_contract.rs` — контракт `qa`: состав реестра (ровно пять кодов, без
  `duplicate_primary_field`), уровень `error` без отказа (и без влияния на
  `validate`/`edit`), границы выборок в `evidence`, `--max-per-code` против полных
  счётчиков, детерминизм, пометка неадресуемых findings, полный контекст группы и
  пересчёт counts независимым oracle'ом по сырому `deck.json` на синтетических
  фикстурах (ни одно ожидаемое число не зашито в тест);
- `tests/review_contract.rs` — контракт `review`: размер страницы, полный обход
  пагинации без потерь и повторов, пустая страница за концом выборки, компактность
  batch, ограничение findings внутри заметки, совпадение ошибок `--guid` с `find`,
  приведение участников группы правил-дубликатов (в пределах
  `MAX_RELATED_NOTES`) и исключение неадресуемых заметок с видимым
  `excluded_unaddressable`, а также отказ на снятом флаге `--word`;
- `tests/review_check_contract.rs` — контракт `review-check`: все пять статусов
  предложения, приоритет `stale`/`invalid` (5 → 4 → 3) в exit codes, отказ на
  документе чужой формы (`edits`) и на устаревшем флаге `--request`, все причины
  `invalid_request` документа предложений (`malformed_proposals`,
  `unsupported_schema_version`, `empty_proposals`, `too_many_proposals`,
  `proposals_too_large`, `duplicate_proposal_id`), перенос метаданных
  (`proposal_id` → `edit_id`, `reason` только в отчёт), отсутствие записи и
  временных файлов, усечение отчёта при полных счётчиках, чтение документа со
  stdin и сквозной конвейер `review → предложения → review-check → edit (dry-run и
  `--apply`) → validate` на временной копии экспорта;
- `tests/edit_contract.rs` — контракт `edit`: режимы dry-run и `--apply`, все
  четыре исхода правки, конфликт предусловия, пакетные ошибки разрешения,
  отказы по неканоничному и невалидному экспорту, схема JSON-ответа, exit codes
  и равенство путей `--request FILE` и `--request -`;
- `tests/edit_source_preservation.rs` — физический результат правки: ровно одна
  изменённая строка на правку, сохранение нетронутых строк байт в байт,
  экранирование, переводы строк и Unicode, идемпотентность без перезаписи,
  отказы неканоничных вариантов, сохранение прав доступа, отсутствие временных
  файлов. Колоду целиком строит сам тест, а не берёт из `decks/`: массовые прогоны
  идут по синтетическому экспорту с шестью полями и второй, однополевой моделью во
  вложенной колоде;
- конкурентная публикация покрыта отдельно: unit-тест write-layer
  детерминированно воспроизводит окно между проверкой и `rename` (два writer'а
  от одного snapshot: публикуется ровно один, второй получает `source_changed`),
  контрольный тест показывает, что та же последовательность без блокировки теряет
  update, тест на блокировку проверяет, что публикация действительно ждёт
  освобождения, а `tests/edit_source_preservation.rs` прогоняет два реальных
  процесса `edit --apply` параллельно и проверяет, что итог остаётся каноническим
  экспортом без потерянных правок.

Регрессия на исходный race защищена так: детерминированный unit-тест проверяет
итог `replace_atomically` (проигравший не публикуется и получает `source_changed`,
результат победителя остаётся в файле), контрольный тест фиксирует, что
последовательность без критической секции теряет update, а тест на блокировку
подтверждает, что без неё публикация не завершается. Сама race-window внутри
`write_and_publish` недоступна снаружи без тестового шва, поэтому она проверяется
не подделкой сигнала «вот-вот опубликует», а этими тремя наблюдаемыми свойствами.
