# anki-repo

`anki-repo` — набор инструментов для детерминированного анализа CrowdAnki-экспортов,
строго ограниченных правок их содержимого и сбора свидетельств для независимого
ревью кода репозитория `Anki-decks`. Он даёт агенту быстрый и предсказуемый доступ к структуре
`deck.json`, не требуя читать многомегабайтный JSON вручную.

Команды `inspect`, `find`, `stats`, `validate`, `qa`, `review`, `review-check`
и `models` только читают экспорт. `visual-report` читает экспорт и записывает
лишь новый каталог отчёта. `code-review triage` работает с отдельными локальными
артефактами semantic review; ни одна из этих команд не меняет экспорт. Команды,
меняющие экспорт:

- `edit` меняет **значения** уже существующих полей уже существующих заметок;
- `create` **добавляет** новые заметки в существующую колоду по уже существующей
  модели; по явно заданным правилам он может разместить проверенные изображения
  кандзи и pitch-accent и добавить их имена в `media_files`;
- `retire` **дописывает тег** вывода из обращения к уже существующей заметке;
- `migrate-media` переводит ссылки с прежнего имени файла на текущее
  каноническое имя домена — единственная команда, которой разрешено изменить
  медиассылку существующей заметки, и только после доказательства её семантики.

Физического удаления заметок в наборе инструментов нет: заметка, которую пора убрать из
работы, помечается тегом, а удаляет её человек в Anki. Ни одна команда не создаёт
и не удаляет колоды, модели, поля и конфигурации, не перемещает сущности и не
меняет их идентичности (`guid`, `note_model_uuid`, `crowdanki_uuid`,
`deck_config_uuid`). По умолчанию изменяющие команды выполняют dry-run; запись
возможна только по явному `--apply`. `create` размещает только проверенные файлы,
разрешённые правилами точного домена и поля. `migrate-media` материализует
канонический файл и удаляет соответствующий старый файл только при доказанной
миграции; произвольной записи в `media/` набор инструментов не предоставляет.

`qa`, `review` и `review-check` образуют конвейер внешней проверки содержимого
карточек: инструмент детерминированно находит проблемы, отдаёт по ним компактный пакет,
принимает структурированные предложения внешнего агента и превращает их в готовый
запрос для `edit`. Сам инструмент при этом **не вызывает никаких LLM API** и не содержит
ни одного сетевого вызова: разбор содержимого делает внешний агент, а `anki-repo`
остаётся детерминированной границей репозитория.

Маршрут «создать и проверить» выглядит так: `models` даёт фактическую схему полей
модели и свидетельства о семантике каждого поля, `create` добавляет заметку по
этой схеме, `retire` помечает устаревшую, а `visual-report` собирает статический
офлайн-отчёт о том, что именно изменилось между двумя состояниями экспорта, — с
превью карточек по фактическим шаблонам модели. Для мигрируемых ссылок есть узкая
`migrate-media`: сначала она доказывает пару идентификатор — прежнее имя файла и
инвентаризирует потребителей, затем переводит только доказанные ссылки.

Отдельные пространства команд `code-review` и `language` работают с исходниками
и локальными артефактами ревью. `code-review` собирает свидетельства, строит
структурную очередь для навигации и сравнивает снимки; семантические решения
ревьюер хранит отдельно. `language` сканирует человеческий текст и применяет
явно утверждённые замены.
Описанные выше четыре мутирующие команды относятся именно к CrowdAnki-экспорту;
`language apply --apply` меняет исходные файлы по отдельному контракту ниже.

## Зачем

- Один вызов вместо ручного `jq`/скрипта: `inspect`, `find`, `stats`, `validate`,
  `qa`, `review`, `review-check`, `models`, `visual-report`, `edit`, `create`,
  `retire`, `migrate-media`.
- Разрешение имён полей через `note_model_uuid` → `note_models[].flds[].ord`
  сосредоточено в одной реализации, поэтому агент не повторяет эту логику ни при
  чтении, ни при правке, ни при создании заметки.
- `models` отдаёт не только имена полей, но и свидетельства: живые значения и
  число пустых, разобранные конструкции шаблонов и явный список того, что
  статически не вычисляется. Агент не угадывает семантику поля по имени.
- Точечная правка, которая физически не может задеть остальной файл: проверки
  предусловий, dry-run по умолчанию и проверка байтового diff перед записью.
- Создание заметки, которое не может испортить экспорт: значения новых полей по
  умолчанию обходятся без ссылок на медиа; явно настроенные обработчики домена
  разрешают только проверенные изображения этого домена и материализуют их по
  `--apply`. Колода и модель адресуются идентичностями, а кандидат переразбирается
  и проверяется до записи.
- Вывод из обращения без физического удаления: заметка остаётся на месте и
  остаётся адресуемой, меняется только её набор тегов.
- Визуальный отчёт, который открывается офлайн и показывает фактические превью
  карточек по шаблонам модели, а не пересказ diff'а.
- Конвейер внешнего ревью, который не читает многомегабайтный `deck.json` целиком:
  детерминированный отбор, компактные страницы по 25 заметок и проверка
  предложений агента против фактического состояния экспорта.
- Стабильный машиночитаемый вывод: одинаковый JSON на одинаковых данных.
- Человекочитаемый вывод по умолчанию и отдельный JSON-режим для автоматизации.

## Требования

- Linux — единственная поддерживаемая платформа: проверенное чтение использует
  Linux-библиотеку `asset-store`, которая не собирается на других платформах.
- Набор инструментов Rust с редакцией 2024. Минимальная поддерживаемая версия (MSRV)
  объявлена один раз — в `[workspace.package] rust-version` корневого
  `Cargo.toml`; участники workspace наследуют её (`edition.workspace = true`,
  `rust-version.workspace = true`), поэтому отдельной копии версии в
  `tools/anki-repo/Cargo.toml` нет. Проверено на стабильном `rustc`/`cargo` и на
  заявленной MSRV.
- Единственная точка сборки — корневой Cargo workspace (`/Cargo.toml`, участник —
  `tools/anki-repo`); `Cargo.lock` тоже лежит в корне репозитория. Собирать и
  тестировать нужно из корня, а не из каталога пакета.
- Никаких системных сервисов и сети: инструмент работает только с локальными файлами.
  Ни одна команда не обращается к LLM API или к любому другому внешнему сервису.

## Сборка и запуск

Из корня репозитория:

```bash
cargo build --release --workspace
./target/release/anki-repo --help

# или без установки
cargo run --quiet --bin anki-repo -- inspect decks/japanese/words/Words__N3
```

Пути к экспортам можно задавать и относительно текущего каталога, и абсолютно.

## Команды

Во всех примерах ниже `EXPORT` — каталог экспорта, например
`decks/japanese/words/Words__N3`. Указывать нужно именно каталог: путь к самому
`deck.json` отвергается с понятной ошибкой.

Пути и имена полей в примерах иллюстративны. Набор инструментов работает с произвольным
CrowdAnki-экспортом и не знает имён полей конкретной модели: `Слово`,
`Часть речи`, `Значение` и прочие имена, а также уровни и пути колод взяты из
текущих пользовательских колод только для наглядности и контрактом не являются.
Имя поля всегда называет вызывающая сторона, а сверяется оно с фактическими
`note_models[].flds[].name` того экспорта, с которым работает команда.

### `code-review collect|verify|delta|queue|triage|execution|learning`

Пространство `code-review` собирает детерминированные свидетельства для
независимого ревью кода. Порядком самого ревью владеет
[anki-code-review](../../.agents/skills/anki-code-review/SKILL.md).
Карточные команды `review` и `review-check` продолжают работать со своим доменом.

В выводе различаются четыре понятия:

- **свидетельства** — факты о диапазоне Git, файлах и результатах анализаторов;
- **кандидат** — сигнал детектора, который требует содержательной проверки;
- **диагностика** — структурированное сообщение Cargo/rustc/Clippy с уровнем,
  кодом и привязкой к исходнику, если анализатор их предоставил;
- **замечание** — подтверждённое ревьюером нарушение с условиями и последствиями.
  Инструмент не создаёт замечаний и не назначает семантическую оценку по одному сигналу.

`collect` принимает обязательные `--base` и `--head`. Ссылки разрешаются в
точные SHA; анализируется этот диапазон и полное содержимое релевантных
затронутых файлов в проверяемом HEAD. Рабочая копия не
переключается и не очищается. Незакоммиченные изменения не становятся частью
зафиксированного снимка только потому, что находятся в той же рабочей копии.

Перед вызовом `collect`/`verify` вызывающий агент устанавливает номер PR из
запроса или надёжной информации GitHub о текущей ветке. CLI сам не обнаруживает
PR, а `anki-code-review` skill задаёт порядок такого определения. Не выводи номер
из имени ветки. Если PR существует, передавай `--pr-number NUMBER` явно в
каждой команде `collect` и `verify`. Опускай параметр только когда отсутствие
PR подтверждено; тогда каталог использует сегмент `local`. Если статус PR
нельзя достоверно установить, не представляй локальное ревью как ревью PR.

Все постоянные локальные артефакты независимого code review хранятся только в
каноническом workspace внутри текущего репозитория:
`.anki-repo/review/<PR_NUMBER|local>/<FULL_HEAD_SHA>/`. Для PR номер —
навигационный сегмент; полный SHA HEAD и digest байтов `review.json` задают
идентичность снимка. Новый HEAD в том же PR получает отдельный каталог и не
перезаписывает предыдущий. Если для того же HEAD нужна другая база или набор
анализаторов, передай `--out-dir` с новым дочерним каталогом
`snapshot-<32 lowercase hex>`; он хранит отдельные свидетельства и не заменяет
предыдущий снимок. Ожидаемая структура снимка по умолчанию:

```text
.anki-repo/review/<PR_NUMBER|local>/<FULL_HEAD_SHA>/
├── review.json
├── review-queue.json
├── review.txt
├── delta.json                         # если создан verify или delta
├── semantic-triage.input.json        # решения главного reviewer'а
├── semantic-triage.json              # проверенное каноническое представление
├── review-report.md                  # производный отчёт
└── runs/
    └── <unique-job-id>/              # собственные файлы execution job/субагента
```

Имена показывают контракт размещения, а не требование создавать пустые файлы.
Используй фактический `artifact_dir`, возвращённый успешным `collect`/`verify`,
как источник всех downstream-путей; не реконструируй путь по SHA вручную и не
выбирай временный каталог. Необязательный `--out-dir DIR` допустим только если
он в точности совпадает с workspace по номеру PR/local и полному HEAD SHA либо
с его единственным дочерним каталогом `snapshot-<32 lowercase hex>`. Выбирай новый
snapshot ID при повторном сборе того же HEAD с другой базой или набором
анализаторов. Произвольный каталог, tracked workspace, symlink, `..` и
конфликтующий файл отвергаются до записи. Исходные артефакты неизменяемы:
повторная генерация тех же байтов идемпотентна, другое содержимое для того же
пути завершается конфликтом. Проверенные производные triage/report могут
обновляться только по своим точным именам и только внутри этого же workspace.

`collect` и `verify` создают полный `review.json`, производный
`review-queue.json` и компактный навигационный `review.txt`; `verify`
дополнительно сохраняет `delta.json`. Полный набор сырых кандидатов остаётся в
`review.json`, а структурная классификация и членство в review units — в
`review-queue.json`. `review.txt` помогает выбрать следующий шаг, но не является
источником истины. `.anki-repo/review/` исключён через `.gitignore`: локальные
артефакты не попадают в PR автоматически. Команда сама не добавляет файлы в
индекс и не создаёт коммиты. Перед записью проверяется, что workspace не
содержит tracked Git-файлов. Единственное общее исключение — инфраструктура
между jobs: `.anki-repo/review/execution-locks/` может содержать общие слоты
concurrency-lock. Там нет результатов, отчётов или иных артефактов конкретного
PR/HEAD; все job-файлы остаются внутри `runs/<unique-job-id>/` своего workspace.

`verify --baseline PACK --head REF --pr-number NUMBER` повторно собирает
свидетельства, используя базу из исходного пакета, и сравнивает с новым HEAD.
Передавай номер известного PR явно и при `verify`; результат появится в новом
workspace этого PR, соответствующем полному SHA нового HEAD. Доступны
`--out-dir DIR` и `--run-clippy`. `delta --before PACK --after PACK` сравнивает
уже сохранённые пакеты без повторного анализа; `--out PATH` может указывать
только на `delta.json` канонического workspace пакета `after`. Несовместимые
снимки репозитория и базы не считаются одной итерацией ревью.

`verify` выводит в stdout счётчики и краткую сводку статусов. Полные списки
изменений сохраняются в `delta.json` каталога артефактов. Так размер вывода не
растёт вместе с числом сигналов.

Статусы сравнения относятся к сигналам детекторов: сигнал исчез, остался,
изменился или появился. Исчезновение кандидата не доказывает исправление
подтверждённого замечания; это устанавливает ревьюер по актуальному коду.
В JSON `verify` поле `delta` содержит идентичности `before`/`after`, общие числа,
`candidate_status_counts`, `diagnostic_status_counts` и краткие статусы анализаторов;
полные массивы изменений доступны в `delta.json`.

```bash
# PR_NUMBER получен из запроса или проверен через GitHub для текущей ветки.
COLLECT=$(anki-repo --json code-review collect --base origin/main --head HEAD --pr-number "$PR_NUMBER")
ARTIFACT_DIR=$(jq -er '.result.artifact_dir' <<< "$COLLECT")
PACK="$ARTIFACT_DIR/review.json"
QUEUE="$ARTIFACT_DIR/review-queue.json"
anki-repo code-review collect --help
VERIFY=$(anki-repo --json code-review verify --baseline "$PACK" --head "$NEW_HEAD" --pr-number "$PR_NUMBER")
NEW_ARTIFACT_DIR=$(jq -er '.result.artifact_dir' <<< "$VERIFY")
NEW_PACK="$NEW_ARTIFACT_DIR/review.json"
anki-repo code-review delta --before "$PACK" --after "$NEW_PACK" --out "$NEW_ARTIFACT_DIR/delta.json"
```

`artifact_dir` извлекается из JSON-конверта успешной команды. При подтверждённом
отсутствии PR в `collect`/`verify` опусти `--pr-number`; тогда CLI выберет
`local/<FULL_HEAD_SHA>`. Не используй такой режим, если номер существующего PR
не был надёжно выяснен. Для последующих команд получай `PACK`, `QUEUE`, triage,
report, delta и execution пути от соответствующего `artifact_dir`.

#### Анализаторы и ограничения

Обычные `collect` и `verify` не запускают Cargo/Clippy и не исполняют код
проверяемого проекта. Явный `--run-clippy` разрешает локальный запуск Clippy,
включая исполнение `build.rs`, процедурных макросов и других частей сборки.
Используй его только для кода, которому доверяешь. Старый `--skip-clippy`
удалён: для сбора без исполнения дополнительные флаги не нужны.
Для параллельных проверок в независимом ревью запускай Clippy через приватный
job режима `isolated_checks`; наличие `--run-clippy` само по себе не обещает
отдельную job-область.

Адаптер использует уже установленный локальный инструмент в режиме без сети;
он не устанавливает компоненты и не скачивает зависимости. Режим без сети ограничивает
сетевую работу Cargo, но не изолирует код сборки от файлов, окружения и секретов
пользователя. При недоступном анализаторе, отсутствующих локальных зависимостях
или ошибке запуска пакет содержит статус и причину ограничения; `unavailable`
не означает успешную проверку без диагностик. Сообщения Cargo/rustc/Clippy
читаются из структурированного вывода. Их наличие не превращает сбор
свидетельств в содержательное ревью.

#### Изолированное исполнение проверок

`code-review execution` управляет локальными execution jobs, привязанными к
точному snapshot и digest `review.json`. Для обычного чтения неизменяемого
`review.json`, очереди и точных Git images отдельная рабочая копия не нужна. Для
сборки или запуска проверок подготовь приватный job в режиме `isolated_checks`;
для эксперимента, меняющего исходники или тесты, используй
`disposable_source_experiment` на detached worktree проверяемого HEAD.

Возвращённые `artifact_dir` и `job_directory` заданы относительно корня
репозитория. CLI принимает относительные входные пути от текущего рабочего
каталога: выполняй весь workflow из корня или преобразуй возвращённые пути в
абсолютные относительно корня.

Последовательность CLI для уже полученного `artifact_dir`:

```bash
REPO_ROOT=$(git rev-parse --show-toplevel)
cd "$REPO_ROOT"
PREPARED=$(anki-repo --json code-review execution prepare --pack "$PACK" --mode isolated_checks --scope tests --pr-number "$PR_NUMBER")
JOB_PATH=$(jq -er '.result.job_directory' <<< "$PREPARED")
anki-repo code-review execution run "$JOB_PATH" --timeout-seconds "$TIMEOUT_SECONDS" --cwd "$CWD" --env RUST_BACKTRACE=1 -- cargo test --workspace --locked
anki-repo --json code-review execution inspect "$JOB_PATH"
```

`prepare` принимает путь к пакету, режим `isolated_checks` или
`disposable_source_experiment`, обязательное направление `--scope` и
необязательный `--pr-number`. `--pack` обязан указывать на канонический
`review.json` внутри `.anki-repo/review/<PR_NUMBER|local>/<FULL_HEAD_SHA>/` или
его `snapshot-<32 lowercase hex>` варианта; `prepare` наследует namespace,
полный HEAD SHA и вариант workspace из этого пути и source pack, создавая job
только в `runs/<unique-job-id>/` этого workspace. Если передан
`--pr-number`, он проверяется как assertion; несовпадение завершается
`invalid_request` до создания job. Поэтому известный PR не может незаметно
попасть в `local` или другой PR namespace. `run` принимает timeout от
1 секунды до 24 часов, относительный `--cwd` и явный argv после `--`; оболочка
самостоятельно не запускается. Политика среды по умолчанию — `minimal`.
`HOME`, `CARGO_HOME` и каталог сборки приватны для job: общий изменяемый кеш Cargo не используется. Зависимости общего кеша не
появляются в новом job автоматически; выполнение Cargo может требовать сети,
а `--offline` — завершаться отказом при отсутствии зависимостей в приватном кеше. Повторяемый `--env
KEY=VALUE` выбирает политику `explicit`; приватные пути job нельзя переопределить. В
структурированном результате распознаются формы `--key value`, `--key=value` и
`KEY=value` для ключей `token`, `api-token`, `access-token`, `auth-token`,
`refresh-token`, `secret`, `client-secret`, `password`, `passwd`, `api-key`,
`apikey`, `authorization`, `proxy-authorization`, `credential`, `credentials`,
`cookie` без учёта регистра; дефис и underscore эквивалентны.
Распознаются заголовки `Authorization`, `Proxy-Authorization`, `Cookie`,
`X-Api-Key`, `Api-Key`, в том числе через `-H`, `--header` и `--proxy-header`.
`argv[0]` и аргументы после отдельного `--` не разбираются как секретные флаги.
Для explicit env распознаются отдельные компоненты имени `TOKEN`, `SECRET`,
`PASSWORD`, `PASSWD`, `APIKEY`, `AUTHORIZATION`, `CREDENTIAL`, `CREDENTIALS`,
`COOKIE`, имя `API_KEY` и суффикс `_API_KEY`; `TOKENIZER_PATH` и
`SECRETARY_NAME` не считаются секретными.

Эти значения маскируются в `request.argv` и ограниченных текстах stdout/stderr.
Маскирование работает по совпадению исходных байтов; секрет, пересекающий
границу вывода, не оставляет видимого префикса. `total_bytes` относится к сырому
логу, а `truncated` учитывает как исходный лимит, так и дополнительную обрезку
после маскирования. `utf8_lossy` сообщает о замене некорректного UTF-8. Произвольные
секреты под нераспознаваемыми именами автоматически не обнаруживаются.
`argv_sha256` рассчитывается по безопасному представлению `argv`, поэтому его
нельзя использовать для перебора распознанных секретных значений.
`--max-parallel-jobs` задаёт общий для репозитория предел одновременно активных
jobs (1–64, по умолчанию 4). Пока есть активные jobs, запрос с другим пределом
отклоняется как `invalid_request` (exit 3); после их завершения можно выбрать
другое значение. При совпадающем пределе и полной ёмкости возвращается
`execution_busy` (exit 13) с `details.retryable: true`, `resource` и `reason`.
Занятый job также возвращает временный отказ; завершённый job повторно запускать
нельзя, и это постоянный конфликт.

`inspect` показывает наблюдаемое состояние job и ограничения отдельно от
сохранённого результата. Жизненный цикл различает `preparing`, `prepared`,
`running`, `completed`, `preparation_failed` и `interrupted`; статус проверки
различает `passed`, `failed`, `timed_out`, `cancelled`, `unavailable` и
`incomplete`.

`preparing` («идёт подготовка») публикуется до создания runtime-каталогов и до
`git worktree add`, поэтому частично подготовленное задание никогда не выдаётся
за готовое: `prepared` появляется только последним шагом подготовки. Пока
подготовку удерживает другой процесс, запуск и очистка задания недоступны;
брошенная подготовка очищается без подтверждения, потому что код этого задания
не запускался. Ограничения различают три наблюдаемых состояния: подготовку
удерживает другой процесс; подготовку никто не удерживает, но её ресурсы уже
удалены очисткой; подготовку никто не удерживает и ресурсы остались. В последнем
случае запуск запрещён, а очистка допустима.
`cancel` создаёт отдельный маркер, `cleanup` проверяет ownership и состояние
перед удалением временных каталогов. Manifest, результаты, `logs/` и `outputs/`,
включая `outputs/direction-report.json`, сохраняются.

После запуска процесса обычный `cleanup` сохраняет worktree, поскольку
невозможно доказать отсутствие потомков, вышедших из группы процессов.
Оператор может явно подтвердить отсутствие живых потомков:

```bash
anki-repo --json code-review execution cleanup "$JOB_PATH" --confirm-no-live-descendants
```

Этот флаг — подтверждение оператора, а не техническое доказательство.
Проверки ownership, блокировки и безопасных путей продолжают действовать;
в результате очистки сохраняется это ограничение. `workspace_removed` описывает
удаление исходного worktree и временных рабочих поверхностей, а `evidence_retained` — сохранение
свидетельств и результатов.

Execution jobs и отчёты отдельных субагентов используют только свои каталоги
внутри `runs/<unique-job-id>/` того же PR/HEAD workspace. Execution jobs
выделяют собственные изменяемые каталоги для проверки и не
должны перезаписывать общий пакет или выходы другого job. Это разделение
рабочих файлов предотвращает конфликты, но само по себе не является security
sandbox и не доказывает запрет доступа к файлам, окружению, сети или секретам.
Execution доступен только на Linux с доступным `/proc` для безопасной очистки;
на других платформах запуск завершается отказом до исполнения. Полные
`logs/stdout.log` и `logs/stderr.log` сохраняются в приватном job без очистки
секретов и могут содержать чувствительные значения. Маскирование
ограниченного свидетельства в JSON не очищает эти файлы; проверь сырые логи
перед передачей другому агенту. `collect` и подготовка job проверяемый код автоматически не
запускают; исполнение выбирает ревьюер с учётом действующей политики доверия. Делегирование
субагентов остаётся ответственностью Codex CLI, DSH или другого агента; у
`anki-repo` нет общего API их запуска.

Для provider-neutral handoff reviewer сохраняет в собственном job namespace
`outputs/direction-report.json` с полями `schema_version`, точным `snapshot`
(`base_sha`, `head_sha`, `review_pack_sha256`), `direction`, исходной `task`,
`completion` (`complete`, `incomplete`, `interrupted`, `not_started` или
`unverified`), `checks` с `job_id`, `status` и evidence paths,
`potential_findings` и `limitations`. Это сообщение субагента, а не готовое
семантическое решение: только главный reviewer переносит перепроверенные выводы
в canonical triage.

Детерминизм относится к нормализованному представлению одного снимка и
стабильной сортировке. Clippy вызывается с `--quiet`; известные строки прогресса
Cargo (компиляция, проверка, время завершения и ожидание блокировок) исключены
из `stderr_summary`, а полезные сообщения об ошибках сохраняются с ограничением
длины. Повторная запись того же содержимого в тот же каталог идемпотентна;
другое содержимое даёт `review_artifact_conflict`. Набор диагностик зависит
также от доступности и версии локального анализатора; этот статус нужно
учитывать при сравнении.

#### Структурная очередь ревью

`review-queue.json` — отдельный версионируемый артефакт, который детерминированно
классифицирует кандидатов и объединяет только структурно однородные сигналы в
элементы очереди. Он привязан к точным байтам исходного `review.json` по SHA-256
и к переносимой идентичности Git-снимка. Очередь сохраняет исходные
идентификаторы кандидатов, классификацию, отдельные элементы и группы,
представителей и сводные метрики.
Она не содержит семантических решений или замечаний.

`queue validate` сверяет syntax-derived классификации с результатом
авторитетного классификатора, восстановленным из точных Git images и AST
снимка. Самосогласованные поля очереди, её групповые подписи и digest не служат
доказательством происхождения классификации. Если нужные Git objects или AST
недоступны, полная проверка завершается `syntax_authenticity_unavailable`.
Передай `--structure-only`, чтобы ограничить проверку структурой и digest;
результат явно помечается `structure_only`, и syntax authenticity не
подтверждается. Этот флаг поддерживают также команды `summary`, `list`, `group`
и `candidate`; ограниченный результат нельзя представлять как полностью
подлинную syntax-derived классификацию.

Очередь можно проверить, свести к навигационной сводке, получить страницу
подходящих элементов и раскрыть отдельную группу или кандидата командами только
для чтения:

```bash
anki-repo code-review queue validate --pack "$PACK" --queue "$QUEUE"
anki-repo code-review queue summary --pack "$PACK" --queue "$QUEUE"
anki-repo code-review queue list --pack "$PACK" --queue "$QUEUE"
anki-repo code-review queue group --pack "$PACK" --queue "$QUEUE" --id "$GROUP_ID"
anki-repo code-review queue candidate --pack "$PACK" --queue "$QUEUE" --id "$CANDIDATE_ID"
```

`PACK` — путь к исходному `review.json`, а `QUEUE` — путь к `review-queue.json`
того же снимка. Сводка и раскрытие сохраняют ссылки на исходные идентификаторы
кандидатов, чтобы по ним можно было перейти к полным свидетельствам.
`review.txt` показывает точные идентификаторы `base` и `head`, число исходных
кандидатов и элементов очереди, отдельных элементов и групп, кандидатов в
группах; распределение по приоритету;
сводки по детекторам и структурным поверхностям/ролям; заметные отдельные
элементы и группы с представителями; число `unknown`; состояния анализаторов и
диагностики. Это компактная карта для навигации, а не самостоятельный источник
истины.

##### `queue list`

`list` выдаёт страницу элементов очереди и перед чтением списка проверяет, что
`PACK` и `QUEUE` относятся к одному точному снимку: сверяются байты `review.json`, Git
identity, структура очереди и доступный результат syntax-authenticity
verification. При несовпадении команда завершается ошибкой, а частичный список
не возвращается. Если exact Git images или AST недоступны, передай
`--structure-only`, чтобы вывести ограниченный результат с явным статусом
`structure_only`. В `--help` команда описана как постраничный просмотр
элементов очереди с фильтрами; доступные параметры:

```text
anki-repo code-review queue list --pack PACK --queue QUEUE [--limit N] [--offset N] [--priority high|normal|low] [--unknown] [--detector LABEL] [--surface LABEL] [--execution LABEL] [--role LABEL] [--text-role LABEL] [--code-role LABEL] [--structure-only]
```

По умолчанию `--limit` равен `50`, максимум — `200`; `--offset` по умолчанию
равен `0` и отсчитывается с нуля. Сначала применяются фильтры, затем из
совпавшего списка выбирается страница. Для следующей страницы передай offset,
увеличенный на `returned_units`, и продолжай, пока `has_more` не станет `false`.
Без фильтров совпавший набор включает всю очередь, но команда всё равно
возвращает только запрошенную страницу. Пустое совпадение — успешный пустой
результат, а не `not_found`.

`--priority` оставляет элементы одного приоритета. `--detector`, `--surface`,
`--execution`, `--role`, `--text-role` и `--code-role` фильтруют по точным
машинным меткам соответствующего измерения. Совместно заданные фильтры сужают
результат одновременно. `--unknown` оставляет элементы, где неизвестно хотя бы
одно измерение классификации; его можно сочетать с остальными фильтрами.
Фильтр не меняет очередь и не подтверждает семантическое решение.

В JSON-режиме объект `result` содержит `source_digest_valid`,
`syntax_authenticity`, `total_units` (все элементы очереди),
`matched_units` (число элементов после фильтрации, до пагинации), `offset`, `limit`,
`returned_units`, `has_more` и страницу `units`. Каждый элемент `units` — краткая
запись с `id`, `kind`, `priority`, `classification`, `detector`,
`candidate_count`, `candidate_id` и `representative_candidate_ids`. Для
`kind: individual` поле `candidate_id` содержит неизменённый ID исходного
кандидата, а `representative_candidate_ids` всегда пуст; для `kind: group` `candidate_id`
равен `null`, а `representative_candidate_ids` содержит ограниченный набор
представителей группы. Это навигационная выборка; полные сведения об участниках
по-прежнему берутся из очереди, `review.json` и команд `queue group` /
`queue candidate`.

Для обработки всех элементов с приоритетом high запрашивай страницы с
`--priority high`, а для полного прохода по всем неизвестным измерениям —
отдельно страницы с
`--unknown`. Если страниц несколько, используй `--limit 200` и увеличивай
`--offset` по фактическому `returned_units`:

```bash
# первая страница элементов с высоким приоритетом
anki-repo code-review queue list --pack "$PACK" --queue "$QUEUE" --priority high --limit 200 --offset 0
# следующая страница, если в предыдущем ответе `has_more` было true
anki-repo code-review queue list --pack "$PACK" --queue "$QUEUE" --priority high --limit 200 --offset 200
# элементы с неизвестностью хотя бы в одном измерении — отдельный проход
anki-repo --json code-review queue list --pack "$PACK" --queue "$QUEUE" --unknown --limit 200 --offset 0
anki-repo code-review queue list --help
```

Приоритет задаёт только детерминированный порядок и гранулярность внимания; он
не определяет серьёзность, замечание или итоговое решение. Групповой элемент
предлагает совместно рассмотреть структурно похожие сигналы, но не является
семантическим решением по группе.
Представители помогают навигации и не доказывают семантическое покрытие остальных
участников. Если группа по представителям или контексту выглядит неоднородной,
раскрой её глубже и проверь различающиеся случаи отдельно.

`review.json` остаётся полным авторитетным источником свидетельств для независимого анализа.
Сверяй очередь с diff и окружающим кодом: самостоятельное чтение реализации и
контекста обязательно, даже если элемент имеет низкий приоритет или выглядит
однородным. Отсутствие кандидатов означает только отсутствие сигналов этих
детекторов и не доказывает отсутствие дефекта.

#### Семантический разбор

`collect`, `verify` и `delta` остаются слоем свидетельств о коде и сигналах
детекторов; очередь только структурирует эти сигналы для навигации.
Семантический разбор оформляется как отдельный версионируемый
JSON-документ ревьюера: он хранит решения по кандидатам
и замечания (`findings`), не меняя `review.json`. Сгенерированный отчёт строится
по проверенному документу решений и служит его человекочитаемым представлением; финальный
ответ ревьюера — отдельное обобщение только доказанных замечаний и реальных
ограничений. Ни сбор свидетельств, ни команды `triage` не вызывают LLM/API, не
исправляют код и не меняют проверяемый исходный код.

Полный цикл:

```bash
WORKSPACE="$ARTIFACT_DIR"
TRIAGE="$WORKSPACE/semantic-triage.input.json"
CANONICAL_TRIAGE="$WORKSPACE/semantic-triage.json"
REPORT="$WORKSPACE/review-report.md"
anki-repo code-review triage init --pack "$PACK" --out "$TRIAGE"
# Внешний ревьюер редактирует TRIAGE; незавершённые кандидаты остаются явными.
anki-repo code-review triage validate --pack "$PACK" --triage "$TRIAGE" --canonical-out "$CANONICAL_TRIAGE" &&
anki-repo code-review triage summary --pack "$PACK" --triage "$CANONICAL_TRIAGE" &&
anki-repo code-review triage report --pack "$PACK" --triage "$CANONICAL_TRIAGE" --out "$REPORT"
```

`PACK` — путь к исходному `review.json`, `TRIAGE` — редактируемый исходный
JSON-артефакт решений ревьюера, `CANONICAL_TRIAGE` — его производный
канонический JSON после успешной валидации, `REPORT` — производный
человекочитаемый отчёт. Имена файлов обязательны: `semantic-triage.input.json`,
`semantic-triage.json`, `review-report.md`. `triage init` создаёт `TRIAGE` и не
перезаписывает его другим содержимым. Команды `validate --canonical-out` и
`triage report --out` обновляют только производные файлы своего workspace; сам
`TRIAGE` редактирует ревьюер. Запускай `summary` и `report` только после успешного `validate`. Если
проверка текущего `TRIAGE` завершилась ошибкой, не используй оставшийся от
прежнего запуска `CANONICAL_TRIAGE`: он может содержать старые решения и не
отражать текущий исходник.

`--canonical-out PATH` необязателен. `validate` без этого параметра проверяет
`TRIAGE` по `PACK` и не зависит от текущего каталога: Git-репозиторий для такой
проверки не требуется. `triage init`, `validate --canonical-out` и `triage report
--out` определяют корень репозитория от текущего каталога, поэтому их нужно
запускать внутри Git-репозитория. Запись принимается только в точные имена
артефактов внутри `.anki-repo/review/<pr-number|local>/<full-head-sha>/` или
его `snapshot-<32 lowercase hex>` варианта.
Произвольные пути, tracked файлы, `..`, symlink traversal и замена `review.json`
или `review-queue.json` запрещены. Действующие derived files проверяются по
типу и привязке к текущему snapshot; публикация выполняется атомарно под lock с
повторной проверкой входных байтов. `summary` не требует
Git-репозитория; `summary` и `report` сверяют triage с тем же исходным пакетом,
поэтому используй для них `CANONICAL_TRIAGE`, созданный текущим успешным
`validate`.

`triage init` создаёт версионируемый документ, в котором каждый элемент
`ReviewPack::all_candidates()` — кандидат статического или языкового анализатора
из общего пространства ID — явно остаётся нерассмотренным до решения ревьюера.
Группы из `review-queue.json` не копируются автоматически в
`group_decisions`: только ревьюер после самостоятельного изучения свидетельств
и окружающего кода принимает и фиксирует групповое решение в `TRIAGE`.
Основные поля документа:

```json
{
  "schema_version": 1,
  "source": {
    "snapshot": {
      "repository_id": "<portable id>",
      "base_sha": "<full SHA>",
      "head_sha": "<full SHA>",
      "merge_base_sha": "<full SHA>"
    },
    "review_pack_sha256": "<SHA256 of exact review.json bytes>",
    "candidate_count": 0
  },
  "individual_decisions": [],
  "group_decisions": [],
  "findings": [],
  "unreviewed_candidate_ids": []
}
```

Фрагмент показывает форму, а не готовый документ: `init` заполняет поля
идентичности и список кандидатов, поэтому их число и ID берутся из фактического
`PACK`. `source.snapshot` содержит переносимый `GitTarget` (`repository_id`,
`base_sha`, `head_sha`, `merge_base_sha`); абсолютный путь клона в артефакт не
записывается. `review_pack_sha256` — SHA-256 в виде 64 строчных hex-символов по
точным байтам исходного `review.json`, а `candidate_count` — число кандидатов в
объединённом списке. Совпадение одного лишь имени файла недостаточно: изменение
байтов исходного пакета, снимка Git или числа кандидатов приводит к отказу
валидации. Несовпадающий снимок Git возвращает типизированную ошибку
`baseline_mismatch`; несовпадение контрольной суммы, числа кандидатов,
неизвестные ID и другие нарушения артефакта — `review_artifact_invalid`.

Каждая запись `individual_decisions` содержит `candidate_id`, `disposition`,
`reason_code`, пояснение `explanation` и `finding_ids`. Каждая запись
`group_decisions` содержит `id`, `candidate_ids`, `representative_candidate_ids`,
`disposition`, `reason_code`, `explanation` и `finding_ids`. Каждый элемент
массива `findings` содержит `id`, `severity`, `title`, `description`,
`provenance` и `candidate_ids`. В `unreviewed_candidate_ids` перечислены исходные
кандидаты, для которых ещё нет индивидуального или группового решения.
В Markdown-отчёте заголовок и ID замечания экранируются, а `description`
выводится как блок цитаты с экранированием Markdown-символов, чтобы содержимое
замечания не меняло структуру отчёта.

Допустимые значения `disposition`: `confirmed`, `acceptable`, `false_positive`,
`not_applicable`, `uncertain`. Состояние «не рассмотрен» задаётся только
отдельным `unreviewed_candidate_ids`, а не отсутствующим решением или значением
`disposition`. Подтверждённое решение обязано ссылаться на замечание. Ссылки
`finding_ids` и `findings[].candidate_ids` проверяются взаимно: неизвестные ID и
односторонняя связь отклоняются. Для каждой пары «кандидат — замечание» обе
стороны должны содержать взаимную ссылку. Замечание может существовать без
кандидата; значение `provenance` различает `direct_candidate` (кандидат
непосредственно указал на замечание), `candidate_assisted` (сигнал помог
навигации или расследованию, а дефект установлен шире исходного сигнала) и
`independent` (замечание найдено без помощи кандидатов). Для `direct_candidate`
и `candidate_assisted` список `candidate_ids` должен быть непустым и содержать
рассмотренные кандидаты; для `independent` список пуст. Каждый кандидат у
`direct_candidate` должен иметь значение `disposition: confirmed`; для
`candidate_assisted` допустимы и другие рассмотренные значения `disposition`.
Допустимые значения `severity`: `critical`, `major`, `minor`, `trivial`.

`reason_code` — стабильный закрытый enum в `snake_case`; пояснение не заменяет
машинный код. Текущий набор: `pre_existing`, `out_of_scope`, `test_fixture`,
`machine_contract`, `technical_identifier`, `documented_invariant`,
`expected_failure_path`, `insufficient_evidence`, `duplicate_signal`, `other`.
Новые или переименованные коды требуют изменения версии публичного контракта.

Тип рассмотрения определяется структурой, а не задаётся свободной меткой:

- запись в `individual_decisions` означает, что кандидат рассмотрен индивидуально;
- `group_decisions` означает групповое решение по ровно перечисленным
  `candidate_ids`; `representative_candidate_ids` показывает, какие кандидаты
  группы непосредственно изучались как представители;
- `unreviewed_candidate_ids` означает, что решения по кандидату ещё нет.

Группа включает не менее двух уникальных `candidate_ids` и не менее одного
уникального `representative_candidate_id`; представители должны входить в
покрытую группу. Кандидат не может повторяться между группами,
`individual_decisions` и `unreviewed_candidate_ids`: все кандидаты исходного
пакета покрываются ровно одним из этих трёх способов. Значения `id` в
`group_decisions[]` и `findings[]` уникальны внутри артефакта. Неизвестные
JSON-поля и пустые обязательные ID, пояснения, названия или описания
отклоняются. Валидация также отклоняет неоднозначное покрытие, дублирующие
конфликтующие решения, неподдерживаемую версию схемы, несовпадающие значения
снимка/hash/count, неизвестные ID кандидатов и замечаний, подтверждённые
решения без замечания и решения без устойчивой причины. Частичный triage
допустим: непроверенные кандидаты сохраняются в явном виде.

`summary` выводит детерминированный `TriageSummary` (с `--json` он находится в
поле envelope `result`) со следующими ключами и смыслом:

```json
{
  "schema_version": 1,
  "total_candidates": 0,
  "reviewed_candidates": 0,
  "unreviewed_candidates": 0,
  "individual_review": {
    "decision_count": 0,
    "by_disposition": {},
    "by_reason_code": {}
  },
  "group_review": {
    "decisions": {
      "decision_count": 0,
      "by_disposition": {},
      "by_reason_code": {}
    },
    "covered_candidate_ids": 0,
    "representative_candidate_ids": 0
  },
  "by_detector": {
    "<detector>": {
      "total_candidates": 0,
      "reviewed_candidates": 0,
      "unreviewed_candidates": 0,
      "individually_reviewed_candidates": 0,
      "group_reviewed_candidates": 0,
      "finding_linked_candidates": 0,
      "covered_ids_by_disposition": {},
      "covered_ids_by_reason_code": {}
    }
  },
  "findings": {
    "total_findings": 0,
    "by_severity": {},
    "by_provenance": {}
  }
}
```

`individual_review.decision_count` и `group_review.decisions.decision_count` —
число единиц решений; `group_review.covered_candidate_ids` и
`representative_candidate_ids` — отдельные числа покрытых и непосредственно
изученных ID. В `by_detector` значения `disposition`/`reason_code` и
`finding_linked_candidates` считаются по покрытым ID кандидатов; эти показатели
не являются оценкой точности детектора. Сводка разделяет рассмотренных и
нерассмотренных кандидатов, индивидуальное и групповое покрытие, решения по
значениям `disposition`/`reason_code`, кандидатов по детектору и замечания по
`severity`/`provenance`. Markdown-отчёт повторяет агрегаты и сами замечания, но не
дублирует строки решений или тысячи кандидатов; полная трассировка остаётся в
JSON.

Новый семантический разбор не связан с `LanguageDecisions`: они по-прежнему
отвечают только за явные решения в безопасном процессе `language apply`.
Значение `disposition` для кандидата языкового анализатора не утверждает замену
и не запускает `language apply`. Если меняется проверяемый HEAD/base или исходный
пакет, собери новый пакет, создай новый triage и заново проверь решения.
Артефакт старого снимка нельзя молча переносить на новый.

```bash
anki-repo code-review triage init --help
anki-repo --json code-review triage summary --pack "$PACK" --triage "$CANONICAL_TRIAGE"
```

<a id="code-review-learning"></a>

#### Адаптивное обучение по истории ревью

`code-review learning` — добавочный локальный слой, который накапливает
проверенную историю завершённых ревью и помогает планировать следующее. Он не
является источником семантической истины: команды не создают замечаний, не
меняют `review.json`, `review-queue.json` и `semantic-triage.json`, не назначают
`disposition` и не отменяют обязательный просмотр единиц очереди. Содержательное
суждение по-прежнему делает ревьюер по актуальному коду; history даёт только
контекст и порядок.

Отсутствие истории — штатное состояние, а не ошибка. `collect`, `verify`,
`delta`, `queue validate|summary|list|group|candidate`,
`triage validate|summary|report` и `execution prepare|run|inspect|cancel|cleanup`
работают без базы learning и не создают её. Базу создаёт только записывающая
команда (`import`, `feedback record`, `policy propose`, `restore`) либо
`backup`/`export` по уже существующей истории. Операции, которым нужна
существующая база, завершаются различимым `not_found` (exit 4): `validate`,
`stats`, `patterns`, `search`, `feedback list|show`, `policy list|show|approve`,
`export`, `backup` и `forget`. `status` сообщает об отсутствующей базе с exit 0.
`recommend` без `--require-history` также завершается с exit 0 и строит документ
в режиме без learning; с `--require-history` отсутствие базы даёт `not_found`.

Локальная база по умолчанию — `.anki-repo/learning/state.sqlite` относительно
корня репозитория; `--db PATH` (alias `--database`) выбирает другую базу внутри
того же репозитория. Каталог `.anki-repo/learning/` исключён через `.gitignore`:
история не попадает в PR автоматически, а перенос между машинами делается
явными `export` и `restore`. Текущая схема базы — версия 2: открытие старой
поддерживаемой схемы применяет проверенную транзакционную миграцию; база с более
новой неизвестной схемой отклоняется без изменения данных.

Границы доверия различаются явно:

- `ast_authenticated` — запись, очередь которой прошла проверку синтаксической
  подлинности по точным Git-образам и AST. Только такие записи участвуют в
  паттернах, поиске и рекомендациях;
- `structure_only_quarantine` — запись, импортированная с `--structure-only` или
  без подтверждённой подлинности. Она сохраняется для аудита, но не участвует в
  выводах и не влияет на подсказки.

```bash
anki-repo --json code-review learning status
anki-repo --json code-review learning import --pack "$PACK" --queue "$QUEUE" --triage "$CANONICAL_TRIAGE"
anki-repo --json code-review learning patterns --detector error_path --limit 20
anki-repo --json code-review learning search --text "parse" --limit 20 --offset 0
anki-repo --json code-review learning recommend --pack "$PACK" --queue "$QUEUE" --triage "$CANONICAL_TRIAGE"
anki-repo --json code-review learning feedback record --review-id "$REVIEW_ID" --unit-id "$UNIT_ID" --kind usefulness --usefulness useful --explanation "Подсказка помогла"
anki-repo --json code-review learning export --out .anki-repo/learning/exports/archive.json
anki-repo --json code-review learning restore --db .anki-repo/learning/restored.sqlite --archive .anki-repo/learning/exports/archive.json
anki-repo --json code-review learning policy propose --signature "$SIGNATURE" --rule-id rule-runtime-error-path
anki-repo --json code-review learning forget --review-id "$REVIEW_ID" --confirm
```

`import` (alias `ingest`) принимает обязательные `--pack` и `--queue`,
необязательный `--triage`, не более одного `--execution`, `--structure-only`,
`--variant` (по умолчанию `root`; для snapshot workspace — `snapshot-<32 hex>`)
и свободную метку `--label`. Повторный импорт тех же точных байтов идемпотентен и
возвращает `noop_existing`; другие байты при той же идентичности снимка создают
аудируемую ревизию (`revision_created` с `revision_of`), а прежняя запись
помечается вытесненной, но не удаляется. `--structure-only` помечает запись
карантином вместо доверенной истории. `--execution` принимает только
`result.json` из задания с завершённым lifecycle, проверенным через его манифест,
state и source snapshot. В историю попадает компактная сводка статуса, кода или
сигнала выхода, объёмов и полноты stdout/stderr, очистки процесса и ограничений;
содержимое журналов, argv и произвольный текст ошибки не сохраняются.

`status` показывает состояние базы, не создавая её; `validate` дополнительно
проверяет версию схемы, целостность и доступность поиска. `stats` даёт
агрегированные наблюдения по странице записей (`--include-quarantine`,
`--limit`).

`patterns` показывает объяснимые структурные паттерны: поддержку в независимых
единицах, а не в числе кандидатов, покрытие решений, противоречащие единицы,
возраст случаев и нижнюю границу доли `confirmed` по интервалу Уилсона для
95 % уровня. Эта граница — мера согласованности наблюдений, а не вероятность
безопасности нового кода. Минимум поддержки — 3 независимые единицы; ниже него
вывод воздерживается. Фильтры: `--detector`, `--role`, `--code-role`,
`--origin`, `--include-quarantine`, `--limit`. `--require-supported` превращает
воздержание в явный `insufficient_evidence` (exit 3) вместо тихого вывода.

###### Что считается одной независимой линией наблюдения

Порог поддержки считается по линиям наблюдения, а не по числу записей истории:
иначе повторный импорт той же правки в новой версии набирал бы уверенность из
одного и того же случая.

- **Линия наблюдения** — это пара `(repository_id, unit_id)`, где
  `repository_id` — переносимый идентификатор совместимости точной базовой
  Git-ревизии (`GitTarget.repository_id`), а `unit_id` — sha256
  сериализованной `GroupingSignature` единицы очереди.
- `unit_id` даёт **структурную** идентичность, а не позицию в файле: пока
  дефект остаётся тем же структурным случаем, идентификатор единицы устойчив к
  переименованиям, сдвигу строк и смене версии; когда структура изменилась —
  это другое наблюдение, и сворачивать нечего.
- `repository_id` входит в линию потому, что повторы одного диапазона между
  версиями (`base` общий, `head` меняется) — это повторное чтение того же
  случая. `head_sha` и `workspace_variant` в линию намеренно не входят: смена
  версии или снимок того же состояния — то же наблюдение.
- Линию представляет **последнее** наблюдение (по времени импорта и монотонной
  ревизии истории): если решение изменилось в следующей версии, действует новое,
  а не прежнее.
- Следствие, о котором нужно знать: два независимых PR, отведённых от **одной и
  той же** базовой ревизии, тоже схлопываются в одну линию. Это осознанное
  консервативное поведение: поддержка занижается, а не завышается. Разные базы
  остаются разными линиями.

Числа отчёта показывают это явно и не смешиваются:

| Поле | Смысл |
|---|---|
| `support_units` | число независимых линий наблюдения; именно оно сравнивается с минимумом поддержки и стоит в знаменателе Уилсона |
| `support_reviews` | число записей ревью, наблюдавших срез: сырые запуски, включая повторы |
| `revised_units` | сколько единиц среза оказались повторными наблюдениями той же линии |

Инвариант: `support_units + revised_units` равно числу единиц среза, поэтому
`revised_units` всегда объясняет разницу между сырыми наблюдениями и
независимой поддержкой. «Не рассмотрено» — не позиция, а нехватка информации:
такие единицы считаются отдельно (`unresolved_units`), не образуют
противоречия и не позволяют выдать вывод по одному решению.

Связь повторяющихся случаев импорт доказывает явно и хранит в
`learning_case_link`: `structural_repeat` — тот же структурный дефект в другой
версии того же ревью, `same_iteration` — повторное чтение того же неизменного
случая, `unknown` — связь не установлена доказанно. Отсутствие доказанной связи
остаётся `unknown`, а не догадкой: в отчётах и `search` вид связи виден в поле
`link` каждой ссылки на случай.

`search` (alias `similar`) ищет аналогичные исторические случаи локально: FTS5
при доступности и подстрочный fallback без него (`fts5_used` в результате
честно называет режим). Текстовая подстрока ищет по пояснениям решений ревьюера
и текстам замечаний — тому, что ревьюер записал в `TRIAGE`, — а не по исходному
коду: код в историю не копируется, и `review.json` остаётся единственным
источником свидетельств. Фильтры: `--text` (не короче двух символов),
`--detector`, `--surface`, `--origin`, `--role`, `--code-role`, `--disposition`,
`--provenance`, `--severity`, `--repository`, страница — `--limit` и `--offset`.

Поиск — читатель истории, а не основание для вывода, поэтому карантинные записи
пониженного доверия из результатов **исключены по умолчанию** — так же, как в
`stats` и `patterns`: найденная аналогия становится вспомогательным контекстом
ревью, и смешивать её с доверенной историей без явного согласия нельзя. Включить
их можно только явно, флагом `--include-quarantine`. Доверие не скрывается:
человекочитаемый вывод называет применённый фильтр и печатает статус доверия
каждого возвращённого случая, а машинный результат несёт `trust` в каждом
`SearchCase` и фактический фильтр страницы в аддитивном поле
`include_quarantine` (версия схемы результата поиска — 2).

`recommend` строит версионируемый документ подсказок для конкретного снимка:
`--pack`, `--queue`, `--triage`, `--structure-only`, `--variant`, `--label`,
`--limit`, `--case-limit`, `--history-revision`, `--policy-version`,
`--without-learning`, `--require-history` и `--out`. Подсказки выполняют жёсткие
guardrails: baseline priority и порядок `review-queue.json` не меняются, ни одна
единица не исключается из обязательного просмотра, а единицы с неизвестной
классификацией и защищённые единицы (`security`, `suppression`, `error_path`,
`runtime_boundary`, высокий приоритет) сохраняют обязательность даже при
низкошумной истории. Документ детерминирован для тех же входов, истории и версии
политики: время в него не попадает. Явные `--history-revision` и
`--policy-version` проверяются и при расхождении дают `source_changed` (exit 7)
и `learning_schema_unsupported` (exit 3). `--require-history` требует
непустую доверенную историю (`not_found`, exit 4 — если базы нет;
`insufficient_evidence`, exit 3 — если доверенных единиц нет).
`--without-learning` строит документ с явным `learning_disabled: true`.

`feedback` — аудируемая обратная связь. `record` (alias `revise`) принимает
`--review-id`, `--unit-id`, необязательный `--candidate-id`, `--kind`
(`usefulness` или `semantic-outcome-revision`), `--action` (`append` по
умолчанию, `retract`, `supersede`), `--disposition`, `--usefulness`,
`--supersedes-event-id`, обязательное `--explanation`, `--provenance` (по
умолчанию `reviewer`) и необязательный явный `--event-id`. Событие с тем же
содержанием не дублируется, а попытка записать другое содержание под уже
занятым `event_id` завершается `learning_conflict` (exit 7). `list` показывает
журнал случая, `show` — одно событие. Содержательная правка меняет действующий
исход и пересчёт паттернов, оценка полезности — нет.

`export` собирает переносимый архив с digest тела и манифестом (без сырых
execution logs, credentials и содержимого временных worktrees), `backup` делает
транзакционный снимок базы (`VACUUM INTO`), `restore` повторно проверяет digest
архива перед восстановлением и идемпотентен для уже восстановленных записей.

Архив версии 3 переносит поисковые случаи (`manifest.search_cases`), сводки
проверенных execution results и структурные ссылки кандидатов, но не их source
snippets. Архив версии 2 переносит поисковые случаи: тексты
пояснений ревьюера существуют только в них, а решения в архив не входят, поэтому
пересобрать поиск из восстановленных записей нельзя. Старые snippets из архива
версии 2 при восстановлении отбрасываются. После `restore` локальный
поиск находит те же `case_id`, что и до экспорта, включая случаи решений, а
индекс FTS5 пересобирается из `learning_search`. Архив версии 1 принимается: он
переносит только исходные записи, а `restore` честно сообщает в `limitations`,
что поисковых случаев в нём нет.

`forget --review-id ID --confirm` явно и атомарно удаляет выбранную запись
истории и связанные с ней единицы, кандидаты, решения, findings, поисковые
записи, feedback, связи и предложения policy. Команда не удаляет исходные review
artifacts и утверждённые policy files. Уже созданные `export` и `backup` —
отдельные файлы, их при необходимости удаляют отдельно.

Пути вывода производных артефактов learning (`export --out`, `backup --out`,
`policy approve --out`) проверяет та же модель публикации, что и остальные
артефакты code review: служебные каталоги `decks/**` и данные Git, символические
ссылки и чужое содержимое отвергаются (`invalid_request` / exit 3 либо
`review_artifact_conflict` / exit 7). Дополнительно артефакт learning обязан
оставаться внутри текущего репозитория: история, архив и снимок базы не
переносят путь за пределы клона. `recommend --out` уже, чем остальные: он
принимает только `recommendations.json` в рабочей области своего `--pack`
(`.anki-repo/review/<PR|local>/<HEAD>[/snapshot-<32 hex>]/`), поэтому запись в
чужую область или через ссылку отвергается.

`policy` — жизненный цикл предложений постоянных правил: `propose` (по
`--signature` и `--rule-id`), `list`, `show --id` и `approve --id --out --note`.
Предложение никогда не применяется само: `auto_applied` всегда `false`, а
утверждённый артефакт материализуется по обязательному `--out`. Рекомендуемое
значение — `.anki-repo/policies/learning-policy.json`, вне игнорируемого
каталога истории; попадание файла в Git остаётся решением человека. SQLite не является владельцем утверждённой политики: база
хранит предложение и историю, а не действующие правила. Предложение без
подтверждающих случаев утвердить нельзя (`insufficient_evidence`).

Пределы вывода и пагинация:

| Команда | По умолчанию | Жёсткий максимум | Страница |
|---|---|---|---|
| `stats --limit` | 50 | 200 | нет |
| `patterns --limit` | 20 | 200 | нет |
| `search --limit` / `--offset` | 50 | 200 | есть |
| `recommend --limit` | 50 | 200 | нет |
| `recommend --case-limit` | 3 | 10 | нет |
| `policy list --limit` | 50 | 200 | нет |

Человекочитаемый вывод сообщает, сколько записей показано из найденного, и
называет реальное действие для продолжения (`--limit`, `--offset`). Полные
списки идентификаторов кандидатов не печатаются ни в текстовом, ни в машинном
выводе: остаются счётчик и ограниченный срез, а точные идентификаторы доступны
в исходном `review.json`.

Публикация производных артефактов подчиняется тем же правилам, что и остальной
набор: произвольный `--out` вне репозитория, `..`, symlink, `decks/**`,
`.git/**` и tracked workspace отвергаются до записи; повтор тех же байтов
идемпотентен, другое содержимое даёт `review_artifact_conflict` (exit 7).
`recommend --out` принимает только `recommendations.json` рабочей области
своего `--pack`; `export`, `backup` и `policy approve` пишут по явному пути,
выбранному вызывающей стороной.

### `language scan|check|apply`

`scan` извлекает человеческий текст с учётом формата файла. Он проверяет полные
релевантные файлы, а не только добавленные строки: комментарии, документацию и
человеческие строки Rust, пояснения Markdown, подходящие значения конфигураций.
Идентификаторы, машинные ключи, внешние литералы и технические токены требуют
учёта контракта, а не механического перевода. Предметные данные `decks/**`
не входят в обычную политику русского текста исходников. Каталоги `media/`
на любом уровне, `.git/`, `target/` и `.anki-repo/review/` также исключены из
сканирования и замены. Начальный YAML-блок метаданных Markdown, включая
`SKILL.md`, целиком считается машинной поверхностью: ключи, идентификаторы и
значения внутри него не сканируются и не заменяются. Незакрытый начальный блок
также исключён. Тела и разделители shell here-doc исключены как потенциально
машинные данные; неоднозначное начало `<<` исключает оставшийся текст файла.
После закрытого блока сканирование продолжается; here-string `<<<` допускает
обычное сканирование строкового литерала. Человеческие значения
отдельных конфигурационных файлов анализируются по правилам своего формата.

Источник выбирается явно: повторяемый `--path PATH` относительно `--root DIR`
(по умолчанию `.`) либо `--pack PACK` с областью изменений и содержимым HEAD сохранённого
пакета ревью. Требуется `--out PATH` для полного артефакта сканирования.
`LanguageScan` не содержит поля `origin`: для `scan --path` происхождение
относительно диапазона Git не определено. При сравнении и текстовом выводе
пакета ревью языковые кандидаты проецируются в общую схему свидетельств;
именно там `origin` определяется по пересечению полного многострочного диапазона
кандидата с изменёнными строками. Содержательную классификацию и допустимость
текста определяет ревьюер.

`check --scan SCAN` перечитывает исходные пути после ручных правок относительно
`--root DIR`; необязательный `--out PATH` сохраняет обновлённый артефакт сканирования.
Этот результат говорит о новых сигналах детекторов, а не о качестве перевода.

`apply --decisions PATH` проверяет явно подготовленные решения. Без `--apply`
выполняется только проверка предусловий; с ним применяются исключительно
решения `replace`. Решение `allow` не меняет текст. Инструмент не переводит текст
сам и не исправляет остальные кандидаты ревью кода.

До первой записи проверяются все предусловия набора: допустимость путей,
хеш исходного файла, точное ожидаемое содержимое и отсутствие пересекающихся
замен. Устаревшее решение отклоняется целиком; его нельзя применять после
изменения файла, молча пересчитав позиции. Повторное сканирование и новая семантическая
проверка создают актуальные решения. Для поддерживаемых текстовых файлов
сохраняются кодировка и окончания строк.

```bash
anki-repo language scan --pack "$CURRENT_PACK" --out "$SCAN_ARTIFACT"
anki-repo language scan --path src/lib.rs --out "$SCAN_ARTIFACT"
anki-repo language apply --decisions "$DECISIONS_ARTIFACT"
# Запись — только после проверки решений и dry-run:
anki-repo language apply --decisions "$DECISIONS_ARTIFACT" --apply
anki-repo language check --scan "$SCAN_ARTIFACT"
```

Пути в примерах иллюстративны. Артефакты сканирования и решений сохраняются по
указанным путям вне `decks/**`; если они находятся в репозитории, то видны в
Git и могут быть включены в PR вручную. Команда не публикует их автоматически.
JSON `language check` содержит `files_total`, `candidates_total`,
`candidates_truncated`, `skipped_total` и не более 20 примеров в `candidates`.
Поле `text` каждого примера ограничено 120 символами, а `text_truncated` указывает
усечение. Полный повторный результат доступен в артефакте, если передан `--out PATH`.

#### Машинный контракт

Пакет ревью, результаты сканирования, решения и сравнение — разные версионируемые
JSON-документы. Нельзя подставлять один вместо другого или считать краткий
stdout полным артефактом. При подготовке решений используй схемы сканирования и решений
и точные идентичности кандидатов из соответствующего прогона; не угадывай
поля по отображаемой строке. Общий JSON-конверт CLI описан в разделе
«Режимы вывода», ошибки — в «Коды возврата». Наличие кандидатов или диагностик
само по себе не равно ошибке команды или подтверждённому дефекту. Актуальные
аргументы каждой подкоманды доступны через `--help`.

#### Схемы артефактов версии 1

`review.json` — объект `ReviewPack` со следующими верхнеуровневыми ключами:
`schema_version`, `target`, `scope`, `diagnostics`, `candidates`, `language`,
`dependencies`, `tests`, `suppressions`, `risk_surfaces`, `tool_runs`.
`target` содержит `repository_id`, `base_sha`, `head_sha` и `merge_base_sha`.
`repository_id` — SHA-256 строки `anki-repo:git-base:v1:<base_sha>`: переносимый
якорь базового коммита, а не удостоверение происхождения репозитория. Он не
зависит от абсолютного пути клона или адреса удалённого репозитория. `scan --pack`
читает точные объекты base/HEAD в текущем Git. `verify` разрешает base из
исходного пакета и новый HEAD, затем проверяет общий base и merge-base;
`delta` требует их совпадения в сохранённых пакетах. Совместимый пакет принимается в
другом клоне с теми же объектами. Имена ссылок в пакете не сохраняются: разные
имена, разрешающиеся в те же SHA, дают тот же снимок.
`scope` содержит `merge_base_sha`, `text_image_limit_bytes` и отсортированный
`files`. Каждый элемент `files` описывает `path`, `previous_path`, `status`,
`additions`, `deletions`, `category`, `surfaces`, `binary`, состояния и размеры
файлов до и после, идентификаторы объектов Git и диапазоны изменённых строк.

`diagnostics` — структурированные сообщения Cargo/rustc/Clippy со `severity`,
`code`, `message`, `spans`, `children` и `source`. `candidates` — статические
сигналы с ключами `id`, `detector`, `path`, `line`, `column`, `snippet`, `origin`,
`signals`, `source` и `metadata`. Допустимые `origin`: `introduced_or_changed`,
`pre_existing`, `unknown`. Происхождение статических сигналов определяется
по изменённым диапазонам конкретной позиции, а не по совпадению текста с любой
строкой базы. Если позиционные свидетельства отсутствуют, а образы
различаются, происхождение остаётся `unknown`; идентичные полные образы дают
`pre_existing`. Сигнал `assertion_removed` отражает уменьшение числа assertions
в тестовом контексте всего файла; он не указывает удалённую строку.
Типы детекторов охватывают абсолютные пути, локальные
адреса сервисов, привязку к истории разработки, подавления, обработку ошибок и небезопасный код,
изменения тестов, зависимости, конфигурационные, сгенерированные файлы, skills и поверхности
безопасности. Это навигационные кандидаты, требующие проверки ревьюером.

`review-queue.json` — отдельный артефакт со своей `schema_version` и ключами
`source`, `classifications`, `units`, `summary`. `source` содержит переносимый
снимок Git, SHA-256 точных байтов исходного `review.json` и число уникальных
идентификаторов кандидатов. В `classifications` каждому исходному
идентификатору соответствует `StructuralClassification`: поверхности файла
`surfaces` и категория `file_category`, независимый контекст выполнения
`execution`, происхождение `origin`, структурная роль `role`, роль текста
`text_role`, роль кода `code_role`, основания классификации и доказанная
синтаксическая подпись. Если классификацию доказать нельзя, соответствующее
поле сохраняет `unknown` или `null`; кандидат при этом остаётся в очереди.

`units` содержат отдельную единицу `individual` с одним исходным идентификатором
либо группу `group` с полным отсортированным `candidate_ids`, ограниченным
списком `representative_candidate_ids`, структурной подписью, `priority`,
объясняющими `priority_signals` и статистикой. `summary` считает исходных
кандидатов, единицы, покрытие группами, представителей, неизвестные случаи и
распределения по приоритету, детекторам, поверхностям и ролям. Допустимые
значения `priority` — `high`, `normal`, `low`; это порядок навигации, а не
уровень серьёзности или семантический вердикт. Неизвестные JSON-поля запрещены.
Валидатор проверяет точный хеш источника и переносимую идентичность Git-снимка,
полное однократное покрытие `candidate_ids`, детерминированные идентификаторы групп и выбор
представителей, однородность подписей и соответствие сводки. Очередь не
содержит семантических решений или замечаний ревьюера.

`language` использует собственную `schema_version` и содержит `files`,
`candidates`, `skipped`. Кандидат хранит `id`, путь и SHA исходного файла,
байтовые `start`/`end`, `line`/`column`, `context`, точный `text` и `signals`.
Артефакт решений имеет `{ "schema_version": 1, "decisions": [...] }`; каждое
решение содержит исходный `candidate`, `action` (`replace`, `allow`, `ignore`,
`needs_review`), `replacement` и `reason`. `replace` требует непустые `reason`
и `replacement`. Артефакт сравнения имеет `schema_version`, `before`, `after`, `candidates`,
`diagnostics`, `tool_runs`; статусы `still_present`, `gone`, `changed`, `new`
описывают только наблюдения детекторов.

Полные исходные файлы не копируются в `review.json`. Даже с `--run-clippy`
Clippy запускается только когда рабочая копия соответствует сохранённому `head_sha`,
отслеживаемые файлы не изменены, а среди неотслеживаемых файлов нет известных
входов Cargo: `*.rs`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain`,
`rust-toolchain.toml` или `.cargo/config[.toml]`. Эти входы проверяются и среди
игнорируемых Git файлов; при такой проверке содержимое `target/**` исключается.
Если Git не смог проверить список игнорируемых входов, Clippy пропускается.
Локальные данные `decks/**`, `.asset-store/**`, `.anki-repo/review/**` и
`.codex/local/**`, а также прочие неотслеживаемые файлы, например `notes.txt`,
не блокируют запуск. Это проверка известных входов сборки; она не ограничивает
произвольное чтение файлов из `build.rs`. При несоответствии в `tool_runs`
записывается `skipped` с причиной.
Статусы Clippy:
`unavailable`, `failed`, `success_without_diagnostics`, `diagnostics`, `skipped`.
Сборщик использует локальный `cargo clippy --workspace --all-targets --locked
--offline --quiet --message-format=json`; неизвестные поля JSON и будущие уровни
серьёзности не ломают разбор. См. [формат JSON rustc](https://doc.rust-lang.org/rustc/json.html)
и [Cargo external tools](https://doc.rust-lang.org/cargo/reference/external-tools.html).

### `inspect`

Компактное описание структуры экспорта: корневая колода, число узлов колоды,
общее число заметок, модели заметок с их полями в порядке `ord`, конфигурации
колод, сводка по медиа и распределение заметок по путям колод.

```bash
anki-repo inspect decks/japanese/words/Words__N1
anki-repo inspect decks/japanese/words/Words__N1 --verbose
```

`--verbose` добавляет UUID, дерево колод от родителя к детям, шаблоны карточек, статистику
по `guid` и ограниченную выборку диагностик (в том числе примеры отсутствующих и
необъявленных имён медиафайлов). В JSON-режиме подробная часть лежит в
`result.verbose` и появляется только при `--verbose`.

### `find`

Поиск заметок по стабильным критериям. Нужен ровно один критерий: `--guid` либо
`--field` вместе с `--value`.

```bash
# поиск по guid: identity lookup
anki-repo find decks/japanese/words/Words__N1 --guid 'D!TAYVuHi,'

# поиск по сырому значению поля: содержит подстроку
anki-repo find decks/japanese/words/Words__N1 --field Слово --value 偶然

# общий поиск по любому имени поля: подстрока и точное совпадение
anki-repo find decks/japanese/words/Words__N2 --field 'Часть речи' --value Существительное
anki-repo find decks/japanese/words/Words__N1 --field 'Часть речи' --value Существительное --match exact
```

Поведение:

- `--field` задаёт имя поля, `--match` принимает `contains` (по умолчанию) или
  `exact` и применяется только вместе с `--field`. Имя поля проверяется против
  фактических `note_models[].flds[].name` экспорта: неизвестное поле — доменная
  ошибка `unknown_field` (код возврата 3), а не пустой ответ.
- Отбора по «слову» как отдельной сущности у команды нет: имя поля всегда
  называет вызывающая сторона, поэтому `--field X --value Y --match contains`
  выражает ровно то же, что раньше выражал удалённый флаг `--word` (см.
  «Изменения публичного контракта»).
- `--deck` ограничивает поиск колодой и всеми её вложенными колодами.
- `--limit` (по умолчанию 20, максимум 500) ограничивает размер вывода, но не
  сам поиск: `matched_total` считает все совпадения, а `returned`/`truncated`
  показывают, что именно попало в ответ.
- Сопоставление чувствительно к регистру и выполняется по сырым значениям поля,
  без нормализации HTML.

### `stats`

Структурная агрегированная статистика: число заметок по колодам, по моделям,
использование конфигураций, разбивка полей на пустые и непустые, сводка по
медиафайлам.

```bash
anki-repo stats decks/japanese/words/Words__N3
anki-repo stats decks/japanese/words/Words__N3 --group-by 'Часть речи' --top 10
```

- `--group-by` считает распределение по сырым значениям указанного поля; `--top`
  (по умолчанию 20, максимум 500) ограничивает размер вывода, а
  `distinct_values` и `truncated` показывают полную картину.
- Столбцы распределения сортируются по убыванию количества, затем по значению.

### `validate`

Детерминированная проверка структурной целостности одного экспорта.

```bash
anki-repo validate decks/japanese/words/Words__N1
anki-repo --json validate decks/japanese/words/Words__N1
```

`valid` равно `true`, если не найдено ни одной проблемы уровня `ERROR`.
Предупреждения (`WARNING`) и информационные отметки (`INFO`) не делают экспорт
невалидным. Проблемы пути (нет каталога, нет `deck.json`) — это доменная ошибка
с кодом возврата 3, а проблемы содержимого (включая невалидный JSON) — это проблемы с
кодом возврата 6.

Уровни и коды проблем:

| Уровень | Коды |
|---|---|
| `ERROR` | `invalid_json`, `root_not_deck`, `schema_invalid`, `node_not_deck`, `duplicate_note_model_uuid`, `duplicate_deck_config_uuid`, `note_model_identity_missing`, `deck_config_identity_missing`, `note_model_uuid_missing`, `note_model_unresolved`, `deck_config_unresolved`, `note_fields_count_mismatch`, `note_field_value_not_string`, `note_guid_missing`, `duplicate_note_guid`, `field_name_duplicate`, `field_ord_invalid`, `field_ord_negative`, `field_ord_duplicate`, `field_ord_out_of_range`, `field_ord_gap`, `template_field_unresolved` |
| `WARNING` | `media_reference_undeclared`, `media_files_duplicate`, `media_physical_missing`, `media_dir_missing`, `media_name_not_basename`, `template_construct_unchecked`, `deck_config_uuid_missing`, `deck_name_missing`, `conflicting_note_model_definition`, `conflicting_deck_config_definition`, `template_ord_invalid`, `template_ord_duplicate` |
| `INFO` | `export_summary`, `media_physical_unused`, `note_model_unused`, `deck_config_unused`, `empty_field_values`, `issues_truncated` |

Соглашения, важные для интерпретации результата:

- Отсутствующий физически медиафайл — это `WARNING`, а не `ERROR`: политика
  хранения медиа в репозитории отдельно не определена.
- Имена медиафайлов сравниваются только по имени файла без каталога; пути из `media_files` никогда не
  используются для доступа к файловой системе.
- Повторное объявление одной и той же модели/конфигурации с тем же определением
  (обычная ситуация во вложенных узлах CrowdAnki) не считается ошибкой; конфликт
  разных определений под одним UUID — это `WARNING`. Сравниваются только
  смысловые части объявления: для модели — `name` и список `flds` (`name` + `ord`),
  для конфигурации — `name`. Различия в `tmpls`, `css` и параметрах
  планировщика эта проверка не сравнивает.
- Ограниченный парсер шаблонов проверяет только простые ссылки вида
  `{{Поле}}` и `{{tts ja_JP:Поле}}`: если хотя бы один сегмент конструкции
  совпадает с именем поля модели, ссылка считается известной. Незакрытый `{{`, а
  также конструкции с фильтрами, в которых не найдено ни одного известного
  имени, помечаются как `template_construct_unchecked` (`WARNING`), чтобы не
  выдавать ложных ошибок. Парность секций `{{#X}}`/`{{/X}}` и прочая логика
  шаблонов не проверяются.
- Число проблем одного кода ограничено; при усечении добавляется
  `issues_truncated` с числом опущенных записей.
- Пустой `guid` — это `note_guid_missing` (`ERROR`); как дубликат он не
  репортится и в индекс `guid` не попадает, поэтому `find --guid ''` ничего не
  находит.

### `qa`

Детерминированные замечания по содержимому карточек. Правила не обращаются ни к
чему, кроме самого экспорта, и не зависят от текущего состояния репозитория.

```bash
anki-repo qa decks/japanese/words/Words__N1
anki-repo qa decks/japanese/words/Words__N3 --code empty_field_value --max-per-code 5
anki-repo --json qa decks/japanese/words/Words__N5 > findings.json
```

Реестр правил (порядок вывода замечания — это порядок реестра, он же порядок
`rules` в JSON):

| Код | Уровень | Что находит |
|---|---|---|
| `empty_field_value` | `warning` | строковое значение поля равно `""` |
| `leading_whitespace` | `warning` | значение начинается с пробельного символа |
| `trailing_whitespace` | `warning` | значение заканчивается пробельным символом |
| `forbidden_white_span` | `error` | `<span>` с белым цветом текста в `style` |
| `duplicate_note_content` | `warning` | несколько заметок одной модели с полностью совпадающим содержимым |

Поведение:

- `--code` можно повторять: вывод ограничивается указанными кодами. Неизвестный
  код — доменная ошибка `unknown_qa_code` (код возврата 3), а не пустой ответ:
  опечатка не должна выглядеть как «проблем нет».
- `--max-per-code` (по умолчанию 20, максимум 200) ограничивает число замечаний
  по каждому коду в выводе, но не сами подсчёты: `findings_total` и `by_code`
  описывают все замечания выбранных кодов, а `truncated` показывает, осталось ли
  что-то за пределами вывода. `rules[].findings` при этом не фильтруется
  аргументами и всегда считает весь экспорт по всем правилам.
- Уровень `error` — это тяжесть проблемы для читателя, а не отказ: `qa` завершается
  с кодом `0` и при найденных замечаниях уровня `error`.
- Значение поля из одних пробельных символов даёт сразу два замечания:
  `leading_whitespace` и `trailing_whitespace`.
- Пустое значение — это не «отсутствующее»: замечание получают и `""`, и строка из
  пробелов; `null` и нестроковое значение не считаются пустым полем (это предмет
  `validate`).
- `duplicate_note_content` сравнивает полный набор сырых полей заметки по позициям
  для одной и той же модели, без нормализации HTML и пробелов. Правило не выделяет
  «главное» поле: понятие главного поля принадлежит конкретной модели заметок, а не
  формату CrowdAnki, поэтому у набора инструментов нет корректной универсальной семантики для
  него. Разделить заметки по значению выбранного поля агент может явным
  `--field`/`--value` в `find` и `review`, где имя поля называет вызывающая сторона.
- Реестр состоит ровно из этих пяти кодов. Правило `duplicate_primary_field`
  удалено осознанно, вместе с ним ушло и понятие «поля `Слово`» из реестра QA (см.
  «Изменения публичного контракта»); попытка запросить удалённый код — доменная
  ошибка `unknown_qa_code`, а не пустой ответ.
- Ни одно правило не зависит от имён полей и моделей: одинаковый набор значений
  под другими именами полей и другой моделью даёт тот же набор замечаний.
- Замечания никогда не делают экспорт структурно невалидным и не блокируют `edit`.
  Шкала `error | warning | info` — это тяжесть дефекта для читателя, независимая от
  шкалы `validate`: QA `error` не является ошибкой структуры экспорта.
- Замечание может попасть в заметку, которую нельзя исполнить: у неё не разрешается
  модель, нет `guid` или `guid` не уникален. Такие замечания **помечаются**
  `addressable: false` и считаются в `unaddressable_findings`, а не исчезают:
  структурную причину называет `validate`, а `qa` не выдаёт неисполнимый адрес за
  обычную цель `edit`.
- Правила-дубликаты описывают группу целиком: `group_size` — число участников,
  `related_note_indices` и `related_guids` — участники группы в каноническом
  порядке исходного замечания, причём владелец замечания входит в список (`review` в своём
  `related` владельца наоборот исключает). Список ограничен 20 участниками
  (`MAX_RELATED_NOTES`), и тогда `related_truncated: true`: группа никогда не
  обрезается молча.

Каждое замечание адресуется позицией заметки в экспорте (`note_index`), `guid`,
путём колоды, моделью и парой «имя поля + `ord`», а `evidence` несёт ограниченные
выборки: длину значения, усечённый образец и детали конкретного правила
(например, `boundary` для пробельных правил и `first_tag` для `forbidden_white_span`).
Данные группы в `evidence` не дублируются: они лежат в полях `group_size`,
`related_note_indices` и `related_guids`.

### `review`

Компактный ограниченный пакет заметок для внешнего ревью. В отличие от `qa`, который
описывает проблемы, `review` отдаёт то, что нужно прочитать и обдумать: поля
заметки в порядке `ord` и уже найденные по ней замечания QA.

```bash
# отобрать заметки по найденной проблеме
anki-repo review decks/japanese/words/Words__N1 --qa-code empty_field_value --limit 25

# следующая страница
anki-repo review decks/japanese/words/Words__N1 --qa-code empty_field_value --offset 25

# выбор по содержимому и точный lookup
anki-repo review decks/japanese/words/Words__N2 --field 'Часть речи' --value Существительное
anki-repo review decks/japanese/words/Words__N1 --guid 'D!TAYVuHi,'
```

Ровно один критерий отбора обязателен:

| Критерий | Значение |
|---|---|
| `--all` | все заметки области |
| `--guid` | одна заметка по `guid` |
| `--field` + `--value` | сопоставление по имени поля; `--match contains` (по умолчанию) или `exact` |
| `--qa-code` | заметки с замечанием указанного кода QA |

`--deck` ограничивает область колодой и её вложенными колодами, `--offset`
пропускает выбранные заметки, `--limit` (по умолчанию 25, максимум 200) задаёт
размер страницы. В ответе есть `total_selected`, `returned`, `truncated` и
`next_offset`; `next_offset` равен `null` на последней странице. Отбор и
разрешение имён полей — та же реализация, что у `find`, поэтому неизвестное поле,
неизвестная колода или неизвестный `guid` дают те же ошибки и те же коды возврата.

`review` — команда чтения и пагинации, а не поиска «хоть чего-нибудь»: пустая
страница (фильтр без совпадений или `--offset` за концом выборки) — это успешный
ответ с `returned: 0` и код возврата `0`, иначе пагинация не могла бы завершаться.
Исключение — `--guid`: он адресует конкретную заметку, поэтому её отсутствие
остаётся ошибкой `not_found` (код возврата 4), а неоднозначный `guid` — `ambiguous`
(код возврата 5).

Что попадает в пакете:

- Заметки без исполнимо адресуемого `guid` в пакете не выводятся: без `guid`, с
  пустым `guid` или с `guid`, встречающимся больше одного раза (адрес неоднозначен,
  поэтому исключаются **все** такие вхождения). Их число видно в
  `excluded_unaddressable`; `notes_total` при этом описывает экспорт целиком, а не
  страницу. Пустая страница из-за этого исключения не молчит: счётчик объясняет
  причину.
- `--qa-code` для правил-дубликатов приводит участников группы, а не только
  владельца замечания: иначе группа потеряла бы остальных заметок на пути
  `qa → review`. Владелец несёт само замечание (с `group_size` и `related` —
  участниками, кроме себя), а каждый участник — `group_membership` со ссылкой на
  владельца (`code`, `owner_note_index`, `owner_guid`, `group_size`).
  Список участников приходит из результата домена и ограничен
  `MAX_RELATED_NOTES` (20): в группе из 30 заметок пакет получит владельца и 20
  участников, а `related_truncated: true` в замечании владельца покажет, что
  список неполон. Обещать «всех участников» для группы больше предела нельзя:
  чтобы увидеть остальных, нужен отдельный обход (`review --all` или `--field`).
- `--all`, `--guid`, `--field` и `--qa-code` группы не расширяют: они отбирают ровно
  то, что означает их критерий.

### `review-check`

Проверка предложений внешнего агента против **текущего** состояния экспорта.
Команда только читает: она не пишет ни `deck.json`, ни вспомогательных файлов.

```bash
# проверить предложения и получить готовый запрос для `edit`
anki-repo --json review-check decks/japanese/words/Words__N1 \
  --proposals proposals.json | jq .result.edit_request > request.json

# то же со stdin
anki-repo review-check decks/japanese/words/Words__N1 --proposals - < proposals.json

# готовый запрос уходит в существующую границу записи
anki-repo edit decks/japanese/words/Words__N1 --request request.json
anki-repo edit decks/japanese/words/Words__N1 --request request.json --apply
anki-repo validate decks/japanese/words/Words__N1
```

У команды собственный версионируемый документ предложений, а не запрос `edit`:

```json
{
  "schema_version": 1,
  "proposals": [
    {
      "proposal_id": "p0",
      "guid": "guid-1",
      "field": "Пример",
      "expected": "",
      "replacement": "пример-1",
      "reason": "в колоде пустой пример"
    }
  ]
}
```

`proposal_id` и `reason` — часть контракта предложения: первый становится
`edit_id` в выпущенном запросе, второй остаётся метаданными ревью (в отчёте он
усечён до безопасной длины, а в `edit_request` не переносится вовсе). Неизвестные
ключи запрещены: документ предложений — отдельный публичный вход, поэтому он не
принимает поля чужой формы, а ошибки называют именно его словарь. `review-check`
переиспользует внутренний разбор и разрешение целей `edit`, поэтому выпущенный
`edit_request` принимается `edit` без переупаковки.

Исход предложения:

| Статус | Условие | Попадает в `edit_request` |
|---|---|---|
| `valid` | цель разрешается, текущее значение равно `expected` и отличается от `replacement` | да |
| `already_correct` | текущее значение равно и `expected`, и `replacement` | нет |
| `already_applied` | текущее значение уже равно `replacement` | нет |
| `conflict` | текущее значение не совпало ни с `expected`, ни с `replacement` | нет |
| `invalid` | цель не разрешается: нет заметки, нет поля, поле не редактируется как строка, `guid` неоднозначен | нет |

`problem` для `invalid`-предложений называется по существу проверки:
`note_not_found`, `unknown_field`, `ambiguous_guid`, `field_not_resolvable`.
Последние два случая `edit` для той же цели описывает общим кодом
`internal_error` и прекращает работу целиком; `review-check` этого не повторяет —
неразрешимая цель здесь неисполнимое предложение в отчёте, а не внутренняя ошибка
инструмента, и остальные предложения всё равно проверяются.

Итог и код возврата:

| `outcome` | Условие | Код возврата |
|---|---|---|
| `ok` | нет ни одного `invalid` и ни одного `conflict` | `0` |
| `stale` | есть хотя бы один `conflict`: представление агента устарело | `7` |
| `invalid` | есть хотя бы один `invalid`; при неоднозначном `guid` — `5`, иначе при отсутствующей заметке — `4`, иначе `3` | `5` / `4` / `3` |

`edit_request` присутствует только при `outcome: ok`, хотя бы одном `valid`
предложении и правимом исходнике (`source_editable: true`): пустой `edits`
нарушил бы контракт `edit`, а запрос, собранный из частично неверного документа,
был бы молчаливой правкой «чего получилось». `expected` в выпущенном запросе
переносится из предложения агента, и это безопасно: статус `valid` получают
только предложения, чей `expected` уже совпал с фактическим текущим значением.

Поэтому `review-check` проверяет ещё и сам исходник — ровно теми же условиями,
на которых останавливается `edit` (общая функция, а не вторая реализация):

| Блокер | Код в `source_blockers` | Код возврата |
|---|---|---|
| `deck.json` не в канонической форме | `source_not_canonical` | `3` |
| в экспорте есть `ERROR` | `export_invalid` | `6` |
| неоднозначный порядок полей модели (`WARNING conflicting_note_model_definition`) | `export_not_mutable` | `6` |

Отчёт по предложениям в этом случае всё равно печатается: статусы, счётчики и
`proposals` остаются полезными агенту, а `source_editable: false` и
`source_blockers` объясняют, почему запрос не выпущен. Код возврата при этом
называет причину блокировки — неправимый исходник делает неисполнимым любой
запрос, и принимать такой `ok` за готовность к записи нельзя.

`stale` и `invalid` — это результат проверки, а не отказ команды, поэтому и в
обычном, и в JSON-режиме отчёт формируется полностью (в JSON он лежит в
`result`, а не в `error`), и только код возврата сигнализирует о ненулевом исходе.
Так же ведёт себя `validate` с кодом возврата 6.

Отчёт ограничен (`proposals` — до 50 записей, `proposals_truncated`), но счётчики
`counts` и сам `edit_request` не усекаются: усечение затрагивает только печать, и
человеческий вывод говорит об этом прямо, не обещая «полного списка в `--json`».

Проблемы уровня всего документа остаются доменными ошибками с кодом возврата 3 (пока
документ не разобран, проверять нечего). Собственный словарь предложений даёт
`invalid_request` с `details.reason`: `malformed_proposals` (структурно
некорректный или чужая форма), `unsupported_schema_version`, `empty_proposals`,
`too_many_proposals` (больше 20 000), `proposals_too_large` (больше 8 МиБ) и
`duplicate_proposal_id`. Проверки, общие с запросом `edit`
(`edit::validate_request`), добавляют к ним `empty_guid` и `empty_field`, а повтор
пары «`guid`, поле» — это отдельный код `duplicate_edit_target`, а не `reason`
внутри `invalid_request`.

### `models`

Фактическая схема полей моделей области: как поля называются, в каком порядке
лежат в `fields` заметки, что в них реально написано и какие конструкции
шаблонов понимает превью. Это вход для создания заметки и для визуального отчёта:
имя поля — не контракт, а факт конкретного экспорта.

```bash
EXPORT=decks/japanese/words/Words__N1

# модели корневой колоды экспорта (селектор по умолчанию — preorder 0)
anki-repo models "$EXPORT"

# колода по имени, по идентичности или по позиции в обходе
anki-repo models "$EXPORT" --deck "Words::N1"
anki-repo models "$EXPORT" --deck-uuid 00000000-0000-0000-0000-000000000000
anki-repo models "$EXPORT" --deck-preorder 1

# сколько примеров значений показывать на поле (1..10, по умолчанию 3)
anki-repo models "$EXPORT" --sample-limit 5
```

Селекторы можно комбинировать: все указанные обязаны указывать на один узел, а
несогласованность — ошибка `deck_identity_mismatch` (код возврата 3), а не повод выбрать
один из них. Пустой селектор означает корневую колоду экспорта.

По каждой модели в области выводятся:

- идентичность (`crowdanki_uuid`), имя, вид (`standard` или `cloze`), тип модели и
  то, объявлена ли модель в поддереве колоды или унаследована;
- сколько заметок этой модели лежит в самой колоде и во всём поддереве;
- поля **в порядке `ord`** — именно `ord` является индексом значения в `fields`
  заметки, поэтому поля, объявленные в другом порядке, выводятся в порядке
  применения, а не объявления;
- по каждому полю: описание из модели, если оно объявлено, число пустых значений
  в колоде и до `--sample-limit` примеров непустых значений с `guid` заметки-донора;
- по каждому шаблону: `ord`, имя, используемые поля и специальные поля, а также
  отдельный список конструкций, которые превью статически не вычисляет
  (`{{cloze:…}}` и прочие фильтры, `<script>`, структурно битые шаблоны);
- `schema_problems` — причины, по которым схема полей непригодна для сборки
  значений (пропуск, повтор или нечисловой `ord`). Такая модель остаётся в ответе
  со свидетельством, но `create` по ней откажется работать.

Пример значения — это свидетельство, а не гарантия формата: значение берётся из
фактической заметки и обрезается по длине. Именно по нему агент понимает, что за
поле перед ним (например, что «Ударение» — это `<img>`, а не текст).

Проверок на запись у `models` нет и быть не может: команда ничего не пишет.

### `create`

Добавление новых заметок в **уже существующую** колоду **уже существующей**
модели. Команда не создаёт ни колод, ни моделей, ни полей: она работает с той
схемой, которую объявляет сам экспорт.

```bash
EXPORT=decks/japanese/words/Words__N1
REQUEST=create.json

# 1. сначала dry-run: посмотреть, что получится
anki-repo create "$EXPORT" --request "$REQUEST"

# 2. записать ту же самую заметку
anki-repo create "$EXPORT" --request "$REQUEST" --apply

# 3. зафиксировать результат в переносимом виде
anki-repo create "$EXPORT" --request "$REQUEST" --apply --emit-resolved resolved.json

# запрос можно читать со stdin
cat "$REQUEST" | anki-repo create "$EXPORT" --request -
```

#### Формат запроса

```json
{
  "schema_version": 1,
  "notes": [
    {
      "note_id": "новая-заметка-1",
      "guid": "w0Wc3Ip@N#",
      "deck": { "path": "Words::N1", "crowdanki_uuid": "…" },
      "model": { "mode": "auto" },
      "fields": {
        "Слово": "новое",
        "Часть речи": "",
        "Значение": "значение",
        "Ударение": "…",
        "Пример": "…",
        "Похожие слова": "…"
      },
      "tags": ["черновик"]
    }
  ]
}
```

- `note_id` — метка вызывающей стороны: она возвращается в отчёте и в ошибках,
  чтобы агент связал исходы с запросом. Экспорт её не видит.
- `deck` — селектор колоды: `path`, `crowdanki_uuid` и/или `preorder`. Все
  указанные обязаны указывать на один узел. Запись в колоду, которая не
  объявляет `crowdanki_uuid`, отклоняется (`unresolved_deck_identity`).
- `model` — `{"mode": "auto"}` (по умолчанию) или
  `{"mode": "explicit", "crowdanki_uuid": "…"}` / `{"mode": "explicit", "name": "…"}`.
  В режиме `auto` модель ищется по совместимости с набором имён полей запроса;
  поэтому опечатка в имени поля выглядит как `unknown_model` с сообщением,
  которое перечисляет фактически запрошенные имена. Неоднозначность
  (`ambiguous_model`) — ошибка с кодом возврата 5, а не повод выбрать первую модель.
  Правило `auto` целиком, без догадок и приоритетов по частоте:

  1. кандидаты — модели экспорта с полностью используемой схемой (битая схема
     отсеивается как `model_schema_unusable`) и ровно тем же набором имён полей,
     что и запрос, — ни больше, ни меньше. Отсев битых схем идёт первым: если
     подходящей по именам поля модели нет именно из-за схемы, отказ будет
     `unknown_model`, а `details.rejected` назовёт каждую отсеянную модель и её
     `schema_problems` — «модели нет» и «модель есть, но непригодна» это разные
     вещи, и вторая не должна выглядеть как первая;
  2. если среди них есть модели, заметки которых лежат в поддереве целевой
     колоды, кандидатами остаются только они;
  3. если таких моделей нет (например, колода ещё пустая), кандидатами остаются
     все совместимые модели экспорта — правило «единственная совместимая схема»,
     и оно называется в `model_evidence` прямо («в поддереве целевой колоды нет
     заметок совместимых моделей…»). Если совместимых моделей больше одной,
     отказ обязателен: соседние по дереву колоды сами по себе основанием для
     выбора не служат;
  4. ровно один кандидат — выбор; ноль — `unknown_model`; больше одного —
     `ambiguous_model` со списком кандидатов и числом их заметок в поддереве.

  `model_evidence` в каждом исходе сообщает, какое из этих правил сработало, и
  какую роль сыграли заметки целевой колоды. Когда нужна определённость, а не
  вывод — указывай `mode = explicit`: это единственный способ гарантированно
  попасть в конкретную модель при нескольких совместимых схемах.
- `fields` — значения по **именам** полей модели. Обязаны присутствовать все поля
  модели; пустая строка — это законное пустое значение. Порядок ключей не важен:
  в `fields` заметки значения всегда попадают в порядке `ord`.
- `guid` — необязательный. Без него `guid` генерируется (`guid_generated: true` в
  отчёте) и попадает в файл `--emit-resolved`, чтобы повторный запуск был
  идемпотентным.

Успешный прогон с `--emit-resolved` пишет **два** результата: разрешённый запрос в
указанный файл и сам отчёт в `stdout`. В `--json` разрешённый запрос не дублируется
(запрос на 20 000 заметок раздул бы конверт), поэтому переносимым артефактом
является именно файл, а не вывод команды.

Порядок записи — часть контракта, а не деталь реализации:

1. разрешённый запрос планируется целиком (все заметки, их `guid` и модели);
2. путь артефакта сверяется с `deck.json` по нормализованному пути: `--emit-resolved`
   в сам `deck.json`, в его символическую ссылку или в путь, отличающийся только
   записью (`./`, `..`, регистр на нечувствительной файловой системе), —
   это `invalid_request` с `reason = emit_resolved_aliases_source`, и **до** любых
   изменений;
3. артефакт записывается целиком и атомарно — временный файл рядом, затем `rename`;
4. только после этого публикуется `deck.json`;
5. если публикация провалилась, заметка не создана, но артефакт уже на диске —
   с `guid` каждой заметки. Повторный запуск с этим артефактом либо создаст ровно
   одну заметку, либо сообщит `already_applied`: молчаливой второй заметки не будет.

Обратный порядок (сначала `deck.json`, потом артефакт) отвергнут: отказ записи
артефакта после успешной правки экспорта вернул бы ошибку при уже созданной
заметке и потерял бы выданный `guid`. Откат после `apply` тоже отвергнут: он
превращает частичный сбой в потенциальное уничтожение чужих правок.

В dry-run `--emit-resolved` тоже пишет артефакт, но `deck.json` не меняется:
артефакт — это отдельный результат команды, а не следствие правки экспорта.
Каталог артефакта должен существовать: `create` не создаёт каталоги по чужому
пути, а сообщает `write_failed`.
Отсутствие `--emit-resolved` ничего не меняет: без него `create` работает как
раньше, а каждый `guid` всё равно виден в отчёте.
- `tags` — необязательный список тегов новой заметки. Теги проверяются тем же
  правилом, что и в `retire`, и повтор ищется так же, как его ищет Anki — без учёта
  регистра: `["Дом", "дом"]` это один тег в двух написаниях, и такой запрос
  отвергается (`duplicate_tag`), а не создаёт заметку с тегом дважды.

#### Три исхода каждой заметки

| Статус | Что произошло |
|---|---|
| `created` | заметки с таким `guid` не было, и она добавлена (или была бы добавлена в dry-run) |
| `dry_run` | запись не запрашивалась: показано, что было бы записано |
| `already_applied` | заметка с таким `guid` уже есть, и её содержимое совпадает с запросом: файл не перезаписывается |

Если заметка с таким `guid` уже есть, но **содержимое отличается** — это
`guid_conflict` (код возврата 6), а не молчаливое обновление: `create` не редактирует
существующие заметки, для этого есть `edit`.

#### Что гарантируется

- По умолчанию новые значения полей не содержат ссылок на медиа
  (`media_forbidden`, код возврата 3). Исключение — явно настроенный обработчик
  домена из описанных ниже правил; он допускает только проверенные ссылки
  `img/src` на изображения этого домена.

  Ссылкой считается:

  - `[sound:имя]` в любой записи, включая `[sound: имя]` и `[sound: путь/имя]`;
  - атрибут медиа у элемента, который его несёт, — по общей таблице
    `ADDRESS_ATTRIBUTES`: `src` у `img`, `audio`, `video`, `source`, `track`,
    `input`, `embed`, `iframe`, `frame`, `script`; `srcset` у `img` и `source`;
    `poster` у `video`; `data` у `object`; `href`/`xlink:href` у SVG `image` и
    `feImage`; устаревший `background` у `body`, `table`,
    `thead`, `tbody`, `tfoot`, `tr`, `td`, `th`;
  - атрибут медиа у элемента, который его несёт, встретившийся в незакрытой
    конструкции (`<img src="a.png"` без `>`): разметка непонятна, а значение поля —
    не документ: Anki склеивает его с шаблоном, и незакрытый тег может закрыться уже
    там, став настоящим запросом файла. «Не понял» здесь означает отказ, а не
    пропуск. Навигационные атрибуты (`href` и прочие) в это правило не входят: они
    файла не запрашивают, и незакрытая запись перехода ссылкой на медиа не делает.
    Сама граница доверия отчёта незакрытую конструкцию тоже отвергает — как
    непонятую разметку, — но по другой причине и другим правилом.
  - адрес в CSS внутри значения поля: `url(…)` в `style`-атрибуте и в `<style>`,
    `image()`/`image-set()` и `src` в `@font-face`, а также `@import` — правило
    называется целиком. Адрес в CSS — такая же ссылка на файл: браузер пойдёт по
    нему из карточки, а `@import` принесёт в неё ещё и чужую таблицу стилей. Своего
    разбора здесь нет: адреса называет владелец политики адресов отчёта
    (`report::css`), поэтому «что здесь адрес» решается один раз, а не дважды.
    Значение `style` перед разбором раскодируется — браузер раскодирует символьные
    ссылки в атрибуте, и `url&#40;a.png&#41;` для него адрес, а не текст. Ссылка,
    которой разбор не знает, — отказ: адрес в таком значении не виден;

  Запись тега и атрибута значения не имеет: `<IMG SRC = a.png>`, `<img srcset="…">`
  и `<img src="a.png">` — одно и то же. `<img alt="a.png">` и `<функция src=x>`
  ссылкой не считаются, а незакрытые кавычки — это всё ещё адрес.

  `<div src="не-адрес">` тоже не ссылка, и это не послабление, а семантика: такого
  атрибута у `div` нет, и браузер по нему ничего не запрашивает. Значит, «что здесь
  адрес» определяется элементом, а не именем атрибута, — и таблица устроена
  соответственно: атрибуты медиа перечислены поэлементно, зато навигационные
  (`href`, `xlink:href`, `action`, `formaction`, `ping`, `manifest`, `cite`,
  `longdesc`, `usemap`, `archive`, `classid`, `codebase`) объявлены для любого
  элемента. Переход не запрашивает файл, но уводит документ за его пределы, и
  неполный список здесь означал бы живой внешний адрес в офлайн-отчёте.
  `href` у `use` остаётся навигационным намеренно: тем же атрибутом адресуется и
  фрагмент внутри документа (`#иконка`), который файла не запрашивает, а таблица
  различает элементы и атрибуты, а не значения.
  Один разбор HTML (`htmlscan`) и одна таблица «что здесь адрес» обслуживают и
  этот гейт, и `visual-report`: расхождение между ними невозможно. По той же причине
  адреса в CSS называет не гейт, а `report::css` — владелец политики адресов отчёта.
- Новая заметка описывается ровно ключами `__type__`, `fields`, `guid`,
  `note_model_uuid`, `tags`: чужие ключи в заметку не попадают.
- Заметка добавляется **в конец** `notes` целевого узла, остальные заметки не
  сдвигаются и не переписываются. Единственное исключение из правила «существующие
  заметки не меняются» — доказанная миграция прежнего имени медиа командой
  [`migrate-media`](#migrate-media); сам `create` чужих заметок не трогает.
- Перед записью кандидат переразбирается и проверяется (`candidate_reparsed`,
  `appended_notes_verified`, `only_notes_and_media_files_appended`, `guids_resolved_without_conflict`),
  а `validation` сравнивает коды до и после: если кандидат приносит новую ошибку,
  записи не будет.
- Требуется канонический `deck.json`; запись атомарна и защищена от конкурентной
  правки так же, как в `edit`.

#### Правила явного разрешения медиафайлов

`create` ищет ближайший родительский каталог экспорта с `.git` (каталогом или
файлом-маркером рабочего дерева Git), затем читает `.anki-repo/create.yaml` из
этого репозитория. Текущий каталог процесса на выбор правил не влияет. Если файла
правил нет, сохраняется прежнее поведение без медиафайлов. Флаги
`--create-config PATH`, `--asset-store PATH` и `--pitch-asset-store PATH`
позволяют указать отдельные правила и хранилище каждого домена для экспорта;
ошибка при этом возникает, если явно указанный файл правил отсутствует. По
умолчанию используются `.asset-store/kanji` и `.asset-store/pitch-accent` того же
репозитория. Без ссылок на медиа ни одно хранилище не открывается; домен, на
который запрос не ссылается, хранилища не требует.

```yaml
schema_version: 1
note_models:
  - crowdanki_uuid: "identity-from-models"
    fields:
      ExactFieldName:
        processors:
          - type: kanji_assets
      OtherExactFieldName:
        processors:
          - type: pitch_accent
```

Идентичность модели — фактический `crowdanki_uuid`, поле — точное имя из `models`.
Имена моделей не участвуют в выборе обработчика. Правило для другой модели
допустимо; несуществующее поле в правиле выбранной модели даёт
`config_stale_field`. Неподдерживаемая версия, неизвестные ключи и типы,
повторяющиеся ключи, UUID моделей, имён полей и обработчиков, а также
неоднозначная структура YAML приводят к отказу целиком. Файл правил задаёт выбор
обработчиков, но не перечень изображений. Правило в репозитории задаёт
`note_models[].crowdanki_uuid` конкретной модели заметок из текущих экспортов;
это описание данных на сегодня, а не контракт кода.

`processors` — непустая упорядоченная цепочка: обработчики вызываются в порядке
списка YAML. Поддерживаются два типа — `kanji_assets` и `pitch_accent`; неизвестный
тип остаётся ошибкой конфигурации, а повтор одного типа в одном списке
отвергается до исполнения, потому что элемент правила описывает только `type` и
не несёт отдельной конфигурации, которой различались бы два его вхождения.
Внутренняя граница композиции позволяет каждому обработчику объявлять только
распознанные им ссылки. Каждая ссылка должна получить единственного владельца;
конфликт нескольких владельцев даёт `media_reference_conflict`, отсутствие
владельца — `media_reference_unclaimed`. Наличие цепочки не разрешает остальные
ссылки поля. Ненастроенные модель или поле по-прежнему не получают обработчиков.

Значение поля задаёт сам запрос. Обработчик принимает только полный HTML-элемент
`img/src`, распознанный общим разборщиком HTML. `kanji_assets` принимает имя
файла без каталога, содержащее один поддерживаемый иероглиф Han/CJK и точное
расширение `.gif` или `.png`, например `<IMG SRC = '漢.gif'>`. `pitch_accent`
принимает имя файла без каталога вида `<surface>.pitch.png` — то же каноническое
имя, которое домен выдаёт для этого `surface`. URL, пути, параметры запроса,
якоря, ссылки вида `[sound:...]`, CSS, `srcset` и другие ссылки остаются
запрещенными. Обработчик не создаёт HTML и не подменяет расширение: при
несовпадении имени файла указывается доступное каноническое имя.

`asset-store::AssetStore::read_verified_with_policy` возвращает проверенные байты
и запись по семантике домена. Для создания требуются каноническое состояние
`VERIFIED` и итоговое доверие, подтверждённые владельцем ресурса: решение текущего
валидатора домена либо — там, где домен это допускает — явное одобрение человека
для точного SHA-256 после корректной полной расшифровки изображения. `kanji_assets`
допускает такое одобрение: автоматические свидетельства при нём сохраняются, а
явный отказ человека снимает доверие к текущим байтам. `pitch_accent` доверяет
только текущему автоматическому `VERIFIED` от `jpdb-pitch-accent-render` для
точного SHA; одобрение человека там не заменяет
автоматическое решение, а устаревшие свидетельства другой версии валидатора не
пригодны даже при совпадающем SHA. Также требуются совпадение контрольной суммы,
размера и формата, а также дескриптор файла, открытый без перехода по
символическим ссылкам и остающийся в границах хранилища. `.runtime` не
используется. Разрешение ссылок не загружает изображения и не обращается к сети;
отсутствие изображения блокирует создание и требует отдельного получения через
`kanji-assets` или `pitch-assets`.

Плоское пространство имён `media/` CrowdAnki общий для всех доменов. Если две разные
идентичности или обработчики разрешаются в одно имя файла с разными байтами,
`create` отказывает целиком с `media_filename_collision` и не выбирает порядок
обработчиков. Одинаковый SHA при одном имени конфликтом не считается.
Неизвестный `namespace` в закреплённом `media_assets` даёт `media_domain_unknown`:
порядок обработчиков выводится из `identity.namespace`, а не из имени файла.

То же плоское пространство имён — источник единственного известного конфликта имён:
прежний конвейер называл pitch-картинку `<surface>.png`, и для односложного слова
с запасным kanji-изображением это имя совпадает с каноническим именем изображения символа.
Такой конфликт разрешается не перезаписью файла и не ручной правкой `deck.json`, а
отдельной командой [`migrate-media`](#migrate-media), которая переводит ссылки на
текущее каноническое имя и освобождает прежнее имя. `create` при этом видит уже
согласованное состояние и просто размещает запасное kanji-изображение под освободившимся
именем.

Пробный запуск выполняет все предварительные проверки без записи в JSON, `media/`,
файл правил и хранилище. JSON `media` содержит первые 50 элементов `references`
(индекс заметки, UUID модели, поле, имя файла, идентичность), полное число ссылок
в `references_total` и признак усечения `references_truncated`; `assets`
(идентичность, `canonical_filename`, `sha256`, относительный `destination`,
`action: copy|reuse`),
`media_files_added`, `mutations_planned` и `mutations_applied`. Если целевой файл
занят, команда возвращает ошибку с `action: conflict`. `outcomes[].processor_fields`
показывает выбранные поля даже для запроса без ссылок на медиа;
`media_references` при этом может быть ненулевым. Человекочитаемый вывод содержит
краткую сводку медиа-плана; полный план доступен в JSON.

Разрешённый файл запроса v1 дополнительно содержит `media_assets`: отсортированный
список идентичностей, имён файлов и SHA-256 без путей на конкретном компьютере.
Список может быть пустым и всё равно закрепляет набор. Его можно передать обратно в
`--request`; изменение, удаление или переименование закреплённого изображения
даёт `stale_pinned_asset`. Старые запросы v1 без поля `media_assets` остаются
совместимыми и не закрепляют набор. Для нового выбора используйте исходный запрос
без старых закреплений. `--emit-resolved` записывается до изменения медиафайлов и
не может перезаписать исходник, `media/`, файл правил или хранилище.

При `--apply` запрос, правила, изображения, все целевые файлы и кандидат
проверяются до первого изменения экспорта. Общая устойчивая блокировка каталога
экспорта упорядочивает `edit`, `retire` и `create`; изменившийся исходник
отклоняется до размещения файлов. Проверенные байты сначала записываются во
временный файл, затем публикуются жёсткой ссылкой без замены существующего файла.
Если целевой файл появился одновременно и содержит те же байты, он используется
повторно; другие байты приводят к `conflict`. Символические ссылки и объекты,
которые не являются обычными файлами, отклоняются. Полная инвентаризация
пользовательского `media/` для выбора изображений не выполняется.

Только после размещения медиафайлов публикуется `deck.json`. Имена добавляются в
корневой `media_files`, если их ещё не объявил ни один узел; прежние объявления и
их порядок сохраняются. Проверка сначала подтверждает точное добавление заметок,
затем точные добавления в `media_files` сравнением всего JSON.
`only_notes_and_media_files_appended` и `media_assets_verified` подтверждают эти
проверки; `only_notes_appended` истинен только без добавления объявлений.
`media_references_absent` показывает фактическое отсутствие ссылок на медиа.

При частичном отказе `deck.json` не публикуется; уже скопированные корректные
файлы остаются для безопасного повторного использования. Повтор того же запроса
восстанавливает отсутствующий файл или объявление без дублирования заметки;
`already_applied` относится к заметке, а `media.mutations_applied` — к
восстановлению медиафайла. После восстановления полный повтор становится
пустой операцией. Общая блокировка согласует процессы записи, которые используют
тот же протокол; внешний процесс записи должен соблюдать его.

Новые причины доступны в `error.details.reason`, дополнительные данные —
в `error.details.evidence`; русское сообщение не является API:

| `reason` | код / код возврата | Значение |
|---|---|---|

| `config_invalid`, `config_unsupported`, `config_stale_field`, `config_context` | `invalid_request` / 3 | Правила невалидны или устарели либо не удалось разрешить контекст экспорта |

### `migrate-media`

Переводит доказанные ссылки с прежнего имени файла на текущее каноническое
имя домена. Это единственное узкое исключение, при котором набор инструментов меняет поле
уже существующей заметки.

```bash
# 1. сначала dry-run: доказать семантику ссылок и посмотреть план
anki-repo migrate-media EXPORT --namespace pitch_accent --key 飴 --from 飴.png

# 2. записать: переписать ссылки, разместить канонические байты, освободить имя
anki-repo migrate-media EXPORT --namespace pitch_accent --key 飴 --from 飴.png --apply
```

Когда план предусматривает освобождение прежнего имени, при `--apply` команда
удерживает `ExportLock`, повторно сверяет присутствие, размер и SHA-256 файла
со снимком, снятым при построении плана, и останавливается с
`legacy_media_changed`, если состояние разошлось. Сверка выполняется до
размещения файлов и публикации `deck.json`, затем повторяется непосредственно
перед удалением старого файла.

Зачем она нужна. Плоское пространство имён `media/` CrowdAnki общее для всех
доменов, а канонические имена домены разводят намеренно: kanji-домен кладёт изображение
символа под `<char>.gif|png`, pitch-домен — под `<surface>.pitch.png`. Прежний
конвейер называл pitch-картинку `<surface>.png`, и для односложного слова с
запасным kanji-изображением это имя совпадает с каноническим именем изображения символа: под
одним именем оказываются два разных файла. `create` обязан отказать
(`destination_media_conflict`) и не выбирать, чьи байты важнее. Команда переводит
такие ссылки на текущий контракт, после чего имя освобождается и канонический
файл изображения символа размещается под ним без конфликта.

`--namespace` — пространство имён домена, которому принадлежит **каноническое**
имя (`kanji`, `pitch_accent`). `--key` — ключ идентичности внутри домена (например,
словоформа). `--from` — точное старое имя файла: безопасное имя файла без каталога,
`..` и управляющих символов. Каноническое имя задаёт владелец домена
через `AssetDomainPolicy::canonical_location`; команда получает и проверяет его
по `identity`. Проверку пары старого имени и `AssetIdentity` выполняет отдельный
метод `AssetDomainPolicy::proves_legacy_consumer_filename`. Флаги
`--create-config`, `--asset-store`, `--pitch-asset-store` те же, что у `create`.

#### Что команда считает доказательством

До открытия хранилища команда доказывает, что конкретная пара `AssetIdentity` и
`--from` разрешена политикой домена. Это не выводится из старого пути хранения и
не зависит от наличия ресурса в хранилище. Разрешены только точные безопасные имена:
для `kanji` — `<key>.gif` или `<key>.png`, для `pitch_accent` — `<key>.png`;
общая политика имён не объявляет.

Затем команда инвентаризирует **всех** потребителей этого имени в экспорте:

- в значениях полей заметок, разрешённых по фактическим UUID модели и именам
  полей из `.anki-repo/create.yaml`; каждый адрес должен принадлежать ровно
  одному настроенному обработчику и иметь точную форму, которую он распознаёт,
  — полный элемент `img/src` со значением `--from`;
- в `note_models[].tmpls[].qfmt`, `afmt` и `note_models[].css`. Такие ссылки —
  статические потребители, для которых нельзя доказать владение отдельной
  заметкой и идентичностью, поэтому они блокируют миграцию, даже если находятся в
  другой модели или не связаны с мигрируемым полем.

Проверяются адреса, а не любое появление строки в обычном тексте. При поиске
учитываются URL-кодирование пути, параметры запроса и якорь: например,
`飴.png?cache=1`, `飴.png#front` и `%E9%A3%B4.png` указывают на тот же файл для
инвентаризации. Однако `srcset`, CSS-адрес в значении поля, `[sound:…]`,
незакрытая конструкция, имя с каталогом и значение, которое после разбора не
совпадает с точной формой обработчика, не принадлежат ему.
Если ссылка или неоднозначная конструкция не может быть доказана, команда
останавливается целиком, ничего не меняет и возвращает свидетельства. В них
указаны `guid` и поле заметки либо статическая поверхность (`qfmt`, `afmt`,
`css`), `model_uuid`, путь поддерева и причина, например
`field_not_owned_by_domain`, `reference_shape_not_claimable`,
`field_position_not_described_by_model` или
`static_model_reference_not_owned_by_domain`. Счётчики отличают все найденные
адреса медиафайлов от ссылок, которые обработчик смог заявить. Так неподтверждённый
потребитель нельзя молча оставить со старым именем.

#### Что команда пишет

- **Поле заметки.** Все точные диапазоны собираются по исходному значению поля,
  проверяются на пересечение и заменяются согласованно. Несколько ссылок в одном
  поле не сдвигают диапазоны следующих замен; остальной текст сохраняется.
- **`media/<canonical>`.** Байты берутся из проверенного хранилища домена теми же
  требованиями доверия, что и у `create` (для `pitch_accent` — только текущий
  автоматический статус `VERIFIED` от ожидаемого валидатора). Прежний файл **не**
  переименовывается: совпадение SHA с каноническими байтами даёт `reuse`, другие
  байты — `copy`, а занятое чужими байтами каноническое имя — отказ
  `destination_media_conflict`.
- **`media_files`.** Команда проверяет объявления `--from` и канонического имени
  во всех узлах дерева `children`. Повтор прежнего или канонического объявления в
  разных узлах — `media_declaration_conflict` с путями конфликтующих поддеревьев.
  Одно каноническое объявление должно покрывать поддеревья всех перенесённых
  заметок: уже подходящее сохраняется, иначе объявление размещается в ближайшем
  общем родителе потребителей и существующего канонического объявления. При новом
  объявлении используется общий родитель прежнего объявления и перенесённых
  заметок; если это тот же узел, имя заменяется на месте. Порядок других
  объявлений сохраняется. Для подстановки канонического имени наличие прежнего имени
  объявления не обязательно.
- **`media/<from>`.** После публикации `deck.json` удаляется доказанное прежнее имя,
  даже если экспорт не объявлял его в `media_files`. Удаляется только обычный
  файл с точным именем без каталога, который был проверен перед записью.

Порядок — проверка потребителей и кандидата, размещение канонических байтов,
публикация `deck.json`, затем удаление старого файла. Обрыв после публикации JSON
оставляет лишний файл, а не битую ссылку. Снимок до команды не выдаётся за
состояние после неё: отчёт содержит отдельные поля для фактического состояния
файла и объявления после завершения. Повторный прогон не удаляет остаток
«на всякий случай».

Команда идемпотентна: прогон, в котором мигрировать нечего, не меняет документ
побайтово и сообщает `changed: false`. Записи `deck.json` предшествует та же
каноническая форма, та же проверка `ERROR` до и после и та же общая блокировка
каталога экспорта, что у `edit`/`create`/`retire`. Без `--apply` команда
показывает план dry-run, но не пишет `deck.json`, `media/` или `media_files`.

#### Единственное исключение из правила «существующие заметки не меняются»

Обычные операции не меняют поля уже существующих заметок. У этого правила есть
**ровно одно** исключение — `migrate-media`: оно разрешено лишь для ссылки в
поле, которое принадлежит тому же доменному обработчику, что и доказанная пара
идентификатор — имя файла. Команда блокирует операцию целиком, если хотя бы один
потребитель остаётся непринадлежащим, статическим или неоднозначным.

Ручная правка `deck.json`, удаление/переименование файлов в `media/` и другие
обходы не допускаются: только команда может сохранить доказательство семантики,
опубликовать канонические байты и согласовать `media_files` по дереву колод.

| `media_files_added`, `media_files_removed` | изменения объявлений |
| `legacy_declared`, `legacy_media` | снимки до записи: объявлено ли `--from` в дереве `media_files`; имя, размер и SHA-256 физического файла (`null`, если его не было) |
| `legacy_declared_after`, `legacy_media_exists_after` | фактическое наличие объявления и файла после завершения команды; dry-run оставляет исходное состояние |
| `legacy_released` | `true` только если файл действительно удалён при успешном `--apply`; не предсказывает результат удаления |
| `validation` | счётчики и новые коды до/после |

### `retire`

Вывод заметки из обращения: к её тегам дописывается один тег, больше не меняется
ничего. Физического удаления в наборе инструментов нет — незаметно потерять заметку
невозможно, а удаляет её человек в Anki, когда сочтёт нужным.

```bash
EXPORT=decks/japanese/words/Words__N1

# dry-run по одному guid
anki-repo retire "$EXPORT" --guid "w0Wc3Ip@N#" --tag "archived::auto"

# запись
anki-repo retire "$EXPORT" --guid "w0Wc3Ip@N#" --tag "archived::auto" --apply

# несколько заметок и пакетный запрос из файла или stdin
anki-repo retire "$EXPORT" --guid "…" --guid "…" --tag "archived::auto" --apply
anki-repo retire "$EXPORT" --request retire.json --apply
cat retire.json | anki-repo retire "$EXPORT" --request - --apply
```

Файл запроса для пакетного режима:

```json
{
  "schema_version": 1,
  "tag": "archived::auto",
  "notes": [
    { "note_id": "н1", "guid": "w0Wc3Ip@N#" }
  ]
}
```

#### Три исхода каждой заметки

| Статус | Что произошло |
|---|---|
| `retired` | тега не было, и он дописан (или был бы дописан в dry-run) |
| `dry_run` | запись не запрашивалась |
| `already_retired` | тег уже стоит: файл не перезаписывается, тег не дублируется |

Тег проверяется тем же правилом, что и теги Anki: он непустой, без пробелов и
служебных символов. Регистр при этом не важен: `тэг` и `ТЭГ` — один тег, поэтому
`already_retired` видит уже стоящий тег в любом написании и второго написания в
заметку не дописывает. Сравнение регистронезависимое и для не-ASCII: теги бывают
кириллическими. Повтор `guid` в экспорте — уже `ERROR` уровня `validate`, то
есть отказ до любой записи; `guid`, которого нет в экспорте, — `unresolved_guid`
(код возврата 3).

#### Что гарантируется

- Меняются **только** `tags` целевой заметки: её `fields`, `guid`,
  `note_model_uuid` и позиция в `notes` остаются байт в байт теми же.
- Заметка остаётся адресуемой: `find --guid` находит её и после вывода из
  обращения (`retired_notes_still_resolvable` в отчёте).
- Порядок тегов сохраняется, новый тег дописывается в конец; повтор тега
  невозможен.
- Перед записью кандидат переразбирается, проверяется, что изменились только теги
  (`only_tags_appended`, `tags_appended_verified`), и сравнивается `validation`.
- Требуется канонический `deck.json`; запись атомарна и защищена от конкурентной
  правки.

#### Отчёт

| Ключ | Значение |
|---|---|
| `dry_run`, `applied`, `tag` | режим, факт замены файла и тег вывода из обращения |
| `source_bytes`, `candidate_bytes`, `byte_delta` | размеры и их разница |
| `notes_total`, `notes_retired`, `notes_already_retired` | счётчики по статусам |
| `outcomes` | по каждой заметке: `note_position`, `previous_tags`, `tags` (до 50 записей) |
| `checks` | результаты пяти обязательных проверок |

`--emit-resolved` у `retire` нет намеренно: запрос уже полностью явный, а
разрешать в нём нечего.

### `visual-report`

Статический отчёт о том, что изменилось между двумя состояниями экспорта: два
каталога, «до» и «после», сопоставляются по `guid`. Отчёт — это каталог с
`index.html`, превью карточек `cards/*.html`, скопированными медиафайлами
`media/<состояние>/*` и манифестом владения `report-manifest.json`; он
открывается браузером офлайн, без сети и без сервера.

Изменённая заметка показывается **двумя независимыми кадрами** — «До» и «После», —
построенными каждый из данных своего состояния. Созданная заметка получает только
«После», заметка, пропавшая из «после», — только «До»: сторона, которой фактически
не существует, не выдумывается. На широком окне кадры стоят рядом, на узком
складываются вертикально.

Интерактивность отчёта — его собственный код, записанный прямо в файлы отчёта:
переключатель светлой и ночной темы, высота кадра по содержимому и локальный
проигрыватель звука. Это не расширение поддержки шаблонов Anki: граница доверия
описана ниже и проверяется тестами.

```bash
EXPORT=decks/japanese/words/Words__N1

# сравнить колоду с её изменённой копией
anki-repo visual-report \
  --before "$EXPORT" \
  --after /path/to/после \
  --out /path/to/отчёт \
  --retire-tag "archived::auto"

# сколько заметок показать подробно в каждом разделе (по умолчанию 200, максимум 1000)
anki-repo visual-report --before … --after … --out … --preview-limit 50
```

Каждая заметка классифицируется ровно одним исходом:

| Исход | Признак |
|---|---|
| `created` | `guid` есть только в состоянии «после» |
| `changed` | `guid` есть в обоих состояниях, и значения полей различаются |
| `retired` | `guid` есть в обоих состояниях, и в «после» появился тег `--retire-tag` |
| `removed` | `guid` есть только в состоянии «до» |
| `unchanged` | `guid` есть в обоих состояниях, поля и теги совпадают |
| `ambiguous` | `guid` повторяется в одном из состояний: отчёт называет это диагностикой `ambiguous_guid` и **не** угадывает, какая заметка имелась в виду |

`removed` — это наблюдение, а не требование удалить: CrowdAnki не удаляет заметку,
пропавшую из JSON, а `retire` не удаляет её физически. Отчёт не воспроизводит
решения импорта и не утверждает, что Anki что-то создаст, обновит или не тронет.

#### Что попадает в отчёт

- счётчики по исходам, число заметок до и после, число записанных превью;
- `--preview-limit` ограничивает число подробно показанных заметок **в каждом
  разделе** отдельно; независимо от него записывается не больше 4000 файлов
  превью, а список в `--json` обрезается до 500 записей (`card_files_total` при
  этом называет фактическое число записанных файлов);
- секции по исходам: поля «до» и «после», построчный diff значений (по токенам
  HTML, а не только по «тексту на экране») и теги с пометкой добавленных;
- превью карточек отдельными файлами в `cards/`, чтобы CSS модели не влиял на
  страницу отчёта и наоборот: у изменённой заметки это два файла состояний, у
  созданной и у пропавшей — по одному;
- диагностика: отсутствующие файлы медиа и отсутствующий звук, ссылки с путями,
  внешние ссылки, символические ссылки, слишком большие файлы, повтор `guid`,
  неполные превью — с указанием состояния, к которому относится диагностика;
- неподдержанные конструкции шаблонов затронутых моделей;
- явный список ограничений отчёта, чтобы читатель не принял превью за рендер Anki.

#### Превью карточек: что поддержано, а что нет

Разбор шаблона статический, поэтому превью честно показывает то, что можно
вычислить без Anki:

- `{{Поле}}` — подстановка значения поля; имя поля чувствительно к регистру;
- `{{#Поле}}…{{/Поле}}` и `{{^Поле}}…{{/Поле}}` — секции по непустому и пустому
  значению, включая вложенные; пустым считается пробельное содержимое, `<br>` и `<div>`;
- специальные поля `Tags`, `Type`, `Deck`, `Subdeck`, `Card`, `FrontSide`; для
  `FrontSide` стороны рендерятся в два прохода, поэтому лицевая сторона попадает
  в оборотную;
- обёртка `card card{N}`, где `N` — `ord` шаблона плюс один, и CSS модели,
  подключённый после базовых стилей.

Сверх этого отчёт воспроизводит ровно те части поведения Anki, от которых зависит
визуальная проверка карточки:

- ночной режим: переключатель темы в отчёте доходит до корня документа, до `body` и
  до самой карточки классом `nightMode`, поэтому Anki-селекторы `.card.nightMode`
  и `.nightMode …` из CSS модели применяются так же, как в Anki;
- звук: `[sound:имя.mp3]` не остаётся текстом, а превращается в локальную кнопку
  повтора с `<audio preload="none">` на скопированный файл состояния;
- высота кадра: она измеряется по содержимому после загрузки медиа и сообщается
  отчёту, а не задаётся фиксированной константой.

Не поддержано осознанно: исполнение JavaScript из шаблонов Anki и значений полей
(в шаблонах Anki `<script>` исполняется, в статическом отчёте — нет: сторона
считается неотрисованной, а сам тег показан видимым текстом), вычисление фильтров
(`cloze`, `type`, `tts`, `furigana`, `hint` и прочих), поля времени выполнения `CardID` и
`CardFlag`, медиа-ссылки из CSS модели (`url(…)` не копируются). Всё это видно в
самом превью сырым текстом и перечислено отдельным разделом отчёта.

#### Медиафайлы

Рядом с отчётом копируются только те файлы, на которые ссылаются **фактически
показанные** превью, и только если файл нашёлся в `media/` того же состояния.
Файлы раскладываются по состояниям: `media/before/<имя>` и `media/after/<имя>`.
Это не украшение структуры: одноимённый файл в «до» и «после» — два разных файла, и
общий путь молча показал бы в кадре «до» содержимое «после». По той же причине файл,
отсутствующий в состоянии «до», не подменяется одноимённым файлом из «после».
Ссылки переписываются на относительный `../media/<состояние>/<имя>` лишь тогда,
когда файл скопирован. Звук `[sound:<имя>]` разрешается тем же способом и тем же
правилом состояния; неразрешённый звук остаётся видимым текстом `[sound:<имя>]` с
пометкой и диагностикой. Внешние ссылки (`http://`, `https://`, `//`, `data:`) не
скачиваются и ничем не подменяются. Ссылка с путём (`../../секрет`) не читается: в
отчёт попадает только базовое имя, а сама ссылка остаётся диагностикой. Имя, которое
нельзя записать в адрес, не копируется вовсе: разделители пути (`/`, `\`), символы
адреса (`:`, `?`, `#`, `%`), символы, которые экранируются в разметке (`"`, `&`, `<`,
`>`), и управляющие символы делают имя неадресуемым, а скопированный файл —
недостижимым. Такая ссылка названа в `media.traversal` и в диагностике
`media_name_unusable`, а не пропущена молча. Символические ссылки не читаются вовсе,
файлы больше 64 МиБ не копируются, всего копируется не больше 4096
файлов. `media_files` — это список ссылок, а не доказательство наличия файла:
отсутствующий файл честно попадает в диагностику, а не выдумывается.

#### Граница доверия в готовом артефакте

Отчёт открывается браузером, поэтому его собственный код отделён от данных:

- собственный код выполнения отчёта разрешён: без него нет ни переключателя темы, ни
  высоты по содержимому, ни проигрывателя. Он записан в сами файлы отчёта, поэтому
  детерминирован и не требует сети;
- внешних зависимостей нет: ни `<script src=…>`, ни CDN, ни шрифтов, ни ссылок в
  сеть — ни от отчёта, ни от данных;
- код шаблона Anki не исполняется: `<script>` из шаблона или значения поля остаётся
  неподдержанной конструкцией, сторона считается неотрисованной, а тег показан
  видимым текстом, а не исполняемым тегом;
- адрес проверяется **структурно**: он приводится к пути относительно корня
  отчёта и допускается только тогда, когда этот путь действительно принадлежит
  набору файлов отчёта. Схема (`http:`, `https:`, `data:`, `javascript:`),
  абсолютный путь, обратный слэш, `?`, `#`, `%` и всё, что после нормализации
  выходит за корень отчёта, — отказ, а не «похоже на локальный адрес». У `srcset` адресов в
  одном значении несколько, и проверяется каждый кандидат, а не начало строки:
  префиксная проверка пропустила бы всё, что стоит в списке после первого;
- данные показаны текстом, а не разметкой: `<script>` из шаблона или значения поля,
  `on*`-обработчик события, запрещённый элемент (`iframe`, `object`, `embed`,
  `link`, `meta`, `base`, `form`, `applet`, `frame`, `frameset`) и внешний адрес
  перестают действовать; отвергнутое не исчезает молча — оно названо в самом
  превью (`не показано …`) и в диагностике `preview_construct_blocked`.
  Исключений для обработчиков нет: `on*` удаляется всегда, а собственная пометка
  сборщика (`data-report-runtime`, `data-report-state`,
  `data-report-theme-value`) в значении поля ничего не разрешает — эти атрибуты
  рантайм отчёта читает, но написать их может кто угодно;
- регистр и запись значения не важны: `<SCRIPT>`, `OnErRoR`, `SRC = "…"` и
  незакрытая кавычка разбираются так же, как их каноническая запись;
- разметка читается так, как её читает браузер, а не так, как она записана:
  `/` у непустого элемента HTML5 игнорирует, поэтому `<script/>` — это открытый
  `script`, и его тело показывается текстом, а не разметкой; комментарий кончается
  там, где его закрывает браузер (`-->`, `--!>`, а также пустые `<!-->` и
  `<!--->`), — иначе всё после него считалось бы комментарием, а браузер исполнял
  бы это как теги. Символьные ссылки в значении атрибута раскодируются перед
  разбором адреса: `url&#40;a.png&#41;` — это для браузера адрес, а не текст.
  Ссылка, которой разбор не знает (`&lpar;`, `&amp` без `;`), — отказ: «не понял»
  здесь означает отказ, а не пропуск;
- CSS модели остаётся оформлением: `@import` не подключается, нелокальный
  `url(…)` заменяется инертным значением, а `</style>` внутри CSS (и внутри
  значения поля) не может закрыть тег и начать разметку — `<` экранируется.
  Значение `style` раскодируется до разбора CSS, а кавычка в нём экранируется при
  записи: иначе атрибут закрылся бы раньше времени, и остаток значения стал бы
  разметкой;
- CSS разбирается лексером, а не поиском подстрок: `url(…)` и `@import`
  распознаются в любом написании, включая экранированный идентификатор функции
  (`u\72l(`), экранированный символ в самом адресе (`url(https\3a //…)`) и
  оборванный `url(` без закрывающей скобки. То, что лексер не смог разобрать
  однозначно, считается адресом, а не текстом;
- проверяемость: одна функция `report::sanitize::inspect` отвечает на вопрос
  «осталось ли в этом файле исполняемое чужое или сетевой адрес», и её проходит
  **каждый** записанный документ — и `index.html`, и `cards/*.html`. Проверка
  выполняется и на строке перед записью, и повторно на файле, прочитанном с диска:
  проверяется артефакт, который открывает человек, а не значение в памяти.
  Поведение кода выполнения при этом проверяется исполнением этого кода в минимальном
  DOM-стенде. Нарушение — отказ `preview_not_offline`/`index_not_offline`, а не
  предупреждение.

Осознанно отвергнуты CSP-хеши и `sandbox` у кадра превью: кадр без
`allow-same-origin` получает непрозрачное происхождение и теряет доступ к своим же
скопированным медиафайлам, то есть ломает ровно то, ради чего отчёт существует.
Проверка «данных как данных» (очистка) строже и не мешает работать офлайн.

#### Границы каталога отчёта и владение им

`--out` обязан быть вне любого `decks/**` и вне сравниваемых экспортов: отчёт —
это сотни файлов, и попадание такого каталога внутрь экспорта было бы скрытой
правкой данных репозитория.

Непустой каталог принимается только тогда, когда он **доказывает**, что он наш: в
нём лежит `report-manifest.json` — список файлов отчёта, записанный прошлым
прогоном. Обычного `index.html` для этого недостаточно: такое имя есть у чего
угодно, и раньше отчёт перезаписывал чужой файл. Правила:

- пустой каталог или отсутствующий — отчёт создаёт его сам;
- каталог с манифестом — повторный прогон: файлы текущего отчёта занимают свои
  места, а файлы прежнего отчёта, которых в текущем нет, удаляются
  (диагностика `out_dir_stale_removed` называет их поимённо);
- каталог без манифеста — отказ `out_dir_not_owned` **без единого изменения**, в
  том числе когда в нём уже лежит обычный `index.html`;
- испорченный, чужой или ссылающийся наружу манифест — отказ
  `out_dir_manifest_invalid` без изменений: половине доказательства владения
  доверять нельзя;
- `--out`, являющийся символической ссылкой, — отказ `out_dir_is_symlink` **без
  изменений**: за ссылкой владение было бы владением над тем, чего мы не выбирали;
- символическая ссылка **внутри** каталога отчёта — отказ `out_dir_entry_conflict`
  без изменений, и обход каталога за ссылки на каталоги не идёт: иначе «внутри
  отчёта» перестало бы означать «внутри отчёта». Владение выдаёт право заменить
  имя внутри каталога отчёта, а ссылка — это другое имя для чего-то другого, и
  замена по ней ушла бы за его пределы. По той же причине имя, которое в
  доказательстве владения означает файл, не может быть каталогом, а имя каталога
  структуры отчёта — файлом: это две разные записи с одним именем, и решать, какая
  из них наша, отчёт не вправе;
- заменить можно только файл отчёта: перечисленный в прежнем манифесте или лежащий
  внутри `cards/` и `media/`, где имя формирует сам отчёт. Имя в корне каталога
  (`index.html`) этим исключением не покрыто: там рядом лежит что угодно, и
  заменить его можно только по доказательству владения. Иначе цель, занятая чужой
  записью, — отказ `out_dir_entry_conflict` без изменений;
- файлы и каталоги внутри каталога отчёта, которых нет ни в манифесте, ни в
  структуре отчёта, — чужие: они не удаляются и не перезаписываются, а называются
  диагностикой `out_dir_foreign_files`. «Файл исчез» и «файл не наш» — разные
  события.

Порядок записи устроен так, чтобы отказ ничего не стоил:

1. весь отчёт собирается в каталоге-сборке рядом с `--out`
   (`.имя.staging-<pid>`), поэтому разбор экспорта, планирование медиа,
   копирование файлов и проверка границы доверия не трогают прежний отчёт;
2. **весь** новый набор проверяется целиком до первой мутации каталога отчёта:
   каждый целевой путь, каждый каталог, через который он получается, и каждое
   устаревшее имя. Частично применённый набор — это не «почти отчёт», а каталог,
   где часть новых документов уже заняла места тех, которые отказ обязан был
   сохранить;
3. собранные файлы переносятся на свои места (`rename`, то есть файл целиком);
4. удаляются устаревшие файлы из списка владения, убираются опустевшие
   подкаталоги структуры отчёта (`remove_dir` не трогает каталог с содержимым,
   поэтому каталог, заведённый не отчётом, остаётся);
5. последним записывается манифест: пока его нет, каталог считается прежним
   отчётом;
6. после переноса каждый файл отчёта проверяется по **настоящему** пути
   (`canonicalize`), а не по строке: файл, оказавшийся вне каталога отчёта, — это
   отказ `report_file_not_confined`, а не «перенос прошёл»;
7. каталог-сборка убирается — и после успеха, и после отказа.

Явно и честно о контракте: прерывание **между** шагами 3 и 5 (например, гибель
процесса) оставляет читаемую смесь старых и новых документов со старым
манифестом, и следующий успешный прогон сходится ровно к текущему набору файлов:
файлы внутри `cards/` и `media/` он заменяет по именам, которые формирует сам, а
устаревшее удаляет по прежнему манифесту. Всё, что оказалось в каталоге не по этим
правилам, остаётся на месте и называется диагностикой. Все отказы *генерации* — а
это единственные отказы, которые инструмент умеет обрабатывать сам, — случаются до
шага 3 и не меняют каталог отчёта вообще.

Проверка `all_files_inside_out_dir` подтверждает, что все файлы отчёта лежат
внутри каталога отчёта и действительно существуют после переноса, а
`media_confined_to_out_dir` — что скопированные медиафайлы лежат в подкаталоге своего
состояния.

### Типовой конвейер

```bash
EXPORT=decks/japanese/words/Words__N1

# 1. что вообще есть в экспорте
anki-repo qa "$EXPORT"

# 2. компактный batch по найденной проблеме
anki-repo --json review "$EXPORT" --qa-code empty_field_value --limit 25 > batch.json

# 3. внешний агент читает batch.json и возвращает документ предложений
#    (schema_version, proposals: proposal_id, guid, field, expected, replacement)

# 4. проверка предложений против текущего состояния экспорта
anki-repo --json review-check "$EXPORT" --proposals proposals.json \
  | jq .result.edit_request > request.json

# 5. dry-run, запись и проверка результата — существующими командами
anki-repo edit "$EXPORT" --request request.json
anki-repo edit "$EXPORT" --request request.json --apply
anki-repo validate "$EXPORT"
```

Добавление новой заметки и вывод старой из обращения идут тем же маршрутом:

```bash
EXPORT=decks/japanese/words/Words__N1

# 1. фактическая схема полей: как поля называются и что в них лежит
anki-repo models "$EXPORT"

# 2. по умолчанию новые значения не содержат медиассылок;
#    исключение — явно настроенный обработчик домена
anki-repo create "$EXPORT" --request create.json            # dry-run
anki-repo create "$EXPORT" --request create.json --apply --emit-resolved create.resolved.json
anki-repo validate "$EXPORT"

# 3. устаревшая заметка не удаляется, а помечается тегом
anki-repo retire "$EXPORT" --guid "…" --tag "archived::auto" --apply

# 4. что именно изменилось — статическим отчётом по двум состояниям
anki-repo visual-report --before "$ЭТАЛОН" --after "$EXPORT" --out /tmp/отчёт \
  --retire-tag "archived::auto"
```

Разделение ответственности в этом конвейере осознанное: `qa` и `review`
детерминированно выбирают материал, внешний агент предлагает содержательную
правку, `review-check` проверяет предложение против факта, а запись в `deck.json`
остаётся за `edit`, `create`, `retire` и `migrate-media` с явным `--apply`. Человеческое решение — что за
заметка нужна и какую пора убрать — принимает агент или человек; набор инструментов проверяет
его выполнимость и делает ровно запрошенное.

### `edit`

Единственная мутирующая команда. Её предмет — значение одного поля одной уже
существующей заметки. Правка адресуется парой «`guid` заметки, имя поля»: `guid`
ищется в экспорте, имя поля разрешается через `note_model_uuid` заметки и
`note_models[].flds[].ord`, а записывается результат в `fields[ord]`.

Без флага `--apply` команда работает как **dry-run**: она полностью вычисляет
будущий файл и все проверки, но не пишет его. С `--apply` файл заменяется
атомарно и только тогда, когда все проверки прошли.

```bash
# одиночная правка: dry-run
anki-repo edit decks/japanese/words/Words__N1 \
  --guid 'D!TAYVuHi,' --field 'Значение' --expect 'было' --set 'стало'

# та же правка с записью
anki-repo edit decks/japanese/words/Words__N1 \
  --guid 'D!TAYVuHi,' --field 'Значение' --expect 'было' --set 'стало' --apply

# пакетная правка из файла запроса
anki-repo edit decks/japanese/words/Words__N1 --request edits.json --apply

# пакетная правка со stdin
anki-repo edit decks/japanese/words/Words__N1 --request - --apply < edits.json
```

Одиночная правка задаётся флагами `--guid`, `--field`, `--expect` и `--set`; все
четыре обязательны и указываются вместе. Пакетная правка задаётся ровно одним
`--request`: либо путь к JSON-файлу, либо `-` для чтения запроса со stdin.
Одновременно указать и `--request`, и `--guid` нельзя.

`guid`, имя поля и значения в примерах выше иллюстративны: `--expect` — не
подсказка, а предусловие, поэтому в реальном запуске он должен совпадать с
фактическим текущим значением поля. Если фактическое значение поля не совпало с
ожидаемым, правка **не выполняется** целиком (в пакете не применяется ни одна из
конфликтующих правок). Это защищает от правки по устаревшему представлению о
содержимом.

#### Формат запроса

```json
{
  "schema_version": 1,
  "edits": [
    {
      "edit_id": "необязательный идентификатор для отчёта",
      "guid": "D!TAYVuHi,",
      "field": "Значение",
      "expected": "было",
      "replacement": "стало"
    }
  ]
}
```

- `schema_version` обязателен и должен быть равен `1`; неизвестная версия
  отвергается.
- `edits` содержит от 1 до 20000 правок; сам файл запроса — не больше 8 МиБ.
- `edit_id` необязателен, но если указан, то не может повторяться.
- Пара «`guid`, `field`» не может повторяться в одном запросе: порядок
  применения к одному и тому же значению был бы неоднозначным.
- Неизвестные ключи в запросе отвергаются: опечатка в имени поля запроса должна
  быть видна сразу, а не молча проигнорирована.

#### Четыре исхода каждой правки

| Статус | Условие | Запись |
|---|---|---|
| `noop_identical` | текущее значение равно и `expected`, и `replacement` | не нужна |
| `applied` | текущее равно `expected`, отличается от `replacement` | выполнена |
| `dry_run` | то же, но без `--apply` | не выполнена |
| `already_applied` | текущее уже равно `replacement` | не нужна |

`already_applied` и `noop_identical` — успешные исходы, а не ошибки: повторный
запуск той же команды с `--apply` завершается с кодом `0` и не перезаписывает
файл (его `mtime` не меняется). Если все правки оказались безрезультатными,
`applied` в отчёте равно `false`.

Четвёртый случай — текущее значение не совпало ни с `expected`, ни с
`replacement` — это конфликт предусловия: код `expected_mismatch` и код возврата 7.
Ни одна правка из пакета в этом случае не применяется; в отчёте перечислены все
конфликты с выборками ожидаемого и фактического значения.

#### Что гарантируется

Правка возможна только для `deck.json`, который уже находится в канонической
форме этого репозитория (LF, отступ 4 пробела, ключи в алфавитном порядке,
non-ASCII без `\u`-экранирования, без завершающего перевода строки). Проверка
строгая: исходник сравнивается побайтово с собственным рендером инструмента
(`serde_json` с `PrettyFormatter` и отступом 4 пробела), поэтому важны и следствия
этого рендера — формат чисел (`1e3` записывается как `1000.0`), короткие
экранирования управляющих символов `\b`, `\f`, `\n`, `\r`, `\t`, `\uXXXX` для
остальных символов U+0000–U+001F. Это не
косметическое требование: каноническая перезапись документа побайтово совпадает с
источником везде, кроме изменённого значения, поэтому правка не может переписать
остальной файл. Исходник в другой форме (компактный JSON, отступ 2 пробела, CRLF,
завершающий перевод строки) отвергается с кодом `source_not_canonical` и кодом
возврата 3, а не «нормализуется» молча.

Перед записью проверяется:

- исходник действительно каноничен (иначе — `source_not_canonical`);
- в экспорте нет ни одного `ERROR` (`export_invalid`), а также нет
  `conflicting_note_model_definition` (`export_not_mutable`), потому что при
  конфликте определений модели имя поля перестаёт быть однозначным;
- заметки в JSON-дереве и в типизированном дереве совпадают по позициям, `guid` и
  `note_model_uuid` — иначе правка адресовала бы не тот `fields[ord]`;
- все цели разрешаются: `guid` найден ровно один раз, поле есть в модели именно
  этой заметки;
- повторный разбор кандидата даёт ровно запланированное значение;
- байтовый diff содержит ровно запрошенный набор изменений: число различных
  строк файла равно числу эффективных правок, каждая различимая строка содержит
  ровно один строковый токен, а мультимножество пар «было → стало» совпадает с
  запросом;
- прирост размера файла объясняется длиной заменённых токенов, включая
  экранирование;
- валидация кандидата не добавляет ни одного нового `ERROR` (новые `WARNING` и
  `INFO` допускаются и показываются в отчёте);
- замена файла атомарна: кандидат записывается во временный файл в том же
  каталоге, сбрасывается на диск и переименовывается поверх `deck.json` с
  сохранением прав доступа. При любой ошибке временный файл удаляется, а
  исходный `deck.json` остаётся нетронутым.

Все эти проверки — внутренние инварианты: их нарушение означает ошибку в самом
инструменте, поэтому завершается кодом `internal_error` (70) без записи.

#### Конкурентные запуски `--apply`

Сравнение исходника с публикацией кандидата выполняются как одна критическая
секция: перед проверкой байтов `deck.json` берётся эксклюзивная кооперативная
блокировка стабильного каталога экспорта, и она удерживается до конца `rename`. Отдельные
`read → compare → rename` такой гарантии не дают: между сравнением и `rename`
другой процесс записи успевает опубликовать более новый результат, который затем молча
затирается.

Что это значит практически:

- одновременные `edit`, `retire` и `create --apply` одного экспорта используют
  одну блокировку каталога. Проигравший проверяет исходник под блокировкой и
  получает `source_changed` (код возврата 7), если снимок устарел. Замена inode
  `deck.json` не заменяет заблокированный каталог, поэтому публикация остаётся
  последовательной;
- блокировка снимается ядром при завершении процесса, поэтому падение
  `anki-repo` не оставляет «залипший» лок;
- ожидание освобождения блокировки блокирующее: процесс не отказывается сразу, а
  дожидается своей очереди. Это осознанно — вместо произвольного отказа захвата
  процесс записи получает доменный ответ `source_changed`;
- гарантия действует между процессами `anki-repo`. Произвольный внешний процесс записи,
  который эту блокировку не соблюдает, обнаруживается только сравнением байтов
  под блокировкой: изменение, попавшее в файл до сравнения, отклоняется
  (`source_changed`), но изменение, случившееся между сравнением и `rename`,
  переносимыми средствами `std` не перехватывается. Обещать для такого процесса записи
  большее нельзя;
- поддерживается только Linux (см. «Требования»); на остальных платформах набор инструментов
  не собирается, поэтому запасной вариант `lock_unsupported_platform` не является
  доступным поведением при выполнении.

#### Ограничения правки

- Меняются только значения полей; `fields` не может стать короче или длиннее.
- Нельзя править `guid`, `note_model_uuid`, `tags`, `media_files`, модели,
  конфигурации и дерево колод: для них нет ни одного аргумента команды.
- `edit` не читает и не изменяет `media/`. Доказанную миграцию ссылок на медиа
  выполняет отдельная ограниченная команда `migrate-media`.
- Один вызов работает с одним экспортом.

#### Отчёт

Человекочитаемый отчёт содержит режим, размеры до и после, число изменённых
строк, статус каждой правки с выборками старого и нового значения, результаты
проверок и сравнение валидации до и после. В JSON-режиме `result` содержит:

| Ключ | Значение |
|---|---|
| `export_dir`, `deck_json` | путь к экспорту и к `deck.json` |
| `dry_run`, `applied` | режим и факт замены файла |
| `source_bytes`, `candidate_bytes`, `byte_delta` | размеры и их разница |
| `changed_lines`, `first_changed_line` | сколько строк файла изменилось и первая из них |
| `edits_total`, `effective_edits` | сколько правок запрошено и сколько меняет значение |
| `summaries` | счётчики по статусам |
| `outcomes` | отчёт по правкам (до 50 записей) и `outcomes_truncated` |
| `validation` | счётчики и новые коды до/после |
| `checks` | результаты пяти обязательных проверок |

## Изменения публичного контракта

### Добавленные команды и гарантии

- Добавлена группа `code-review learning`: `import`, `status`, `validate`,
  `stats`, `patterns`, `search`, `recommend`, `feedback`, `export`, `backup`,
  `restore`, `forget` и `policy`. Она накапливает локальную проверенную историю
  завершённых ревью в `.anki-repo/learning/state.sqlite`, даёт объяснимые
  паттерны, локальный поиск аналогий, guardrailed-рекомендации, аудируемую
  обратную связь, перенос/восстановление и предложения политики. Ни одна из этих
  команд не создаёт замечаний, не меняет `review.json`, `review-queue.json` и
  `semantic-triage.json`, не выполняет suppression и не применяет политику
  автоматически: утверждённый артефакт материализует человек. Отсутствие истории
  не мешает обычному ревью. Поддержка паттерна считается по независимым линиям
  наблюдения (базовая Git-ревизия + структурная единица очереди), повторы одного
  случая между версиями показываются отдельно (`revised_units`); архив версии 3
  переносит поисковые случаи и execution summaries без candidate source snippets,
  а версии 1 и 2 восстанавливаются с совместимыми ограничениями; производные
  артефакты learning публикуются по канонической модели путей и остаются внутри
  клона; поиск, как и `stats`/`patterns`, по умолчанию не смешивает карантин с
  доверенной историей и включает его только явным `--include-quarantine`.
- Добавлены `models`, `create`, `retire`, `migrate-media` и `visual-report`.
  Мутирующих команд стало четыре (`edit`, `create`, `retire`, `migrate-media`),
  читающих — девять. Ни одна из новых команд не
  создаёт колоды или модели: `create` добавляет заметку в существующую
  колоду существующей модели и по явно заданным правилам может разместить
  проверенные медиафайлы;
  `retire` только дописывает тег.
- `visual-report` пишет новый каталог отчёта и **никогда** не пишет внутрь экспорта
  или `decks/**`: это проверяется до первой записи и подтверждается списком
  фактически записанных путей.
- Физического удаления заметки в наборе инструментов нет. Прежнее поведение «отсутствие
  заметки в JSON ничего не удаляет» осталось наблюдением (`removed` в отчёте), и
  именно поэтому вывод из обращения сделан тегом.

### Исправленные контракты

- `models` выводит поля в порядке `ord` и берёт примеры значений по `ord`. Раньше
  порядок был порядком объявления `flds`, из-за чего примеры значений могли
  относиться к другому полю: свидетельство о семантике поля было недостоверным.
- Селекторы колоды у `models` (`--deck`, `--deck-uuid`, `--deck-preorder`) можно
  комбинировать: несогласованность сообщается доменной ошибкой
  `deck_identity_mismatch` с перечислением расхождений, а не отказом разбора
  аргументов. Так одна и та же проверка работает и для селекторов внутри
  JSON-запроса `create`.
- `create --apply` требует, чтобы целевая колода объявляла `crowdanki_uuid`
  (`unresolved_deck_identity`), а не чтобы селектор был задан идентичностью: имя
  колоды остаётся допустимым селектором, но адресация цели после записи обязана
  быть устойчивой.
- Неполное превью в `visual-report` (например, `<script>` в шаблоне) сообщается и
  диагностикой `preview_incomplete` в JSON, а не только строкой в HTML карточки.
- Счётчик `counts.previews` в `visual-report` равен полному числу записанных файлов
  превью, а не числу, посчитанному до их записи. Изменённая заметка даёт два файла
  («до» и «после»), а `--preview-limit` ограничивает число подробно показанных
  заметок, не разрывая пару состояний.
- Медиафайлы для превью ищутся в `media/` сравниваемых экспортов; ссылки переписываются
  на `../media/<состояние>/<имя>` только для фактически скопированных файлов.
- Файлы, на которые ссылается только состояние «до», копируются из `media/`
  состояния «до», а не из «после»: состояние ссылки и состояние файла совпадают.
- `<script>` из шаблона или значения поля показан в превью видимым текстом: он
  остаётся неподдержанной конструкцией, но не становится исполняемым тегом.

### Удалённые сущности

Две сущности удалены из набора инструментов осознанно: их семантику задавала одна конкретная
модель заметок, поэтому они превращали состав текущих пользовательских колод в
вечный контракт набора инструментов. Набор инструментов работает с произвольным CrowdAnki-экспортом и не
знает имён полей конкретной модели.

- Флаг `--word` у `find` и `review` удалён. Он был сокращением для «содержит по
  сырому значению поля `Слово`», то есть единственным содержанием флага было имя
  поля одной модели. Возможность не потеряна и выражается явно:
  `--field <имя поля> --value <значение> --match contains` — ровно та же
  семантика, но имя поля называет вызывающая сторона.
- QA-правило `duplicate_primary_field` удалено. Понятие «главного/головного» поля
  принадлежит конкретной модели заметок, а не формату CrowdAnki, поэтому у набора инструментов
  нет корректной универсальной семантики такого поля. Реестр правил состоит ровно из
  пяти кодов (`empty_field_value`, `leading_whitespace`, `trailing_whitespace`,
  `forbidden_white_span`, `duplicate_note_content`), а групповой контракт —
  `related`, `group_size`, `related_truncated` — принадлежит
  `duplicate_note_content`.
- Публичная константа `PRIMARY_FIELD` из модуля `selection` удалена вместе с ними:
  модуль больше не знает имён полей конкретных моделей, имя поля всегда задаёт
  вызывающая сторона, а сверку с фактическими `note_models[].flds[].name` выполняет
  `ensure_known_field` (доменная ошибка `unknown_field`, код возврата 3).

Снятые контракты не возвращаются незаметно: `qa --code duplicate_primary_field` и
`find`/`review --word` отвергаются как неизвестный код или неизвестный аргумент, и
это зафиксировано негативными тестами в `tests/cli_contract.rs` и
`tests/qa_contract.rs`.

## Режимы вывода

- Обычный режим: человекочитаемый текст на русском языке в `stdout`. Длинные
  значения полей приводятся к одной строке и ограничиваются по длине.
- `--json` (можно указывать до или после подкоманды): ровно один JSON-документ
  в `stdout`, ничего в `stderr`.
- Исключение: ошибки разбора аргументов, которые отлавливает сам clap
  (неизвестный флаг, несовместимая комбинация, значение вне диапазона), он
  печатает текстом в `stderr` и завершает процесс с кодом 2 — JSON-конверт в
  этом случае не формируется, потому что команда ещё не определена.

Успешный ответ:

```json
{
  "schema_version": 1,
  "command": "inspect",
  "result": { }
}
```

Ошибка:

```json
{
  "schema_version": 1,
  "command": "find",
  "error": {
    "code": "not_found",
    "message": "по заданному критерию не найдено ни одной заметки",
    "details": { }
  }
}
```

`schema_version` описывает контракт вывода; `code` — стабильный snake_case
идентификатор, не зависящий от имён внутренних типов Rust.

В JSON-режиме поля заметки представлены объектом, ключи которого идут в порядке
`ord` модели. Если модель повреждена и содержит повторяющиеся имена полей, к
повторному ключу добавляется суффикс `#N`, чтобы объект оставался однозначным.

## Детерминированность

Одинаковые входные данные дают побайтово одинаковый вывод:


- узлы колод обходятся от родителя к детям;
- заметки сохраняют порядок экспорта;
- поля модели выводятся в порядке `ord`;
- распределения сортируются по количеству (по убыванию), затем по значению;
- проблемы в `validate` сортируются по уровню, коду, пути колоды, месту и тексту;
- правки в `edit` разрешаются в порядке запроса, а канонический кандидат
  сериализуется тем же кодом, что и при проверке каноничности, поэтому одинаковый
  вход даёт побайтово одинаковый кандидат;
- замечания в `qa` и `review` сортируются по позиции правила в реестре, затем по
  позиции заметки в экспорте, затем по `ord` поля и его имени; порядок не зависит
  от порядка обнаружения;
- `models` выводит модели по имени, а при одинаковом имени — по
  `crowdanki_uuid` (порядок обхода экспорта здесь не сохраняется: он не часть
  результата, а имя модели — часть данных), поля — в порядке `ord`,
  шаблоны — в порядке `ord`, а примеры значений — в порядке заметок в экспорте;
- `create` и `retire` разрешают заметки и колоды в порядке запроса, а канонический
  кандидат собирается тем же кодом, что и при проверке каноничности;
- `visual-report` обходит заметки в порядке экспорта, диагностика и списки
  media/медиассылок отсортированы, а имена файлов превью задаются номером, а не
  содержимым: одинаковые входные состояния дают побайтово одинаковый каталог
  отчёта. Время, версия и случайные значения в отчёт не попадают;
- предложения в `review-check` сохраняют порядок документа, а счётчики `counts` не
  зависят от того, попала ли конкретная запись в усечённый отчёт;
- `code-review learning` сортирует паттерны, случаи и подсказки по устойчивым
  ключам, а документ рекомендаций не содержит времени: одинаковые вход, история
  и версия политики дают побайтово одинаковый результат, поэтому повтор
  `recommend --out` идемпотентен. Единственное исключение — `recorded_at` в
  журнале обратной связи: метка времени записи события не входит в сравнение
  содержания, поэтому повтор утверждения не создаёт второй записи;
- при отказе правки `deck.json` не изменяется ни на байт.

Исключение одно и названо прямо: `create` без явного `guid`. Сгенерированный `guid`
случаен (он и должен быть случайным — иначе две одинаковые заметки получили бы один
`guid`), поэтому два прогона такого запроса отличаются и результатом, и байтами
кандидата. Воспроизводимость даёт `--emit-resolved`: разрешённый запрос уже
содержит конкретный `guid`, и повторный запуск по нему попадает в `already_applied`
или в `guid_conflict`, а не создаёт вторую заметку.

## Ограничения

- Инструмент намеренно умеет работать только с одним экспортом за вызов.
- `edit` меняет только значения полей существующих заметок: структура экспорта,
  идентификаторы (`guid`, `crowdanki_uuid`, `note_model_uuid`,
  `deck_config_uuid`), `tags`, `media_files` и `media/` недоступны для правки.
- `edit` требует канонический `deck.json`; экспорт в другой форме нужно сначала
  привести к канонической форме отдельной задачей.
- `create` добавляет заметки только в уже существующую колоду уже существующей
  модели: он не создаёт колоды, модели, поля, шаблоны и конфигурации, не меняет
  их и не переносит заметки между колодами.
- `create` не редактирует существующие заметки: совпадение `guid` при другом
  содержимом — это `guid_conflict`, а не обновление.
- `create` по умолчанию запрещает ссылки на медиа. Явные правила домена могут
  разрешить только точные `img/src` на проверенные изображения этого домена из его
  канонического хранилища; при `--apply` в экспортный `media/` попадают только
  эти проверенные байты и соответствующие имена объявляются в `media_files`.
  Аудио, CSS-ссылки на медиа, `srcset`, произвольные картинки, ссылки
  незакреплённого домена и поля без настройки остаются запрещёнными.
- `migrate-media` — единственный путь изменения медиассылки существующей заметки.
  Он требует доказанной пары идентификатор — прежнее имя файла и полного списка
  потребителей в полях заметок, `qfmt`, `afmt` и CSS. При `--apply` он размещает
  проверенный канонический файл, публикует ссылки и объявления по дереву `children`,
  затем удаляет только доказанный старый файл.
- `retire` не удаляет заметки физически и не умеет снимать тег: он только
  дописывает тег вывода из обращения. Удаление — действие человека в Anki.
- `visual-report` не рендерит карточки как Anki: он собирает статические превью по
  ограниченному набору конструкций шаблона (см. раздел `visual-report`), не
  вычисляет фильтры и не исполняет JavaScript шаблонов. Ночной режим, звук и
  высота кадра воспроизведены ровно в объёме, названном в разделе отчёта, и не
  означают полной эмуляции Anki WebView.
- `visual-report` не воспроизводит решения импорта CrowdAnki и не предсказывает,
  что Anki сделает с экспортом: он сопоставляет два состояния по `guid` и
  показывает различия.
- Каталог отчёта — артефакт, а не часть экспорта: он не попадает в `decks/**`, не
  содержит идентификаторов запуска и не обновляется сам по себе.
- `visual-report` отдельно от `create` и `migrate-media` копирует медиафайлы,
  нужные показанным превью, из соответствующего состояния экспорта в каталог
  отчёта и не меняет исходный экспорт. `create` и `migrate-media` размещают в
  экспортном `media/` только проверенные байты доменов и только в описанных выше
  ограниченных случаях; `migrate-media` после публикации может удалить точное
  прежнее имя.
- Поиск не поддерживает регулярные выражения и не нормализует HTML.
- Набор инструментов не знает имён полей конкретной модели: поле всегда называет вызывающая
  сторона через `--field`, а имя проверяется против фактических
  `note_models[].flds[].name` экспорта. Снятый флаг `--word` и удалённое правило
  `duplicate_primary_field` не возвращаются (см. «Изменения публичного контракта»).
- Семантика `--deck` требует точного пути колоды, как он собран из `name` узлов.
- Инструмент не проверяет семантику японского содержимого и не сравнивает колоды между
  собой: `qa` находит только перечисленные структурные и форматные признаки, а
  содержательное суждение о карточке делает внешний агент.
- Инструмент не вызывает LLM и не ходит в сеть. Конвейер `qa`/`review`/`review-check`
  сознательно останавливается на границе репозитория: предложения приносит
  внешний агент, а `anki-repo` проверяет их и отдаёт готовый запрос для `edit`.
- Предложения принимаются только в форме, которую понимает `edit`: правка значения
  существующего поля существующей заметки. `qa` и `review` не предлагают
  добавление, удаление и переименование сущностей, а `review-check` их не примет.
- Усечение отчёта (лимит замечаний на код, страница `review`, предел правок,
  заметок в запросе, записей в отчёте и файлов превью) никогда не скрывает факт
  усечения: счётчики считают всё, а текст сообщает, что остаток не выводится ни в
  человекочитаемом, ни в JSON-режиме.
- Слово «удаление» не входит в словарь мутирующих команд: `create` умеет только
  добавлять, `retire` — только дописывать тег. Заметка, пропавшая из JSON, для
  `visual-report` — это исход `removed`, и отчёт не требует доводить его до
  физического удаления.
- `review-check` проверяет предложение против текущего состояния экспорта, но не
  резервирует его: между проверкой и `edit --apply` содержимое может измениться, и
  тогда конфликт предусловия поймает уже `edit`.
- Неразрешимая цель предложения (`field_not_resolvable`, `ambiguous_guid`) на
  реальном пути почти недостижима: нестроковое значение поля, отсутствие поля и
  повтор `guid` — это уже `ERROR` уровня `validate`, поэтому такой экспорт
  блокирует запрос раньше классификации (`export_invalid`). Проверка остаётся в
  коде как честная классификация для исходника, который прошёл предпроверку, и
  покрыта контрактными тестами.
- Уровни и коды правил QA не настраиваются: реестр правил фиксирован и расширяется
  только кодом, вместе с тестами.
- `code-review learning` не выводит вероятность безопасности нового кода: нижняя
  граница по интервалу Уилсона — мера согласованности накопленных наблюдений, а не
  оценка точности детектора или вероятности дефекта. История собрана выборочно,
  поэтому доли исходов не являются precision/recall.
- Learning не заменяет независимое ревью: он не создаёт замечаний, не назначает
  `disposition`, не выполняет suppression, не понижает baseline priority и не
  исключает ни одну единицу из обязательного просмотра. Подсказка — только
  дополнительное ранжирование; содержательное решение принимает ревьюер по
  актуальному коду.
- Утверждённая политика не хранится в базе как действующее правило и не
  применяется автоматически: `policy approve` материализует артефакт по явному
  пути, а его попадание в Git — решение человека.
- Локальный поиск learning не поддерживает регулярные выражения, не нормализует
  HTML и не выходит за пределы локальной базы. Он ищет по пояснениям решений и
  текстам замечаний, а не по исходному коду: код в историю не копируется. При
  недоступном FTS5 используется подстрочный fallback, и режим назван в
  результате. Карантинные записи пониженного доверия в результаты поиска не
  попадают без явного `--include-quarantine`, а статус доверия возвращённого
  случая виден и в текстовом, и в машинном выводе.
- Learning не переносит артефакты между снимками автоматически: если изменился
  проверяемый HEAD/base или исходный пакет, нужен новый импорт, а прежняя запись
  остаётся аудируемой ревизией.

## Проверки

Все проверки запускаются из корня репозитория — оттуда, где лежит корневой Cargo
workspace (`/Cargo.toml`):

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

`--locked` уместен потому, что `Cargo.lock` лежит в корне и версия workspace — общая
для всех участников.

То же самое независимо от локального окружения выполняет CI
(`.github/workflows/ci.yml`) на `pull_request`, на push в ветку по умолчанию и вручную:
`cargo fmt --all --check`, `cargo clippy --workspace --all-targets --locked -- -D
warnings` и `cargo test --workspace --locked`. Затем CI сам находит `deck.json`
внутри `decks/` и вызывает для каждого `validate`, не называя ни одной колоды,
уровня, модели или поля по имени: если экспортов нет, шаг проходит успешно, а если
найденный экспорт структурно невалиден — шаг падает. CI только читает репозиторий,
поэтому изменение состава `decks/` не требует правки процесса CI; валидность
фактически закоммиченных данных при этом остаётся обязательной проверкой репозитория.

Фактические данные проверяет CI; обычные тесты набора инструментов строят
собственные синтетические экспорты и `decks/**` не читают.

Заявленная MSRV проверяется отдельным заданием на версии из корневого `Cargo.toml`:
процесс CI читает `[workspace.package] rust-version` через `cargo metadata`, заодно
убеждается, что участники workspace не расходятся в этой версии, и собирает
workspace на ней (`cargo +<msrv> check --workspace --all-targets --locked`).
Версия объявлена ровно один раз — в корневом манифесте; ни процесс CI, ни эта
документация не хранят её копию. Локально ту же проверку можно воспроизвести так:

```bash
MSRV=$(cargo metadata --no-deps --format-version 1 | jq -r '[.packages[].rust_version] | unique | .[]')
rustup toolchain install "$MSRV" --profile minimal
cargo "+$MSRV" check --workspace --all-targets --locked
```

`cargo nextest run` (если nextest установлен) можно использовать локально вместо
`cargo test`: CI выполняет именно `cargo test --workspace --locked`.

Набор тестов состоит из:

- unit-тестов доменной логики (разрешение полей через `ord`, обход дерева,
  проверки `find`/`stats`, сканер шаблонов, контракт кодов возврата);
- unit-тесты правил QA: каждое правило проверяется на своих границах (пустое
  значение, пробелы по краям и внутри, белый `<span>`, группировка дубликатов), а
  также порядок замечаний и усечение отчёта; отдельный тест фиксирует, что набор
  правил и уровень каждого кода — публичный контракт, а замечания не зависят от имён
  полей и моделей;
- `tests/synthetic.rs` — синтетические примеры на каждую ветку валидации и
  каждую доменную ошибку;
- `tests/export_contract.rs` — свойства, обязанные выполняться для любого
  корректного CrowdAnki-экспорта: количества, порядок полей и медиа пересчитываются из
  сырого JSON и из содержимого каталога, а форма фикстур намеренно не совпадает с
  формой реальных колод. Ни один тест не требует, чтобы `decks/` существовал или
  содержал конкретные колоды;
- `tests/cli_contract.rs` — аргументы CLI, коды возврата и разделение
  `stdout`/`stderr` через реальный исполняемый файл, включая негативные проверки снятых
  контрактов: флаг `--word` отвергается как неизвестный аргумент;
- `tests/qa_contract.rs` — контракт `qa`: состав реестра (ровно пять кодов, без
  `duplicate_primary_field`), уровень `error` без отказа (и без влияния на
  `validate`/`edit`), границы выборок в `evidence`, `--max-per-code` против полных
  счётчиков, детерминизм, пометка неадресуемых замечаний, полный контекст группы и
  пересчёт чисел независимым подсчётом по сырому `deck.json` на синтетических
  фикстурах (ни одно ожидаемое число не зашито в тест);
- `tests/review_contract.rs` — контракт `review`: размер страницы, полный обход
  пагинации без потерь и повторов, пустая страница за концом выборки, компактность
  пакета, ограничение замечаний внутри заметки, совпадение ошибок `--guid` с `find`,
  приведение участников группы правил-дубликатов (в пределах
  `MAX_RELATED_NOTES`) и исключение неадресуемых заметок с видимым
  `excluded_unaddressable`, а также отказ на снятом флаге `--word`;
- `tests/review_check_contract.rs` — контракт `review-check`: все пять статусов
  предложения, приоритет `stale`/`invalid` (5 → 4 → 3) в коды возврата, отказ на
  документе чужой формы (`edits`) и на устаревшем флаге `--request`, все причины
  `invalid_request` документа предложений (`malformed_proposals`,
  `unsupported_schema_version`, `empty_proposals`, `too_many_proposals`,
  `proposals_too_large`, `duplicate_proposal_id`), перенос метаданных
  (`proposal_id` → `edit_id`, `reason` только в отчёт), отсутствие записи и
  временных файлов, усечение отчёта при полных счётчиках, чтение документа со
  stdin и сквозной конвейер `review → предложения → review-check → edit (dry-run и
  `--apply`) → validate` на временной копии экспорта;
- `tests/edit_contract.rs` — контракт `edit`: режимы dry-run и `--apply`, все
  четыре исхода правки, конфликт предусловия, пакетные ошибки разрешения,
  отказы по неканоничному и невалидному экспорту, схема JSON-ответа, коды возврата
  и равенство путей `--request FILE` и `--request -`;
- `tests/note_lifecycle_contract.rs` — маршрут «схема → создание → вывод из
  обращения» на синтетических экспортах и реальном CLI: свидетельство `models` по
  каждому полю (включая порядок `ord` там, где объявление ему не равно), запись
  заметки с каноническим результатом и структурно валидным экспортом,
  доказательство «изменилась ровно дописанная заметка» через побайтовое сравнение
  с каноническим рендером исходника плюс дописанной заметки, идемпотентность через
  `--emit-resolved`, атомарность пакета (ошибка в любой заметке не пишет ничего),
  все четыре правила `auto` (единственная совместимая модель поддерева, откат к
  единственной совместимой модели экспорта для пустой колоды с этим правилом в
  `model_evidence`, отказ при двух совместимых моделях и при двух моделях с
  одинаковым именем), отказы (`media_forbidden`, `unknown_model`,
  `ambiguous_model`, `guid_conflict`, `unresolved_deck_identity`,
  `source_not_canonical`, `export_not_mutable`), дописывание тега без изменения
  содержимого заметки, повторный запуск без дублирования тега, сохранение
  адресуемости заметки после вывода из обращения и чтение запроса со stdin;
- `tests/visual_report_contract.rs` — контракт `visual-report`: классификация
  каждого исхода по `guid`, неоднозначный `guid` отдельной диагностикой без
  угадывания превью, офлайн-пригодность всех файлов отчёта (в них нет ничего, кроме
  собственного runtime отчёта, и ни одной ссылки в сеть), два независимых кадра
  состояний с фактическими значениями своего состояния, копирование медиа и звука
  только для фактически показанных превью с переписыванием ссылок, раздельное
  хранение одноимённых файлов разных состояний и запрет подмены отсутствующего
  файла файлом из другого состояния, локальный проигрыватель для существующего
  звука и видимая пометка для отсутствующего, побайтовый детерминизм двух прогонов
  вместе с медиа, неизменность обоих сравниваемых состояний после успешного отчёта,
  отсутствие подсветки diff в превью карточек, изоляция CSS модели (маркер CSS
  модели есть в карточке своего состояния и отсутствует на странице отчёта), все
  шаблоны модели в отдельных файлах карточек, отказы каталога отчёта (внутри
  `decks/**`, непустой без доказательства владения — манифеста отчёта, — совпадение
  состояний), неподдержанные
  конструкции шаблона (включая `<script>`, который не исполняется), предел числа
  превью и контракт выполнения: ночной класс доходит до корня документа, `body` и
  карточки, все кадры синхронно получают выбранную тему, высота приходит измеренной
  и обновляется после загрузки медиа. Проверка кода выполнения исполняет записанный код в
  минимальном DOM-стенде под Node и пропускается, если Node недоступен;
- `tests/edit_source_preservation.rs` — физический результат правки: ровно одна
  изменённая строка на правку, сохранение нетронутых строк байт в байт,
  экранирование, переводы строк и Unicode, идемпотентность без перезаписи,
  отказы неканоничных вариантов, сохранение прав доступа, отсутствие временных
  файлов. Колоду целиком строит сам тест, а не берёт из `decks/`: массовые прогоны
  идут по синтетическому экспорту с шестью полями и второй, однополевой моделью во
  вложенной колоде;
- конкурентная публикация покрыта отдельно: unit-тест слоя записи
  детерминированно воспроизводит окно между проверкой и `rename` (два процесса записи
  от одного снимка: публикуется ровно один, второй получает `source_changed`),
  контрольный тест показывает, что та же последовательность без блокировки теряет
  обновление, тест на блокировку проверяет, что публикация действительно ждёт
  освобождения, а `tests/edit_source_preservation.rs` прогоняет два реальных
  процесса `edit --apply` параллельно и проверяет, что итог остаётся каноническим
  экспортом без потерянных правок.

Регрессия на исходную гонку защищена так: детерминированный unit-тест проверяет
итог `replace_atomically` (проигравший не публикуется и получает `source_changed`,
результат победителя остаётся в файле), контрольный тест фиксирует, что
последовательность без критической секции теряет обновление, а тест на блокировку
подтверждает, что без неё публикация не завершается. Само окно гонки внутри
`write_and_publish` недоступно снаружи без тестового шва, поэтому оно проверяется
не подделкой сигнала «вот-вот опубликует», а этими тремя наблюдаемыми свойствами.
